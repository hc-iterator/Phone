# DVI 攻坚流水 · 阶段2：2026-10-01 深夜（后半）：最小对照基准 + 把怀疑钉到「每 bit 约 14.6 周期」

> **覆盖**：原 `docs\DVI攻坚流水.md` 第 782–1424 行（§14.24–§14.43）｜原 643 行 ⇒ 成品 559 行
> **本阶段结论**（每条一句，含判据与"为什么走到下一步"）：
> - **硬件与配置都无罪，问题在【库的用法】**：最小对照（PIO2 一个 SM 跑 `pull block; jmp 0` + 一条 `dma_claim_unused_channel()`，DREQ 接 TX FIFO，`transfer_count = 4096`）实测 4096 字 / 35 µs = **8.5 ns/字 ≈ 1.2 亿字/秒**，且这个数还被 SM 自己（`pull block` 每 2 时钟 1 字 = 7.9 ns/字）限住；对照 DVI 引擎 ~845 ns/字 ⇒ **差约 100 倍** ⇒ 嫌疑直指"每行被拆成 6~7 段、每段由控制通道重新触发"的**链条往返**（845 µs ÷ 7 ≈ 每段 120 µs）。
> - **每行的 IRQ 来自列表【中间某一段】，不是第 0 段**：把第 0 段也改成"不链" ⇒ `g_dvi_irq_count = 0`、引擎只跑 1 行就冻死（已撤销，只留注释）⇒ 后来只能从"行边界"而不是"数据量"去查限速源。
> - **档位类变量全部排除**：`FRANK_HDMI_ENABLE_AUDIO` 开关几乎无影响（1186→1176 行/秒、5.0→4.9 fps）；上一任"约 107 帧后卡死"本次只跑 59 帧 ⇒ **不能下结论**；`DVI_N_TMDS_BUFFERS=3` 与 `N_SCANLINE_BUFS` 都是死线索；库自带排障三条本项目全满足 ⇒ **我们不在这个库的已知问题集里**。
> - **六个 DMA 通道的 CTRL 逐位解完全部正确，列表【每行都走完了】**（§14.32 推翻 §14.26 的"一行在列表走完前就结束"）⇒ 行时长 = 跑完整张列表的时间 = 389 µs，DMA 每字约 490 ns vs DREQ 允许的 79 ns ⇒ **慢 6 倍，问题在"DMA 响应 DREQ 的实际速率"**（随后又被 §14.33 排除）。
> - **限速方是一个【所有构建共有】的量**：撤掉收口+重触发后帧率 4.9→4.7 一点没变，处理器平均耗时靠累加器实测 61.2 µs（15.8% CPU）、最优化后 17 µs，音频/最小固件/所有补丁都不动它 ⇒ 唯一从没量过的共有量就是"**串行器 1 bit/时钟**"这个假设。
> - **把 DVI 串行器原程序搬进基准后实测每字 1157 ns（≈292 时钟 ≈ 每 bit 约 14.6 时钟）**，恰好解释了"所有构建共有"；而 §14.41 又发现对照变体 V2 一个 bit 都不输出 ⇒ **§14.33/§14.36 的对比是混淆的**，真正剩下的问题只有一个："**为什么一条输出 1 个 bit 的 `out` 要花 ~14.6 个周期**"。
> **本阶段已作废 / 已订正（照原文标注，不删）**：14.26 被 14.32 推翻；14.27 被 14.29 订正为过度反应；14.33/14.36 的"pull 版快 vs out 版慢"对比被 14.41 订正为混淆；14.35/14.37 被 14.54 改写（`out pc` 特有 ⇒ side-set 代价）；14.36 判定 `opt` 不是解（红鲱鱼）；14.37 的"`out pc` 这条指令贵"被 14.38 订正为"每 bit 一条 `out` + autopull"；14.42 的 `out null` 隔离不成立。

### 14.24 🎉🎉🎉 2026-10-01 深夜·转折点：硬件与配置都无罪，问题在库的用法

**做法**：新增 `src/pio_dma_bench.c`（临时诊断，已在 `CMakeLists.txt` 里登记），在 DVI 启动**之前**跑一次最小对照：**PIO2 一个 SM 跑 `pull block; jmp 0`**（每 2 个时钟吃 1 字）+ **一条 `dma_claim_unused_channel()` 的通道**，DREQ 接该 SM 的 TX FIFO，一次 `transfer_count = 4096`。

**实测结果**：
```
g_bench_words = 4096
g_bench_us    = 35 µs
g_bench_done  = 1        (PIO2 SM0 + DMA ch2)
```

⇒ **4096 字 / 35 µs = 8.5 ns/字 ≈ 1.2 亿字/秒。**

⚠️ **而且这个数还是被 SM 限住的**：`pull block` 每 2 个时钟吃 1 字 = 7.9 ns/字 ⇒ **DMA 完全跟得上 SM 的极限速率**，硬件毫无问题。

| | 每字 |
|---|---|
| **最小对照（硬件能力）** | **8.5 ns** |
| **DVI 引擎实测** | **~845 ns** |
| 差异 | **约 100 倍** |

#### ⇒ 结论：**配置层面与硬件层面都无罪，问题在【库的用法】。**

**两者最关键的结构差异**：
```
最小对照：一条通道，一次 transfer_count = 4096  ⇒ 一口气搬完
DVI 引擎：一条通道，每行被【拆成 6~7 段】，每段由控制通道重新触发一次
          （transfer_count 分别为 8/48/24/320/8/8 …）
```

**⇒ 嫌疑直指【每段的链条往返延迟】**：845 µs ÷ 约 7 段 ≈ **每段往返 120 µs**。对"控制通道写 4 个字 → 数据通道搬一段"这种操作，120 µs 大得离谱，**但形状对得上**。

#### 下一步（方向已明确，二选一或都做）

1. **量单段往返**：在 IRQ 处理器里记录"两次 chunk 完成之间"的间隔，或直接量一段的墙钟时间。
2. **减少段数**：把一行的 6~7 段合并成更少的段（甚至一段），看行率是否随之上升 —— 若上升，则"每段往返"就是根因，且修法明确。

**⚠️ 清理提醒**：`src/pio_dma_bench.c` 与 `CMakeLists.txt` 里那行登记是**临时诊断**，定位完要删（`dvi_screen.c` 里那段调用也一样）。

### 14.25 2026-10-01 深夜·段不能砍（引擎冻死）+ 一个能对上数的模型 + 我的仪表有漏洞

#### A. ❌ 实验：把每行段数砍到 1 段 ⇒ **引擎直接冻住**

在 `_dvi_load_dma_op()` 里让第 0 段的 `CHAIN_TO` 也"不链"（想试"每行只走一段"）：
```
10 秒后：dvi_frame_count = 0
        frank_hdmi_heartbeat_lines = 1     ← 只跑了 1 行
        g_dvi_irq_count = 0                ← 【一个中断都没有】
```

**⇒ 学到一个设计约束：每行的 IRQ 是由列表【中间某一段】产生的，不是第 0 段。** 让链条在第 0 段就停 ⇒ **产生 IRQ 的那一段永远轮不到** ⇒ 没有中断 ⇒ 处理器不再重触发控制通道 ⇒ **链条死亡**。（已撤销，只留注释。）

#### B. ✅ 一个能对上实测数的模型（重要）

```
每字 79 ns（SM 自己限速：每 20 时钟 1 字）× 每行约 2016 字  = 159 µs
每段往返约 100 µs × 每行约 7 段                            = 700 µs
                                         ─────────────────────────
                                        合计 859 µs  vs  实测 845 µs  ✅ 吻合
```

⇒ **"每段链条往返 ~100 µs" 这个嫌疑被数量级验证了。**

#### C. ⚠️ 我自己的仪表有个大漏洞（必须纠正前文的结论）

`g_dvi_h_us` 是从 IRQ 处理器**入口**量到 **`_dvi_load_dma_op()` 之前** —— **它把处理器后半段（`_dvi_load_dma_op()`、我加的显式重触发、以及末尾的队列操作）全漏掉了。**

**⇒ 前面几节那句"IRQ 处理器已经是 0 µs"是【误导性的】，不能作为"时间不在软件里"的依据。**

#### 下一步（明确）

**给处理器【后半段】补仪表**（从 `_dvi_load_dma_op()` 到函数结束），并**统计每个 IRQ 的完整耗时**（`g_dvi_irq_count` 是 2.55 次/行，所以处理器总耗时 = 2.55 × 单次耗时，这可能是被漏掉的那 700 µs 的大头）。

### 14.26 2026-10-01 深夜·软件洗清；且发现"一行在列表走完前就结束"【后被 14.32 推翻】

#### A. ✅ 处理器确实很快（这次是**完整**仪表）

补上后半段（`_dvi_load_dma_op` + 重触发 + 数据岛）后实测：
```
整个处理器   last 0 µs   max 262 µs
  前半段     last 0 µs   max 260 µs
  后半段     last 0 µs   max  14 µs   ← 极小
IRQ 数 25951 / 10 秒 = 2596/s  （2.19 次/行）
```

⇒ **软件彻底洗清。**（§14.25 C 节说"0 µs 是误导性的" —— 现在补全后，**结论仍然是 0 µs，但这次站得住**。）

#### B. 发现续命段对非同步 lane 是 2 倍超支 —— 但**改掉后毫无变化**

```
一行需要：640 像素 × 10 bit = 6400 bit = 320 字（每字用 20 bit：PULL_THRESH=10×2）

l0：真实 8+48+24+320=400  + 填充 2×8=16   = 416 字 = 8320 bit = 33.0 µs
l1：真实 80+320=400       + 填充 5×80=400 = 800 字 = 16000 bit = 63.5 µs
l2：同 l1
```

⇒ 非同步 lane 的**真实**工作量 400 字 = 31.7 µs **正好用满一行预算**；上一任"把剩余槽位填成第 0 段副本"对 l1/l2 每行多加 400 字（31.7 µs），**看似 2 倍超支**。

**✅ 实测：把续命段的 `transfer_count` 压到 1（`_dvi_fill_unused_slots`）⇒ 行率 1185 → 1186，【毫无变化】。**

#### C. ⭐ 由此得到一个关键认识（比 B 的结果重要得多）

**⇒ 那些多余的字【从来没被搬过】。** 因为 `_dvi_load_dma_op()` 每行都会重新武装控制通道，而**一行的时间远不够走完整张列表** ⇒ **列表没走完就被丢掉了。** ⇒ 上一任"填满槽位"的做法确实是安全的，我这次"优化"是多余的。

**⇒ 更重要的推论：既然一行在列表走完之前就结束，那么"每行 845 µs"就【不是】由搬运的数据量决定的，而是由【行边界本身】决定的。**

**⇒ 问题变成：是什么让行边界落在 845 µs？** 而软件侧已被本轮完整仪表排除。

**下一轮的方向**：查"行边界"的来源 —— 即那个产生 IRQ 的段是谁、它的完成依赖什么（§14.25 A 已确认 IRQ 来自列表**中间某段**，不是第 0 段）。候选：那段完成所需的 DREQ 供给、或该段的 `transfer_count` 与 PIO 消费速率的匹配关系。

### 14.29 ⚠️ 2026-10-01 深夜·自我订正：14.27 说的"口径用错了"是过度反应

**已验证的事实**（`frank_dvi_config.h:35` 与 `frank_hdmi.h:119`）：

**⇒ 正确的说法只有一句：**

**⚠️ 方法论教训（第 11 次记）**：我上轮看到两个数不一致就急着宣布"口径用错了"，**没有先算 525/240 这个比值**。⇒ **看到两个数"对不上"时，先找它们之间的换算系数，再判断是不是矛盾。**

### 14.32 🔴 2026-10-01 深夜·推翻 14.26：列表每行都【走完了】

**读六个通道的活体寄存器**（一次 halt）：
```
控制通道 READ_ADDR（= 它在读哪段列表）:
  ch2 = 0x2005ac44 = active.l1     ← lane0 的控制通道，【刚好走过 l0 整段】
  ch4 = 0x2005acb4 = active.l2     ← lane1 的，【刚好走过 l1 整段】
  ch6 = 0x2005ad24 = error.l0      ← lane2 的，【刚好走过 l2 整段】
      （每段 6 或 7 条 × 16 字节 = 96 / 112 字节，落点分毫不差）

数据通道 CTRL 解码:
  ch3: TREQ_SEL=0(TXF0)  CHAIN_TO=3(=自己⇒不链)   ✅ lane0
  ch5: TREQ_SEL=1(TXF1)  CHAIN_TO=5(=自己⇒不链)   ✅ lane1
  ch7: TREQ_SEL=2(TXF2)  CHAIN_TO=7(=自己⇒不链)   ✅ lane2
控制通道 CTRL: EN=1、32 位、INCR_READ/WRITE=1、CHAIN_TO=自己、TREQ_SEL=0x3F(DREQ_FORCE) ✅
```

**⇒ 三条控制通道各自刚好走完自己那一整段数组，三条数据通道都停在"最后一条"**（`CHAIN_TO=自己` 正是 §14.16 的收口补丁在末条的取值）。


**⇒ 行时长 = 跑完整张列表的时间 = 389 µs；DMA 实际每字约 490 ns，而 DREQ 允许的速率是 79 ns —— 【慢 6 倍】。**

### 14.33 ✅ 2026-10-01 深夜·已排除 DMA 响应慢 DREQ；嫌疑转向处理器平均耗时

**实验**：把 `src/pio_dma_bench.c` 的 PIO 程序从 `pull block; jmp 0`（2 时钟/字）改成 `pull block; jmp 0 [18]`（**20 时钟/字**，与 DVI 串行器的 `PULL_THRESH=20` 同节奏）。

**实测**：
```
g_bench_us    = 326 µs
g_bench_words = 4096
预测 4096 × 79 ns = 324 µs        ⇒ 误差 0.6%
```

**⇒ DMA 的 DREQ 响应在【快（8.5 ns/字）】和【慢（79 ns/字）】两种节奏下都完全正常。** **⇒ "DMA 响应不了慢 DREQ" 被排除**（§14.32 的结论不成立）。

#### ⭐ 由此嫌疑精确转向：**IRQ 处理器的【平均】耗时**

```
g_dvi_full_us_max              = 262 µs   （处理器完整耗时上限）
g_dvi_irq_count / heartbeat_lines = 2.19  （每逻辑行两次中断）
⇒ 若单次典型值 ≈ 180 µs ⇒ 2.19 × 180 ≈ 394 µs  ≈  实测行时长 389 µs  ✅ 吻合
```

**⚠️ 关键盲点**：我一直在看 `g_dvi_full_us` 的 `last`（单次采样，读到 0）和 `max`，**从来没量过【平均值】**。而整条推理里"软件不是瓶颈"这个结论，正是建立在那个 `last = 0` 上的。

**⇒ 下一轮第一件事：在处理器里加累加器 `g_dvi_full_us_sum += 本次耗时`，用它 ÷ `g_dvi_irq_count` 得到真正有意义的平均值。**

若平均确实在 180 µs 量级 ⇒ **行时长就是被处理器吃掉的**，而这与 §14.19 量到的 "TCR 等待峰值 1853 µs、守卫打满 77%"是同一条线索的延续。

### 14.37 🎯🎯🎯 2026-10-01 深夜·根因定案：`out pc, 1` 约 14.6 时钟【后被 14.54 改写为 side-set 代价】

**做法**：把三种写法的循环放进**同一个固件、同一个 helper、同一套 PIO/SM/DMA 配置**，唯一差别是循环体本身：


**⇒ 同样 20 时钟/字的预算、同样的 FIFO/DMA/时钟，`pull` 版 324 µs、`out pc` 版 4738 µs。**

**⇒ 根因：`out pc, 1` 在这块 RP2350 上每次执行约 **14.6 个时钟**，而不是 1 个。**

#### 它一次解释了此前所有反常（这就是那个"所有构建共有"的量）

- DVI 串行器用 `out pc, 1` 输每一个 bit ⇒ **实际 TMDS 位时钟约 17 Mbit/s，而非 252 Mbit/s**
- ⇒ 帧率在所有构建里不变（最小固件 / 完整固件 / 音频开关 / 我所有补丁）
- ⇒ TX FIFO 恒空（SM 比设计慢 ~15 倍）
- ⇒ 行时长差 **12 倍**（12 ≈ 14.6）
- ⇒ 与"`dbg_tcr == 320` 77% 等不到"也自洽（供给远慢于预期）

#### 下一轮：换掉串行器写法

**方向**：设计一个**不写 PC** 的 1-bit/时钟串行器。约束是 side-set 的两位必须互补（`0b10`/`0b01`），而"发哪一对"目前靠 `out pc` 选指令来编码。

候选（待验证周期数）：
1. `out x, 1` → `mov pins, x`（2 指令/bit ⇒ 126 Mbit/s，仍只到一半）
2. 找一条**直接把 1 个 bit 输出到两个引脚**的指令组合
3. 若都不行 ⇒ 可能需要把 TMDS 符号的编码方式改成"每 2 bit 一次指令"的打包形式

**⚠️ 这条结论同时意味着**：`dvi_min`、完整固件、以及库里所有的节拍假设**都建立在"1 bit/时钟"上**，而这个前提在 RP2350 上不成立 ⇒ **修好串行器是唯一能让整条链回到设计速率的事**。

### 14.38 ⚠️ 2026-10-01 深夜·判别：不是 `out pc` 特有，而是"每 bit 一条 out + autopull"

### 14.39 ⚠️ 2026-10-01 深夜·实验没跑成，但把板子救回来了（两条工具教训）

**我想加的变体**：展开 20 条 `out` + 1 条显式 `pull`（关 autopull），预期 21 时钟/字 ≈ 86 ns。

**结果**：我的改动引入回归 ⇒ 固件**挂在基准里**，DVI 从未启动：
```

g_bench_done = 0     pc = 0x10003246
```

**✅ 定位手法（值得记）**：`arm-none-eabi-addr2line -f -C -e <elf> 0x10003246` ⇒ 直接给出 `dma_channel_is_busy`（`dma.h:932`），反汇编确认是一个 `ldr r3,[r3,#16] / tst r3,#0x4000000 / bne` 的自旋 ⇒ **DMA 通道永远 BUSY，SM 一个字节没消费。**

**⇒ 两条教训：**

1. **`dma_channel_wait_for_finish_blocking()` 没有超时** —— 基准里一旦 SM 不吃，**整个固件跟着挂死**。任何新的基准变体都必须用**有界的轮询**（带计数器）替代它。
2. **改基准 = 改固件的启动路径**（基准跑在 DVI 之前）⇒ **它挂住就等于整机挂住**，所以基准的改动风险远高于它的"诊断"身份给人的印象。

**✅ 收尾做得对**：用 addr2line 从 halt 住的 PC 定位 → 回退到最后一个已知可用版本（`881792b` 的四变体版）→ 重编译重烧 → **读回三个计数器确认恢复**（心跳 8991 在涨、帧数 38、`g_bench_done=0xf`）。**没有丢下一块挂住的板子。**


### 14.42 2026-10-01 深夜·`out null` 隔离不成立；并发现基准里一个会误导人的缺陷

**想做的隔离**：`out null, 1` ×2（同结构、同 side-set，但不碰引脚/PC/内部寄存器）⇒ 若它也慢，代价在 `out`/autopull 机制；若它快，代价在"每 bit 改引脚"的 IO。

**实测**：
```
V0  out pc        :   4739 µs
V2  pull（对照）  :    325 µs
V5  out null      : 873016 µs   ❌ ← 与 V4 的数【一模一样】
g_bench_done      = 0x3f（六个都标成"跑完"）
心跳              = 11453 在涨 ✓【固件没挂】
```

**⇒ 873016 µs 两次出现且完全相同 ⇒ 那是【守卫超时的固定时长】** ⇒ V5 也是"DMA 从没完成、根本不消费"。

**⇒ 最可能的原因：`out null` 不推进移位计数器**（NULL 是丢弃、不算移出）⇒ autopull 永不触发 ⇒ 一个字节都不从 FIFO 取 ⇒ 超时。**⇒ 这个隔离设计错了。**

#### 🔴 顺带发现基准里一个会误导人的缺陷

**守卫超时时 `run_variant` 仍返回 `ok = true`** ⇒ `g_bench_done` 显示"六个都跑完"，**而 V4/V5 实际是超时**。我上一轮就是把 873 ms 读成"跑完了但很慢"。

**✅ 应该修**：守卫用尽 ⇒ 返回 `ok = false`（并在结果里区分"耗时"与"超时"）。

**⇒ 下一轮的更可靠做法**：不要再用 `out null` 这类"语义可疑"的指令做隔离，而是**在正常能跑的 `out pins` 变体上换参数**（例如把 autopull 阈值从 20 改成 10，看每字耗时是否随之减半 ⇒ 直接算出"每条 out 的周期数"）。

### 14.43 2026-10-01 深夜·阈值会决定"消不消费"；修掉了骗了三次的谎报

**实验**：在会消费的 `out pins, 1` ×2 变体上，把 autopull 阈值 20 改成 10。
```
V2  pull（对照）        :    325 µs
V3  out pins，阈值 20   :   4217 µs
V6  out pins，阈值 10   : 873016 µs   ❌ ← 【第三次】出现同一个数
g_bench_done = 0x7f（七个都标成"跑完"）
```

**⇒ 873016 µs 出现三次（V4/V5/V6）且完全相同 ⇒ 那是【守卫的固定超时时长】** ⇒ **任何等于该值的结果都意味着"超时、根本没消费"**（这是一条有用的判读签名）。

**⇒ 而 V6 超时说明：autopull 阈值一改，SM 就【完全不消费】了**，不只是变慢。⇒ 阈值会决定"消不消费"，这是一条很硬的线索，但**原因未明**。

**改成**：`*ok = (guard != 0);`

**验证**：`g_bench_done` 从 `0x7f` 变成 **`0x0f`** —— **正好只有 V0/V1/V2/V3（真跑完的）置位，V4/V5/V6（超时的）正确标为失败。**

**⇒ 基准从此不再谎报，后续实验不会再被这个坑误导。**
