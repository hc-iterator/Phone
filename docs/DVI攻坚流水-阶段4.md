> - **14.44 定案**：V2（`pull + jmp [18]`）324 µs ⇒ 79 ns/字**恰好 = 20 个 252 MHz 周期** ⇒ ① SM 时钟确实 252 MHz、`clkdiv=1` 真生效 ② "每条 `out` ≈13.6 周期"**不能用"SM 时钟慢了"解释**；V0（`out pc,1`×2）4739 µs ⇒ 292 周期，差值 272 ÷ 20 条 out ⇒ 每条 ≈13.6 周期；已排除"FIFO 供给不足""`out pc` 特有" ⇒ 下一步用 `clkdiv` 1→2 判别它是真实 SM 周期还是固定时延。

### 14.44 ⭐ 2026-10-02·把算术钉死：每条 `out` 额外花约 13.6 个周期

**从已有实测能唯一确定的两条：**
```
V2  pull + jmp [18]  （20 周期/字的预算，【没有 per-bit 的 out】）:  324 µs ⇒  79 ns/字 = 20 周期
V0  out pc,1 ×2      （【同样】20 周期/字的预算，但有 20 条 out）: 4739 µs ⇒ 1157 ns/字 = 292 周期
                        差值：20 条 out 额外花掉 272 个周期 ⇒ 【每条 out ≈ 13.6 周期】
```
**✅ 顺带证明了一件重要的事**：V2 的 79 ns/字 **恰好等于 20 个 252 MHz 周期** ⇒ **SM 的时钟确实跑在 252 MHz，`clkdiv=1` 是真的生效的。** ⇒ **所以"每条 `out` ≈ 13.6 周期"不能用"SM 时钟慢了"来解释。**

#### 已排除的两个解释
- **不是 FIFO 供给不足**：V2 同样依赖同一个 DREQ/FIFO，却稳定拿到 20 周期/字 ⇒ **DMA 有能力每 20 周期送一个字** ⇒ V0 里不该饿死。
- **不是 `out pc` 特有**：V3（`out pins,1`，不碰 PC）同样 ~4217 µs（§14.38）。

#### ⇒ 剩下的可能
1. **RP2350 上 `out` 指令本身的流水线代价**（每次改变输出目标/pin 状态都要额外周期）
2. **autopull 每次触发时的固定停顿**——但按阈值 20 算，每 20 bit 才触发一次，若那就是 272 周期，则停顿集中在 pull 上
3. 我的基准里三个变体共有的某项配置（虽然已经尽力对齐）

**✅ 下一步的判别（便宜且干净）**：**在 V0（会消费、~4739 µs）上把 `clkdiv` 从 1 改成 2** ——
- 若耗时**正好翻倍** ⇒ 说明代价是**真实的 SM 周期**（支持可能 1 或 2）
- 若**几乎不变** ⇒ 说明那 13.6 周期不是 SM 时钟驱动的，而是某种**固定时延**（如 IO/总线往返）⇒ 方向立刻改写

**⚠️ 必须用"会消费"的变体**（`out pc`/`out pins` + autopull 20），不要再用 `out null`/阈值 10/展开那些已证明**根本不消费**的形式（§14.42/§14.43）。

### 14.45 🔴 2026-10-02·clkdiv=2 也不消费 ⇒ 浮现"只有唯一一组配置会消费"的模式

**实验**：在 V0（会消费）上把 `clkdiv` 从 1 改成 2。
```
V0  out pc, clkdiv=1  :   4739 µs   ✅
V2  pull（对照）      :    324 µs   ✅
V7  out pc, clkdiv=2  : 873016 µs   ❌ 超时
g_bench_done = 0x0f   ← 只有 V0-V3 成功，V4–V7 全标失败 ✅【§14.43 的谎报修复在正常工作】
```
**⇒ 只是把分频改成 2（本该只是慢一倍），SM 就【完全不消费】了。**

#### 🔴 七变体的汇总模式

| 变体 | 消费？ |
|---|---|
| **V0：`out pc,1` ×2 + autopull 阈值 20 + clkdiv 1** | ✅ **只有它** |
| V1 同 V0 但 `.side_set 2 opt` | ❌ |
| V3 `out pins,1` ×2 | ❌ |
| V5 `out null,1` ×2 | ❌ |
| V6 `out pins,1` ×2，阈值 10 | ❌ |
| V7 `out pc,1` ×2，**clkdiv 2** | ❌ |
| V4 展开 20×out + 显式 pull | ❌ |

**⇒ 只有【唯一那一组精确配置】会消费；任何扰动（opt / 输出目标 / 阈值 / 分频）都让它彻底不消费。** ⇒ **这不像"快慢"问题，更像【autopull 与 DREQ 之间某个脆弱的时序关系】。**

**⚠️ 它同时动摇了 §14.44 那个"每条 `out` ≈ 13.6 周期"的模型**——那是靠 V0 与 V2 相减得出的，而现在看 **V0 的"会消费"本身就是个特例**，拿它当基准去反推"单条 out 的代价"是不稳的。

**⇒ 下一轮应该先把"为什么只有 V0 会消费"搞清楚**（这才是根源），而不是继续在 V0 上换参数。突破口可能是：读 SM 的 `FDEBUG`/`FSTAT` 看它在不消费时到底卡在哪（TXSTALL？还是在执行）—— **halt 住之后读 SM0 的 `addr`/`instr` 就能看出它是否在跑。**

### 14.46 🎯🎯 2026-10-02·抓到"链条丢了触发"的现场，而且是我关掉了防线

**先解决了一个老谜团**：`dma_hw` / `pio0_hw` / `dma_debug_hw` / `pwm_hw` **根本不在 ELF 符号表里**（它们是 SDK 头里的宏）⇒ **这就是当初 gdb 报 `No symbol dma_hw` 的原因。** **⇒ 这些外设只能靠裸地址**：
```
dma_hw        = 0x50000000    （ch N 的寄存器块 = 0x50000000 + N*0x40）
dbg_tcr(ch N) = 0x50000804 + N*0x40    ← 从 SDK 的 DMA_CH0_DBG_TCR_OFFSET=0x804、步长 0x40 算出
   ch3 = 0x500008c4   ch5 = 0x50000944   ch7 = 0x500009c4
pio0_hw       = 0x50200000
```
（**✅ 已实测验证这些地址可用**。）

#### 读到的现场（活体，引擎正在跑）
```
CH3: CTRL=0x0084c21b (EN=1)   COUNT=0   dbg_tcr = 49
CH5: CTRL=0x0084c21b (EN=1)   COUNT=0   dbg_tcr =  4
CH7: CTRL=0x00058606 【EN=0】  COUNT=0   dbg_tcr =  0
PIO0: FSTAT=0x0f000f07   FLEVEL=0（TX FIFO 空）
```
**① 这正是上一任记录过的签名**：`frank_hdmi.c` 里关音频那段注释写着 "…卡死在等 dbg_tcr 装成 320 的死循环中（**实测 dbg_tcr 停在 49/4/0**，TRANS_COUNT 已经是 0）" **⇒ 一模一样。**

**② 具体死因解出来了**：**`CH7` 的 `CTRL=0x00058606` ⇒ `EN=0` ⇒ lane2 的数据通道被禁用。** 而这个值**不在列表的任何 ctrl 里**（列表是 `0x0080421B/0x0082821B/0x0084C21B/0x0000421B`…）⇒ **它是从列表【外面】读来的垃圾控制块** ⇒ **正是 §14.13/§14.14 证明的"控制通道读越界"。**

**③ 🔴 而防住这件事的补丁，正是我第 7 轮用 `#if 0` 关掉的那个**（收口 + 显式重触发）。当时只看帧率没变（4.7 vs 4.9）就留下了 —— **但收口恰恰是那道防线。**

#### ⇒ 于是现在至少是【两个独立问题】叠加

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | **串行器约 13 时钟/bit**（§14.44/§14.45） | 限速 ~12–13 倍 | **主因**，机理未明 |
| 2 | **控制通道读越界 ⇒ 垃圾控制块把 ch7 的 EN 写成 0** | lane2 链路死 | **收口补丁可防**，且**我把它关了** |

**✅ 下一轮第一件事：把收口 + 显式重触发重新打开**（去掉那两个 `#if 0`），让问题 2 消失，然后**只面对问题 1**（串行器）——那才是"12 倍"的主因。

### 14.47 ✅ 2026-10-02·问题 2 已修好并验证；实验分离出"它不限速"

### 14.49 🔴 2026-10-02·纯分析："DMA 一直 BUSY"的含义被读错 ⇒ 问法要改

**我此前把基准里"守卫超时"读成"SM 不消费"。** 但推一下就发现这个读法站不住：
```
若 SM 是停的 / 被禁用的 ⇒ 它的 TX FIFO 就是"不满"
                        ⇒ DREQ 一直有效
                        ⇒ DMA 会【立刻】把 4096 字搬完并结束（根本不会 BUSY）
若 DMA 一直 BUSY ⇒ DREQ 从未有效 ⇒ 【FIFO 一直是满的】⇒ 只能是 SM 根本没在 pull
```
**⇒ ⇒ 所以 V1/V3/V5/V6/V7 那些"超时"变体，不是"慢"，而是【SM 完全不 pull】。**

#### 于是问法必须改
**旧问法**（我前面几轮一直在问）："为什么一条 `out` 要 ~13 个周期？"
**新问法**：**"为什么一改【目的地 / autopull 阈值 / 分频】，SM 就彻底不再 pull 了？"**

而且新的问法**更容易回答**：SM 是否 pull 是可以用**寄存器直接看出来的**——halt 后读该 SM 的 `SHIFTCTRL`（确认 AUTOPULL 和 PULL_THRESH 真的落地）、`FSTAT`（它的 TXEMPTY 位）、以及 `addr`/`instr`（它在不在执行、停在哪条）。

**⚠️ 而这也解释了为什么"只有 V0 会消费"看起来那么反常**——如果原因是"某个配置项没落地 / 某个字段互相覆盖"，那确实会出现"只有一组精确组合能工作"。

**✅ 下一轮的优先动作（比继续换参数值钱得多）**：**在一次 halt 里把某个"不 pull"变体的 SM 寄存器全部读出来**（`SHIFTCTRL`、`EXECCTRL`、`PINCTRL`、`CLKDIV`、`ADDR`、`INSTR`、`FSTAT`），**和 V0 的同一组寄存器逐字段对比**——差异会直接指出是哪个配置没落地。

### 14.50 ⭐ 2026-10-02·纯分析：把结论与那个可疑的基准解耦

我一直在担心"~13 周期/bit 这个结论来自我的基准，而它骗过我两次"。重看数据后发现**不必担心**：

| 来源 | 每 bit | 可信度 |
|---|---|---|
| 我的基准（`pio_dma_bench`） | ~14.6 周期 | ⚠️ 可疑（"只有 V0 会消费"很反常，§14.49） |
| **真实 DVI 自己** | **389 µs ÷ 8000 bit ≈ 12.2 周期** | ✅ **与基准无关**；且它的 SM 寄存器（`SHIFTCTRL=0x680e0000`、`CLKDIV=1`、`ADDR=1`、`INSTR=0x68a1`、`FSTAT` TXEMPTY）**我逐字段验过是对的** |

**⇒ 所以"串行器每 bit 要约 12~13 个时钟"【站在 DVI 自己的测量上】，不依赖那个骗过我的尺子。** **⇒ 而且这同时说明：基准里那些"完全不 pull"的变体，是【基准自己的 setup 毛病】，不是硬件现象——这两件事我之前混着算了。**

#### ⇒ 于是下一步不必先修基准
**下一步应该是：直接改 DVI 的串行器写法，看帧率是否跳上去。** 候选（按把握排序）：
1. **把 `out pc, 1` 换成"先把 1 bit 取到寄存器、再一次性写两脚"的形式**（避免每 bit 都做 PC 写/分支）
2. **一次输出多个 bit**（例如每 2 bit 一条指令），把指令数砍半
3. 查 RP2350 手册里 `OUT` 的周期表（§14.48 那三条外部线索里可能有）

**⚠️ 但先记住**：DVI 的 SM 配置**已经逐字段验证正确**，所以这不是"配置没写对"，而是**这个写法在该芯片上的固有代价**——换写法才是正路。

### 14.51 ⭐ 2026-10-02·纯设计：一个可能真能修好的串行器写法

#### 根本约束（为什么现在必须每 bit 写一次 PC）
```
.program dvi_serialiser
.side_set 2
	out pc, 1  side 0b10     ← 数据【靠"选哪条指令"】编码
	out pc, 1  side 0b01
```
side-set 的取值是**每条指令固定**的，所以"发 `0b10` 还是 `0b01`"只能靠**跳到不同的指令**来表达 ⇒ **必须每 bit 写一次 PC**（`out pc, 1`）。**而 PC 写正是我实测"每 bit ~13 周期"的头号嫌疑。**

#### ✅ 破法：把数据从"选指令"搬到"引脚值"
```
out pins, 2      ← 一条指令输出 2 个 bit 到引脚 p、p+1；【不写 PC】
```
**只要 TMDS 编码器把【每个 TMDS bit 预先展开成 2 bit】（`0b01` 或 `0b10`），`out pins, 2` 一条指令就正好输出一个 TMDS bit 的差分对——与现在完全等价。**

#### 代价（要改的地方，按工作量排）

| # | 要改什么 | 说明 |
|---|---|---|
| 1 | **`frank_serialiser.pio`** | 两条 `out pc,1 side …` → 一条 `out pins,2`（配合 autopull 阈值） |
| 2 | **`frank_serialiser.c` 的 SM 初始化** | 要设 `out_pins` 基址为该 lane 的差分对、并调整 `out_shift` 阈值（每个 TMDS bit 现在占 2 个 OSR bit） |
| 3 | **TMDS 编码器**（`frank_tmds.c` / `tmds_encode.S`） | 输出要**从"每字 2 个 10-bit 符号"变成"每字 16 个展开后的 2-bit 对"** ⇒ 这是最大的一块 |
| 4 | **DMA 表的字数** | `h_active_pixels / DVI_SYMBOLS_PER_WORD` 之类的口径要跟着变（数据量翻倍） |

**⚠️ 风险**：第 3 项要动 TMDS 编码，是本项目最"数学"的一块。 **⇒ 更稳的中间态应先试**：**只把 `out pc,1` 换成 `out x,1` + `mov pins,x`**（2 条指令 1 bit，不写 PC），若它比现在快，就说明"PC 写"确实是代价所在，再决定要不要上第 3 项。

### 14.52 🔴🔴 2026-10-02·换写法让引擎只跑 1 行就停，但换来一条很硬的规律

**实验**：把 `frank_serialiser.pio` 的两条 `out pc, 1 side …` 换成 **`out x, 1 side 0b10` + `mov pins, x side 0b01`**（2 条指令 1 bit，**不写 PC**）。

**结果**：
```
FRAMES = 0     HB-LINES = 1          ← 只跑了 1 行
FLEVEL = 0x00080808                  ← 【三个 TX FIFO 全满】⇒ SM 停止 pull
SM0 ADDR = 9
```
**⇒ 引擎停摆。已回退（`git checkout` 该 .pio）并重烧验证恢复：33 帧/10 秒、770 行/秒、`FLEVEL=0`。**

#### ⭐ 但由此浮现一条**横跨基准与真实 DVI 的硬规律**

| 程序 | SM 是否还在 pull |
|---|---|
| **`out pc, 1` ×2（原版）** | ✅ **在 pull** |
| `pull block` + 延时 | ✅ 在 pull |
| **`out x, 1` + `mov pins, x`（本轮，真实 DVI）** | ❌ **停止 pull（FIFO 全满）** |
| `out pins, 1` ×2（§14.38，基准） | ❌ 停止 pull |
| `out null, 1` ×2（§14.42，基准） | ❌ 停止 pull |
| 阈值改 10 / 分频改 2 / 展开版（§14.43/§14.45） | ❌ 停止 pull |

**⇒ 只写 `pc`（以及显式 `pull`）能维持 pull；写 `X` / `PINS` / `NULL` 都会让 SM 彻底停住。**

**⇒ 这把"我的基准有毛病"与"真实 DVI 一换写法就死"两件事**连成了同一条规律**——它不再是"我基准的 bug"，而是一个**真实、可复现、且非常反直觉的 PIO 行为**。

**⚠️ 而它反过来也说明**：`out pc, 1` 这个"怪写法"**并不是随便写的**——它可能是**唯一**能让 autopull 在这颗芯片上正常工作的形式。 **⇒ 所以我一度想"换掉它"的方向，恐怕是错的。**

**✅ 下一轮方向（改写）**：不再试图换掉 `out pc`，而是**搞清"为什么只有写 pc 能维持 pull"**。候选：① `out` 到非 PC 目标时**不推进/不检查移位计数器**（故 autopull 永不触发）；② 到 PC 时因**分支重启流水线**而恰好给了 autopull 时机。 **判别**：把 `out x, 1` 换成 `out x, 1` **但阈值设成 1**（每 bit 都尝试 pull）看是否恢复——若恢复，则"计数器不推进"成立。

### 14.53 ⭐⭐ 2026-10-02·纯分析：线索推到终点且量化很干净【后被 14.54 改写】

#### 理论：`out pc, 1` 本该【已经满速】
```
每 bit 一条 `out pc, 1`（它按数据位跳到另一条指令）
⇒ 每字 20 条指令 ⇒ 若每条 1 周期 = 20 周期/字 = 79 ns
⇒ 而这【正是设计目标】—— DVI 的列表就按"每字 20 bit"算的（tc = 640/2 = 320）✓
```
**⇒ 这个写法在理论上【不需要任何改动】就能满速。**

#### 实测：每条 `out pc` 约 13.6 周期
```
实测 292 周期/字（= 1157 ns）× 20 条指令/字 ⇒ 每条 ≈ 13.6 周期
```
**⇒ 于是得到了一个干净的量化结论：**

> **`out pc` 这个分支在 RP2350 上每条要 ~13 个周期。**
> **SM 时钟 252 MHz ÷ 13 ≈ 19 Mbit/s，而目标是 252 Mbit/s ⇒ 差 13 倍**
> **⇒ 与全程实测的"12~13 倍"完全吻合。**

#### 这解释并统一了三件事
1. **为什么换任何写法都更快不了**：换成 `out x`/`out pins`/`out null` 会**让 autopull 死掉**（§14.52）
2. **为什么"1 bit/时钟"这个前提从没人质疑**：**它在 RP2040 上是对的**，而 `out pc` 的分支代价大概是 RP2350 特有的（PicoDVI 是给 RP2040 设计的）
3. **为什么所有构建都慢同样的倍数**：这是**指令级的固有代价**，与内核/子系统/我的补丁都无关

#### ⇒ 真正的修法被逼成两个必要条件（缺一不可）
- **必须是【不分支】的写法**（否则每条 ~13 周期）
- **同时必须能让 autopull 正常工作**（否则 SM 停摆）

**⇒ 而 §14.51 那个 `out pins, 2`（2bit 预展开）方案，恰好同时满足这两条。** **⇒ 它仍然是正解方向——只是必须先解决"为什么非 PC 目标会让 autopull 死掉"。**

**✅ 下一轮第一件事**：**在基准里用 `out x, 1` + 阈值 1 做判别**（§14.52 已写好做法）。若它恢复 pull ⇒ "移位计数器只在写 PC 时推进"成立 ⇒ 那就要**用别的方式喂计数器**（例如周期性插入一条 `out pc` 之类）——那才是让 `out pins, 2` 方案可行的关键。

### 14.54 🎉🎉🎉 2026-10-02·最新一轮：去掉 side-set ⇒ 帧率 3.3 → 18.1 fps（5.5 倍）

**实验**：把 `frank_serialiser.pio` 的 `.side_set 2` 去掉，两条指令也不再带 `side`：
```asm
.program dvi_serialiser
.origin 0
	out pc, 1        ; 数据仍靠"选指令"编码，但不再每周期切换差分对引脚
	out pc, 1
```

**实测（12 秒）**：
```
FRAMES       = 217  ⇒ 【18.1 fps】   （改前 33/10秒 = 3.3 fps）⇒ 5.5 倍
FLEVEL       = 0                    ⇒ SM 正常 pull ✓（不是"停住"造成假快）
SM0 INSTR    = 0x000060a1           ⇒ 正是"无 side-set 的 out pc,1"编码 ✓
TCR-TIMEOUTS = 4                    ⇒ 几乎不超时
```
**⇒ ⇒ 那 ~13 周期/条的代价，就是【side-set 每周期切换差分对引脚】。**

#### 🔑 而它直接指出了真正的修法
我前面那次 `out x, 1` + `mov pins, x` 的尝试之所以失败，**是因为它还带着 `.side_set 2`**——它同时吃了**"side-set 的代价"**和**"让 autopull 死掉"**两个问题。

**⇒ 正确做法：去掉 `.side_set`，改用 `mov pins, x` 驱动引脚**（不再靠 side-set 切换）。

#### 距离目标
```
用户第一阶段目标：点亮屏幕、30 fps 就够
现在：18.1 fps  ⇒ 只差 1.7 倍
```
**⚠️ 但"点亮屏幕"还有另一个前置条件**：面板锁定靠的是 **TMDS 位时钟**（要 ~252 MHz）。**当前位流仍未达标**（18.1 fps 说明 SM 仍远慢于 1 bit/周期）——**⇒ 必须先把"1 bit/周期"做到，面板才可能锁上。**

### ⚠️ 2026-10-02 · 【修正】"换编码器函数"这条走不通，真正要做的是**移植一个不复制版 asm 循环**

**原因（已查清）：**
```
libdvi/tmds_encode.c  里那个 fullres 版是【SIO 硬件编码器】路径（configure_sio_tmds_...）
而本 fork 用的是自己的实现：third_party/frank-hdmi-sound/src/frank_tmds.c（仅 128 行）
  ⇒ 走的是【插值器(interp) + asm 循环】路径，没有 SIO 那条
  ⇒ 它只提供 tmds_encode_data_channel_16bpp / _8bpp 两个函数
  ⇒ 所以 libdvi 的 fullres 符号在本工程里根本没有被编译
```
**⇒ 而且"横向复制"在这个路径里的机制是：**
```
pixwidth = h_active_pixels = 640
n_pix    = pixwidth / 2      = 320        ← 输入是 320 个逻辑像素
symbuf   = 640 个符号                     ← 输出
⇒ 也就是：asm 循环把【每个像素的符号写两遍】= 像素复制
   （frank_tmds.c 的 configure_interp_for_addrgen 用 interp0 管低 16 位、interp1 管高 16 位，
     即一个 32 位字里 2 个像素；循环按 n_pix 次产出 2*n_pix 个符号）
```
**⇒ 所以真正要做的是：写/移植一个"每像素只产 1 个符号"的 asm 循环**（libdvi 的非复制路径用的是 SIO 的 `..._poppop_ratio1`，与本 fork 的 interp 路径不同构，不能直接拿来用）。

**配套项（仍然成立）：**
* 逻辑画布宽 320 → **640**（不复制后，一行要有 640 个源像素）
* 帧缓冲 640×240×1B = **153,600 B**（+77 KB）⇒ 从 `KMEM_ARENA_CAPACITY`(320KB, kernel_mem.c:86) 挪
* `DVI_SYMBOLS_PER_WORD` 保持 2（DMA 表长口径）
* 输出仍是 640×480p60 ⇒ 252MHz / SM_CLKDIV=1 不变 ✓

**当前状态：已全部回退，构建绿色（BUILD_EXIT=0）✓，板子未动。**

### 🎯 2026-10-02 · 【最关键】"横向像素复制"的确切机制与不复制版的实现路径

**机制（已读 asm + 表注释确认，不再需要猜）：**
```
frank_tmds.S:75  tmds_encode_loop_16bpp:
    lsls r2, #2                     ; 输出字节数 = n_pix * 4  ⇒ 每输入像素产出 4 字节 = 2 个符号
1:  ldmia r0!, {r4, r6}             ; 每轮读 2 个 32 位字 = 4 个 RGB565 像素
    do_channel_16bpp r2, r4, r5     ; 经 interp0/interp1 查表：PEEK0→r4, PEEK1→r5
    do_channel_16bpp r2, r6, r7
    stmia r1!, {r4, r5, r6, r7}

而库注释原文：
  "The symbol table contains each control symbol *twice*, concatenated into
   20 LSBs of table word, so we can always do word-repeat."
```
**⇒ 结论：复制不是循环写两遍，而是【表项 = 同一符号的两份（2×10bit）】，配合 `DVI_SYMBOLS_PER_WORD=2`（PIO 每次推进吃 20bit = 2 个符号）⇒ 一次查表供两个符号。**

**⇒ 不复制版的正确实现路径：**

| 步骤 | 内容 |
|---|---|
| 1 | 生成一张"单份符号"的表（表项 = 1 个 10bit 符号 + 10bit 填充），或直接由现有表右移 10 位取单份 |
| 2 | 改 asm 循环：查表得到**两个相邻像素各自的符号**后，`orr`/`lsls` 拼进同一个 32 位字再 `stmia` |
| 3 | 输出字数减半（`lsls r2, #1`），DMA 表长口径随之调整（`h_active / DVI_SYMBOLS_PER_WORD`） |
| 4 | 逻辑画布宽 320 → **640**（源像素数要等于 h_active） |
| 5 | 帧缓冲 640×240×1B = 153,600 B（+77KB）⇒ 从 `KMEM_ARENA_CAPACITY`(320KB, kernel_mem.c:86) 挪 |
| 6 | 输出仍 640×480p60 ⇒ 252MHz / SM_CLKDIV=1 / PWM 像素时钟都不变 ✓ |

**⚠️ 第 2 步每 2 像素多约 4 条指令 ⇒ 行内编码耗时上升 ⇒ 实施后要重量行率（当前 61fps，有余量）。**

**当前状态：构建绿色、板子未动、工作树干净。**

### 🎯 2026-10-02 · 【关键观察】"好区域/坏区域"会**对调** ⇒ 是三 lane 水平错位在漂移

**用户两次实测（同一种纯色循环图案，不同版本）：**
```
上一轮：条纹约 20%（左） + 纯色约 80%          边界在 ~20%
这一轮：条纹约 80%（大多数） + 纯色约 20%，紫色在最左   边界在 ~80%
并且：紫色（=红+蓝）只出现在最左边，且"以和条纹差不多的方式闪"
```
**⇒ 推断（重要）：**
* **边界会移动 ⇒ 不是固定的硬件缺陷，而是【累积错位 + 绕回】的相位现象** ✓
* **紫色 = 有红 ⇒ 说明红通道【有数据】，只是【位置不对/时有时无】** ✓ ⇒ 所以"缺红"的措辞要改成"红通道错位"
* **错位量绕回的位置决定"好区域"从哪开始 ⇒ 解释了区域对调**

**⇒ 具体怀疑点：同步 lane（lane0）的 DMA 分段结构与数据 lane 不同**
```
frank_dvi_timing.c:378-380   int real/total = (i == TMDS_SYNC_LANE) ? DVI_SYNC_LANE_CHUNKS... : ...
frank_dvi_timing.c:409-412   synclist[0..3]：h_front_porch / h_sync_width / h_back_porch / h_active
frank_dvi_timing.c:417-418   cblist[0..1]： (hfp+hsw+hbp) / h_active
⇒ 对 640x480：sync 侧 8+48+24+320 = 400 字；data 侧 80+320 = 400 字 ⇒ 【本模式恰好相等】
⇒ 但**整数除法**在别的参数下会不等（例如奇数 porch）⇒ 一旦差 1 个字就逐行漂移 ✓
```
