# HSTX + two-stage PIO relay: driving the onboard HDMI pins 32-39 (2026-10-12)

> 文件名用 ASCII 是踩坑后的选择：中文文件名在本工具的写入通道上会写成 0 字节空文件。

## 结论

- **HSTX 硬连 GPIO12-19**：SDK 的 `FUNCSEL_VALUE_HSTX_0..7` 只定义在这 8 个脚上；GPIO 的"输出覆盖"只有 {外设/反相/强0/强1}，没有跨脚路由。
- **HDMI 座在 GPIO32-39**（用户查原理图确认，板上焊死、不可改）。
- **一个 PIO 实例的窗口只能是 0-31 或 16-47**：`PINCTRL` 的 `IN_BASE[19:15] / OUT_BASE[4:0] / SET_BASE[9:5] / SIDESET_BASE[14:10]` 全是 5 位，且都相对**实例级** `PIO_GPIOBASE`（该寄存器只有 bit4 一位 ⇒ 只能 0 或 16）。
  ⇒ **单实例不可能"读 12-19 同时写 32-39"**。实测佐证：base=0 时写 `out_base=32..38` 被截成 0/2/4/6 —— **这正是 1 号系统当初黑屏的原因**。
  顺带查实：那套 PIO DVI 引擎（frank_hdmi）本来就设对了 base=16（`frank_serialiser.c:88`），所以它确实在驱动 32-39。

## 解法：两级窗口中继（用户提出，已实测）

| 级 | 实例/基址 | SM | 做什么 |
|---|---|---|---|
| 一 | PIO0 / base 0 | 4（每对差分线一个） | `IN=12/14/16/18 → OUT=20/22/24/26`，**顺带把配对排成 HDMI 座顺序**（HSTX: CLK,D0,D1,D2 → 座: D2,D1,D0,CLK） |
| 二 | PIO1 / base 16 | 1 | `IN=20 → OUT=32`，直通到 32-39 |

- 中间脚 **20-27**：既是 PIO0 输出、又是 PIO1 输入，**同一批 pad，无需外部连线**。
- 中间脚的选取约束：PIO0 窗口(0-31) ∩ PIO1 窗口(16-47) = 16-31，再避开 HSTX 的 16-19 与被占的 28-31 ⇒ 正好剩 **20-27**（两个系统都可用）。
- 全程一条 `mov pins, pins`（`0xA000`）：1 指令/位、`clkdiv=1` ⇒ 252 M 更新/秒 = **逐位同速**；无缓冲/DMA/中断 ⇒ **无抖动**；四条 lane 两级延迟相同 ⇒ **skew=0**
  （这也是"16-19 明明能直读也要陪跑第一级"的原因：不等延迟就差 3.97 ns，TMDS 必崩）。

## 别的路子为什么不行

- **HSTX 换脚**：硅片硬连，不可改。
- **DMA 读 GPIO 搬**：`gpio_in → gpio_hi_out` 合法，但①速率只有所需一半（读+写两个总线周期）②bit12-19→bit0-7 是**错 4 位移位**，DMA 只能字节/半字/字对齐③总线仲裁抖动几十 ns，而 TMDS 靠边沿恢复时钟 ⇒ 三条都致命。
- **IRQ 传数据**：IRQ 只有 8 个标志位，没有"把标志当数据读出来"的指令。

## 实测数据

- **连通性**：待测板走线一圈 → 观察板 `STICKY 0x01ffbff` ⇒ 21 根里只有 **GPIO10** 不通；用户复查确认 **10 号杜邦线接到了地**，已修。
- **三级活动度**（20ms 跳变数）：HSTX 12-19 ≈119728、中继1 20-27 ≈119319、中继2 32-39 ≈119926 ⇒ 32-39 确实在被驱动。
- **配对映射（硬数据）**：源 `0x56` 重排应为 `((x&3)<<6)|(((x>>2)&3)<<4)|(((x>>4)&3)<<2)|((x>>6)&3)=0x95`，**输出实测正是 0x95** ✅
- **K 逐位对拍（PIO 图案源 3.15 M 样本/秒 → 中继 → 两个采样 SM 各 `clkdiv=10`=25.2 MSa/s ⇒ 8 采样/位）**：
  ```
  非零样本 src=2560/4096  out=2560/4096
  最佳对齐 12 采样(1.5 位周期)：不一致位 = 0 / 4096 采样（32768 个 lane-bit）
  未对齐(shift 0)：不一致位 = 13824
  ```
  ⇒ **对齐正确时 0 不一致、错位时 13824** = 逐位精确复制的签名；有效比对 20480 个活跃 lane-bit 全对 ✅

## 双向复位（RUN 互联）

- **待测板 `A`(GPIO42) → 采样板 RUN**：实测有效 ✅（脉冲后采样板 COM 口**立即消失** = USB 重新枚举 = 芯片复位）。
- **采样板 `Z`(GPIO28) → 待测板 RUN**：在 `pin_sniff` 固件上此前已实测有效 ✅（当时正是用它救回 panic 卡死的待测板）。
- ⇒ **只要不是两块同时暴毙，任何一块都能被另一块拉回来**。前提：两块都长期保留自己的复位命令（`Z`/`A`），别再刷掉。

## 教训（已入陷阱.md 错 33/34 + 本文）

1. **改运行时时钟要传目标频率**：`clock_configure(..., src_freq, freq)` 末参是 Hz 不是分频（传 16.0f ⇒ 实际 3845 Hz）。
2. **PIO 的 SM 要按实例算**：`pio_claim_unused_sm(..., true)` 拿不到会 **panic**（中继第一级要 PIO0 全部 4 个）。
3. **别把唯一的遥控复位手段刷掉**（本日已经因此吃过一次亏）。
4. **252 MHz 超频必须带散热**。
5. **本机 `Get-Volume`/`Get-CimInstance` 静默返回空** ⇒ 找 BOOTSEL 盘用 `Get-PSDrive` + `INFO_UF2.TXT`。
6. **行缓冲固件**（如 `core1_monitor`）不收整行就不动作 ⇒ 端口能开但 0 字节 ≠ 固件死了（详见 陷阱.md 错 33）。
7. **别对采样 SM 写 pindirs**：会关掉同实例其他 SM 的输出（实测造成假的"0 不一致"，详见 陷阱.md 错 34）。

### 极性（P/N）—— 已备好两个变体（2026-10-12）

**风险**：本板的 PIO DVI 引擎是开着 `FRANK_HDMI_INVERT_DIFFPAIRS=1` 跑的 ⇒ 说明**这块板的差分 P/N
相对那套引擎的约定是反的**；而本中继是"原样照搬"，若 HSTX 的 P/N 约定与 HDMI 座相反 ⇒ 屏幕黑 ✗。

**两手准备（都实测能正常跑，活动度一致）**：

| 命令 | 做什么 | 实测活动度 |
|---|---|---|
| `Y` | 原样中继 → 32-39 | HSTX 118338 / 中继2 117516 |
| `Z` | **整字节取反**中继（`mov pins, !pins` = `0xA008`）⇒ 四对差分线 **P/N 全交换** | HSTX 119389 / 中继2 117862 |

**判据**：发 `Y` 看屏 → 黑屏就重启（`R`）再发 `Z` 看屏。两者必有一个是正确极性。

### `U` 慢速验证模式的实测状态（2026-10-12，结论：仅旁证）

**做法**：库把 HSTX 分频器写进**运行时寄存器** `HSTX_CTRL_CSR_CLKDIV`（`video_output.c:820-822`）⇒
可在运行时把串行器降速（取 CSR=400 ⇒ 位率≈3.15 Mbit/s），中继 `clkdiv=80`、采样 `clkdiv=10`（8 采样/位）。

**实测**：能采到真实输出样本 ✅（117 个样本的结构：`55×10 6a×17 5a×17 66×16 56×24 …`；
6 个数据 lane 互不相同、run 长 10~24 样本 ≈ 1~3 位，符合 TMDS 符号内部结构 ✅）。

**但**：这段里 **bit6/bit7（CLK 对 = 脚 38/39）恒为 1/0** ✗ —— 人为降速后时钟 lane 不跳
（满速时它是跳的：三级活动度里 32-39 全 mask 都测到跳变）。原因很可能在"降速后库那侧的 HSTX 供数节奏"。
⇒ **结论：`U` 只能作为"数据侧有真实码流"的旁证，不能用来判极性**；极性仍以 `Y`/`Z` 看屏为准。

### `hstx_auto`（自动出图版）—— 上真屏最稳的一条路（2026-10-12 实测）

**目的**：即使 PiZero 的 USB CDC 不工作（或没接串口），屏幕也能出图 ⇒ **上真屏不依赖任何命令**。

**做法**：同一份 `src/hstx_copy.c`，编译期加 `-DHSTX_AUTOSTART_SEC=10`：
上电后 10 秒内没收到命令 ⇒ 自动走 `Y` 路径（HSTX + 两级中继 → 32-39）。

**实测（2 号系统）**：烧 `hstx_auto.uf2` 后**什么都不发**，等 15 秒再问 `W`：

```
HSTX   12-19  20ms内变化=119263
中继1  20-27  20ms内变化=118163
中继2  32-39  20ms内变化=117690
```

刚烧完是干净重启、期间没人下命令 ⇒ **它确实自己出图了** ✅
（`[auto]` 那两行 printf 发生在串口打开之前，所以抓不到 —— 活动度才是证据。）

- 产物：`build/hstx_auto.uf2`（110080 B）
- 风险与恢复：自动出图后若挂住 ⇒ 8 秒看门狗复位 ⇒ 再次进入 10 秒窗口（串口随时有机会插进去），BOOTSEL 永远可用。

### HSTX 的 lane 映射：不是假设，而是**库自己写出来的**（2026-10-12 核实）

`video_output.c:824-832`（`video_output_core1_run()`）：

```c
hstx_ctrl_hw->bit[0] = HSTX_CTRL_BIT0_CLK_BITS | HSTX_CTRL_BIT0_INV_BITS;   // GPIO12 = CLK P
hstx_ctrl_hw->bit[1] = HSTX_CTRL_BIT0_CLK_BITS;                             // GPIO13 = CLK N
for (uint lane = 0; lane < 3; ++lane) {
    int bit = 2 + (lane * 2);                                              // bit 2,4,6 → GPIO14,16,18
    uint32_t lane_data_sel_bits = (lane * 10) << SEL_P | ((lane * 10) + 1) << SEL_N;
    hstx_ctrl_hw->bit[bit]     = lane_data_sel_bits | HSTX_CTRL_BIT0_INV_BITS;
    hstx_ctrl_hw->bit[bit + 1] = lane_data_sel_bits;
}
for (int i = PIN_HSTX_CLK; i <= PIN_HSTX_D2 + 1; ++i) gpio_set_function(i, 0);  // 12..19 → HSTX
```

- **GPIO12/13 = 时钟对**（bit0 反相 = P、bit1 = N）⇒ 这是库配置的**直接结论**，不是我们的假设 ✅
- 三条数据 lane 落在 **GPIO14/15、16/17、18/19**（lane 序 0,1,2）
- 「哪条是 D0 / 哪条是 D2」由库的 TMDS 位序决定 ⇒ **若接反，表现是"颜色错"而不是黑屏** ✗
  ⇒ 真屏若出图但颜色不对，只改 stage-1 的 `in_pin` 排列即可（不改机制）。
