# ④ 已排除的歧路与 autopull 悬案（原 1724–1867）

## ⚠️ 由此得到一个三角约束（这是当时最卡的地方）

| 写法 | 引脚有输出 | SM 会 pull | 速度 |
|---|---|---|---|
| `out pc,1` **+ side-set**（库原版） | ✅ | ✅ | ❌ 3.3 fps |
| `out pc,1` **无 side-set** | ❌ | ✅ | ✅ 18.1 fps |
| `out pins,1` / `out x,1` / `out null,1` | ✅ | **❌ 停摆** | — |

**已多次坐实（真实 DVI + 基准都复现）**：**写 X / PINS / NULL 这些非 PC 目标，会让 SM 彻底停止 pull**
—— **且与 side-set 无关**。

### ⚠️ 第 36 轮更正 + 新线索（把 `FLEVEL` 按 SDK 权威布局逐字段重解）
```

```
**⇒ 不是"三个都满"，而是【SM0 和 SM1 卡住、SM2 还在消费】。**
**⇒ 而正常工作时（无 side-set 的 40 fps 版）`FLEVEL = 0`（三个全空，都在消费）。**
**⇒ 于是谜题从"所有 SM 都停"缩小成："为什么三个跑同一个程序的 SM 会有不同命运？"** —— 这是个更有抓手的问题（下一步应逐 SM 读 `ADDR`/`INSTR`/`FSTAT` 对比，而不是笼统看 `FLEVEL`）。

### ✅ 第 37 轮：健康状态的逐 SM 参照系（跟失败变体对比用）
```
健康（库原版、5 fps）：PIO0 CTRL=0x7  FSTAT=0x0f000f07  FDEBUG=0x07000000  FLEVEL=0
SM0 = SM1 = SM2 【三个完全一样】：
  CLKDIV=0x00010000  EXECCTRL=0x0001f000  SHIFTCTRL=0x680e0000 ADDR=0  INSTR=0x000070a1(=out pc,1 side 0b10)  PINCTRL=0x14000000
```
**⇒ `FSTAT` 的 `TXEMPTY=0xf`（三个 TX FIFO 全空）+ 三个 SM 都停在 `ADDR=0`（第一条 `out`）
⇒ 完全自洽：健康状态下三个 SM 都在第一条 `out` 上等 FIFO 数据，这正是 DREQ 节流设计的正常样子。** **⇒ 失败变体（`out pins,1`）则表现为 TX0/TX1 满、TX2 空 ⇒ 拿这张表逐项比就能看出差异。**
### 🎯 第 38 轮：两边的对照想通了，机制是一个【死锁】（后被第 39 轮否证）

| | FIFO 状态 | 含义 |
|---|---|---|
| **健康（原版、5 fps）** | **空**（`TXEMPTY=0xf`） | SM 停在 `out` 上等数据 ⇒ **它把数据【消费掉了】** |
| **失败（`out pins`）** | **满**（TX0/TX1=8） | SM 也停在 `out` ⇒ **但它【从没消费过】** |

**⇒ 两边都"停在 `out` 上"，区别是【FIFO 是被喂进去的、还是被吃掉的】。** **⇒ 指向死锁：`out` 在等一个空的 OSR，而 autopull 从未触发 ⇒ FIFO 灌满后互相等住。**
**⇒ 也就是说：失败变体里【autopull 根本没在工作】——** 这跟"写非 PC 目标 ⇒ SM 停止 pull"那条规律一致，现在它有了机制：
**不是 SM 停了，而是 `out` 堵在空 OSR 上、autopull 又不补。**
**✅ 判别（下一轮，一次 halt 就够）**：在失败变体上读 **`FDEBUG`（`0x50200008`，看 `TXSTALL` 粘滞位）+ `SHIFTCTRL`（确认 `AUTOPULL`/`PULL_THRESH` 真的落地）**。
- 若 `AUTOPULL=1` 且 `PULL_THRESH=20` 都在、却仍不补 ⇒ **autopull 的触发条件与该指令不兼容**（那是 RP2350 的行为差异） - 若某个字段没落地 ⇒ **就是配置没写进去**（更好修）

## ❌ 已排除的歧路（第 34 轮算过，别再试）
 **"整体按比例放慢让信号自洽"**
> 想法：既然每条指令要 ~13 周期，那**把像素时钟也一起除以 13**，让链路在 1/13 速度下自洽。
 **算术上不成立**：最大位流 ≈ 252÷13 ≈ **19.4 Mbit/s** ⇒ 像素时钟最大 ≈ **1.94 MHz**； 而**最小的标准模式 320×240@60 也要 12.6 MHz** ⇒ **还差 6.5 倍，连最小模式都放不下。**
**⇒ 结论：串行器必须真的到 ~252 Mbit/s（至少 ~126）。没有绕过办法 —— 解开那个指令代价是唯一路径。**
