# ② RP2350 特有真根因：GPIO 基址 + 数据脚方向 + `WRAP_TOP`

## 🏆🏆🏆 第 53~54 轮：**找到了"引脚上永远没信号"的真根因（两处），输出已完整**

### 真根因（都是 RP2350/RP2350B 相关，库是按 RP2040 + 小引脚号写的）

**① `pio_set_gpio_base(cfg->pio, 16)`** —— RP2350B 的 PIO 只能寻址 32 根引脚，窗口只有 `0~31` 或 `16~47`（`PIO_GPIOBASE`，偏移 `0x168`）。DVI 用 32~39，**在 0~31 窗口外** ⇒ 不设基址时侧置/输出引脚全落到错的物理脚上。
（实测判据：`GPIOBASE` 寄存器 = 0 → 改成 16 后 = 16 ✓）

**② ★★★ 数据脚方向从来没被设成输出** —— `frank_serialiser.pio` 里原文：
```c
pio_sm_set_pins_with_mask(pio, sm, 2u << data_pins, 3u << data_pins);
pio_sm_set_pindirs_with_mask(pio, sm, ~0u, 3u << data_pins);
```
**`data_pins` = 32/34/36 ⇒ `3u << 32/34/36` 是 32 位移位【溢出】⇒ 掩码 = 0 ⇒ 这两句什么都没做** ⇒ **6 根数据脚一直是【输入】⇒ side-set 把 TMDS 写上去也出不了引脚。**
修法：换成 64 位安全的 `pio_sm_set_consecutive_pindirs` + `pio_sm_set_pins_with_mask64`，并放到 `pio_sm_init` 之后。

### 铁证（同一条探针、同一采样方法；探针自检=40 万次变化，证明方法有效）
```
修复前  CHANGES_32..39 =      0      0     0     0     0     0     0     0
修复后  CHANGES_32..39 =  91064  93090    16 61632 257662 255998 1143044 1077938
                         ↑32    ↑33   ↑34  ↑35   ↑36    ↑37    ↑38(时钟) ↑39
```
**⇒ 8 根引脚【全部】在翻转 ⇒ DVI 输出（数据 + 时钟）已经完整。**

### ⚠️ 用户实测：面板在"黑屏 ↔ No Signal"之间反复切换
**⇒ 面板【检测到了信号】但锁不住**（之前是彻底没反应）⇒ 说明信号真的到屏上了。 **⇒ 当前正在二分"差分对极性"：`FRANK_HDMI_INVERT_DIFFPAIRS` 0 → 1（待用户看屏）。** **⇒ 若两个极性都不行，下一手是"只反时钟、不反数据"**（库只用同一个开关控制全部引脚，而有些板子时钟与数据的相对极性不同 ⇒ 需要单独给 `pins_clk` 传反向的 `invert`）。

### ⚠️ 探针本身的教训（我在这上面栽了三次）
**同一条探针、同一份代码，不同次的读数【会不一样】**（有几轮读到全 0，另一轮读到全部在翻转）⇒ **绝不能拿单次读数下"没有信号"这种结论**；每次都要先跑自检，并且多次取样。
（另外：`gpio_get_all()` 只覆盖 GPIO 0~31；GPIO 32~47 在 SIO 的**高位**寄存器 `gpio_hi_in` 里 —— 我第一版探针正因为这个而全读成 0。）

## 🏆🏆🏆 第 48 轮：**找到了"从来没有画面"的根因 —— RP2350B 的 PIO GPIO 基址**

**SDK 原话（`hardware/pio.h`，RP2350 专属段落）**：
> *"On RP2350B, there are 48 pins but each PIO instance can only address 32 pins (the PIO instance either addresses pins 0-31 or **16-47** based on `pio_set_gpio_base`). **If `PICO_PIO_USE_GPIO_BASE != 1` then bit 5 of the pin number is ignored.**"*

**⇒ DVI 用的引脚是 32~39，而 `32 = 0b100000` —— bit 5 正是被忽略的那一位！**

| 现象 | 解释 |
|---|---|
| **`PINCTRL=0x14000000`（`OUT_BASE=0`/`SET_BASE=0`）** | SDK 把 **bit5 抹掉**了 ⇒ 我传的 32/34/36 → 0/2/4 |
| **`EXECCTRL=0x0001f000`（`SIDESET_BASE=0`）** | 同上 ⇒ **不是"配置没写进去"，是【被抹掉了】** |
| **从来没有画面** | **PIO 实际在驱动引脚 0~7，而不是 32~39** ⇒ 那 8 根 DVI 引脚上什么都没出来 |
| **帧率 5 / 40 fps 都能测到** | 数据流（DMA/FIFO/SM）是通的，但**信号从未到达 DVI 引脚** |

**✅ 修法（两处）**：
1. **编译定义 `PICO_PIO_USE_GPIO_BASE=1`**（否则 SDK 继续忽略 bit 5）
2. **DVI 初始化里加 `pio_set_gpio_base(cfg->pio, 16)`**（窗口 16~47 ⇒ 覆盖 32~39）

**⇒ 这是 fork 为 RP2040 写、而 RP2350B 特有的坑。工程里 `pio_set_gpio_base` 只在 SDIO 的 `#ifdef PICO_SDIO_GPIO_BASE_16` 里出现过，DVI 这条路上【从来没人设过】。**
**⚠️ 这也意味着：在本轮之前，我们测到的所有"帧率"都只是【数据流速度】，与"信号有没有出去"无关 —— 而信号【一直没出去过】。**

### ⚡ 第 49 轮：基址修复把两件事**解耦**了（改变下一步的预期）

| | **修基址前** | **修基址后** |
|---|---|---|
| **信号到不到那 8 根引脚** | ❌ **从没到过**（PIO 在驱动引脚 0~7） | ✅ **到了**（原版 `out pc,1`+side-set 就会真的驱动 32~39） |
| **位率够不够** | —（谈不上） | ❌ 仍差 ~13 倍（~19 Mbit/s vs 252 Mbit/s） |

**⇒ 所以修完基址后，即使帧率还是 5 fps，信号【第一次是真的】—— 面板可能锁不上（位率不够），但也可能出点东西 ⇒ 值得请用户看一眼。** **⇒ 而"帧率"这个数字在修基址前后测的是同一件事（数据流速度），它跟画面没有因果关系。**

**🔴 本会话最大的教训（写给下一任，也写给我自己）**： **我把"数据流快慢（帧率）"当成了"画面能否出来"的指标，追了十几轮。** **而真正的断点是一个 base=0 —— 它让信号【根本没出过门】。** **⇒ 判据要选得能反映【目标本身】；"帧率"在信号没出去时是个假指标。**

## 🔴 2026-10-01 深夜·第 29~31 轮的重大更新（压缩后先看这段）

**突破**：把 `frank_serialiser.pio` 的 **`.side_set 2` 去掉** ⇒ 帧率 **3.3 → 18.1 fps（5.5 倍）**。
健康检查通过：`FLEVEL=0`（SM 正常 pull，不是停摆假快）、`INSTR=0x000060a1`（无 side-set 的编码）。 **⇒ 那 ~13 周期/条 的代价，就是【side-set 每周期切换差分对引脚】。** **⇒ 用户第一阶段目标是"点亮屏幕、30 fps 就够" ⇒ 18.1 fps 只差 1.7 倍。**

（此段的独立复现见索引 §最近阶段 / `docs\DVI攻坚流水-阶段4.md` §14.54。）

**⚠️ 但由此得到一个三角约束（这是现在最卡的地方）：**

| 写法 | 引脚有输出 | SM 会 pull | 速度 |
|---|---|---|---|
| `out pc,1` **+ side-set**（库原版） | ✅ | ✅ | ❌ 3.3 fps |
| `out pc,1` **无 side-set** | ❌ | ✅ | ✅ 18.1 fps |
| `out pins,1` / `out x,1` / `out null,1` | ✅ | **❌ 停摆** | — |

**已多次坐实（真实 DVI + 基准都复现）**：**写 X / PINS / NULL 这些非 PC 目标，会让 SM 彻底停止 pull** —— **且与 side-set 无关**。

### 🔴 第 31 轮追加（比上面更新）

**实测：无 side-set 版跑到 【40.1 fps】（401 帧/10 秒）** ⇒ **已超过用户 30 fps 的门槛**。 **⇒ 所以"速度"这一半【已经达标】；缺的只有"引脚要被驱动"。**

## 🎯🎯🎯🎯🎯 第 46 轮：**找到了 —— `WRAP_TOP = 31`，而它应该是 1**

**权威位域（RP2350 SDK `pio.h`）：`WRAP_TOP = 16:12`、`WRAP_BOTTOM = 11:7`。**

**板上实测（第 37 轮就读到的值，我当时没解它）：`SM0/SM1/SM2 EXECCTRL = 0x0001f000`**
```
0x0001f000 = 0000 0000 0000 0001 1111 0000 0000 0000
                       bits16:12 = 0b11111 = 31   ← ★
                       bits11:7  = 0b00000 =  0
⇒ WRAP = [0, 31]  —— 整个 PIO 指令内存；而这条程序只有 2 条指令 ⇒ 应该是 [0, 1]
```

### 这一条解释了**全部现象**

| 观察 | 解释 |
|---|---|
| **`out pc,1` 能工作** | 它**每周期都分支到 0/1** ⇒ **根本不碰 wrap** |
| **`out x`/`out pins`/`out null` 停止 pull** | 它们靠 PC 自增 ⇒ **0→1→2→…→31 一路执行 30 条垃圾指令**（PIO 内存里还放着 debug UART 程序），根本不在 DVI 的节奏上要数据 |
| **`ADDR = 9`** | **就是走到一半被我抓到的** |
| **FIFO 灌满、`TXSTALL` 全清** | 它没在执行那条 `out` |
| **只跑 1 行就停** | 第一遍还正常，之后开始绕垃圾 |

**⇒ "只有 `out pc` 能工作"根本不是 autopull 的怪癖，而是【它是唯一不依赖 wrap 的写法】。**

### ⇒ 真相是**两个独立的 bug**

| # | bug | 后果 | 修法 |
|---|---|---|---|
| **1** | **`WRAP_TOP = 31`（应为 1）** | **任何不自带分支的程序都会跑飞** | **`sm_config_set_wrap(&c, off+0, off+1)`** |
| **2** | **side-set 每条指令 ~13 周期** | 5 fps | 去掉 side-set（已实测 ⇒ 40 fps） |

**⇒ 两个都修掉 ⇒ "不分支 + 引脚有输出"的写法 ⇒ 点亮屏幕。** **⚠️ 我前面十几轮把这两个 bug 混着推，一度还得出"RP2350 的 autopull 有硬件怪癖"这种结论 —— 而真相是这条 wrap 配置错了。教训：寄存器读到的值要【解到底】，不要只记下数字。**

**✅ 下一轮第一件事（很小）**：在 `frank_serialiser.pio` 的 `% c-sdk` 初始化里加 **`sm_config_set_wrap(&c, offset + 0, offset + 1)`**，并把程序改成**不分支**的写法（如 `out pins, 1` ×2 或 `out pins, 2`），**同时补上 `sm_config_set_out_pins`（无条件）**。
**预期：帧率接近 40 fps 且引脚有输出。**

## 🎯🎯🎯 第 45 轮：复盘时抓到了 —— 而这条线索我【见过两次却没深究】

**失败变体的 `SM0 ADDR` 一直是 `9`，而那个程序只有 2 条指令（地址 0~1）：**

| 轮次 | 变体 | `ADDR` | `INSTR` |
|---|---|---|---|
| **第 27 轮** | `out x, 1` + `mov pins, x` | **`0x09`** | `0x00003ffe` |
| **第 31 轮** | `out pins, 1` ×2 | **`0x09`** | — |
| 健康态 | `out pc, 1` ×2（原版） | `0x00` | `0x000070a1` ✓ |

**⇒ 失败变体里 PC 停在【地址 9】，而程序只占 0~1 ⇒ SM 的 PC【跑出了程序范围】，正在执行地址 9 上的东西。**

**⇒ 这能解释全部现象：**

| 现象 | 解释 |
|---|---|
| **SM 从不 pull、`TXSTALL` 全清** | 它没在执行那条 `out`，而是在执行别的东西（不按 DVI 节奏要数据） |

**⇒ 而 `out x`/`out pins` 靠 PC 自增，一旦 wrap 没生效/没配对，PC 就会一路走下去。** **⇒ 这个线索我在第 27、31 轮各见过一次却两次都放过（第 27 轮甚至写下来了，然后跳过去了）。**

## （原 §14.0 最早的"第 29~31 轮"状态块）

**问题**：DVI 引擎实测 **4.7 fps**（目标 60），差 **12 倍**。判据①已达（持续出帧，不再卡在 14 帧）。

#### 🔴 根因候选（经两个独立测量交叉验证）：**串行器实际约 13 个时钟才输出一个 bit，而不是 1 个**

| 测量 | 每 bit 代价 |
|---|---|
| 最小基准跑 DVI 串行器原程序（`out pc,1` ×2 + autopull） | ~14.6 时钟 |
| **真实 DVI**（行 389 µs ÷ 8000 bit） | **~12.2 时钟** |

**⇒ 这解释了此前所有反常**：帧率在所有构建里不变 · TX FIFO 恒空 · 行时长差 12 倍（**12 ≈ 13**）· 最小固件与完整固件一样慢 · `dbg_tcr==320` 有 77% 等不到。

# ④ 已排除的歧路与 autopull 悬案（原 1724–1867）

### ⚠️ 第 36 轮更正 + 新线索（把 `FLEVEL` 按 SDK 权威布局逐字段重解）
```
失败现场 FLEVEL = 0x00080808
  TX0 = 8【满】  RX0 = 8   TX1 = 8【满】  TX2 = 0【空！】
```
**⇒ 不是"三个都满"，而是【SM0 和 SM1 卡住、SM2 还在消费】。** **⇒ 而正常工作时（无 side-set 的 40 fps 版）`FLEVEL = 0`（三个全空，都在消费）。** **⇒ 于是谜题从"所有 SM 都停"缩小成："为什么三个跑同一个程序的 SM 会有不同命运？"** —— 这是个更有抓手的问题（下一步应逐 SM 读 `ADDR`/`INSTR`/`FSTAT` 对比，而不是笼统看 `FLEVEL`）。

### ✅ 第 37 轮：健康状态的逐 SM 参照系（跟失败变体对比用）
```
健康（库原版、5 fps）：PIO0 CTRL=0x7  FSTAT=0x0f000f07  FDEBUG=0x07000000  FLEVEL=0
SM0 = SM1 = SM2 【三个完全一样】：
  CLKDIV=0x00010000  EXECCTRL=0x0001f000  SHIFTCTRL=0x680e0000
  ADDR=0  INSTR=0x000070a1(=out pc,1 side 0b10)  PINCTRL=0x14000000
```
**⇒ `FSTAT` 的 `TXEMPTY=0xf`（三个 TX FIFO 全空）+ 三个 SM 都停在 `ADDR=0`（第一条 `out`）⇒ 完全自洽：健康状态下三个 SM 都在第一条 `out` 上等 FIFO 数据，这正是 DREQ 节流设计的正常样子。**
**⇒ 失败变体（`out pins,1`）则表现为 TX0/TX1 满、TX2 空 ⇒ 拿这张表逐项比就能看出差异。**

### 🎯 第 38 轮：两边的对照想通了，机制是一个【死锁】（后被第 39 轮否证）

| | FIFO 状态 | 含义 |
|---|---|---|
| **健康（原版、5 fps）** | **空**（`TXEMPTY=0xf`） | SM 停在 `out` 上等数据 ⇒ **它把数据【消费掉了】** |
| **失败（`out pins`）** | **满**（TX0/TX1=8） | SM 也停在 `out` ⇒ **但它【从没消费过】** |

**⇒ 两边都"停在 `out` 上"，区别是【FIFO 是被喂进去的、还是被吃掉的】。** **⇒ 指向死锁：`out` 在等一个空的 OSR，而 autopull 从未触发 ⇒ FIFO 灌满后互相等住。** **⇒ 也就是说：失败变体里【autopull 根本没在工作】—— 这跟"写非 PC 目标 ⇒ SM 停止 pull"那条规律一致，现在它有了机制：不是 SM 停了，而是 `out` 堵在空 OSR 上、autopull 又不补。**

**✅ 判别（下一轮，一次 halt 就够）**：在失败变体上读 **`FDEBUG`（`0x50200008`，看 `TXSTALL` 粘滞位）+ `SHIFTCTRL`（确认 `AUTOPULL`/`PULL_THRESH` 真的落地）**。
- 若 `AUTOPULL=1` 且 `PULL_THRESH=20` 都在、却仍不补 ⇒ **autopull 的触发条件与该指令不兼容**（那是 RP2350 的行为差异）
- 若某个字段没落地 ⇒ **就是配置没写进去**（更好修）

### 🎯🎯 第 39 轮：用【已有数据】就把上面那一步做完了，而且它【否证了死锁假设】

**权威位域（`$SDK/src/rp2350/hardware_regs/include/hardware/regs/pio.h`）：** `TXSTALL = 27:24` · `TXOVER = 19:16` · `RXUNDER = 11:8` · `RXSTALL = 3:0`

| | `FDEBUG` | 含义 |
|---|---|---|
| **健康（原版、5 fps）** | **`0x07000000`** | bit24/25/26 置位 ⇒ **三个 SM 的 `TXSTALL` 都置位** ⇒ 它们在等 FIFO（DREQ 节流下的正常现象） |
| **失败（`out pins`）** | **`0x00000000`** | **`TXSTALL` 全清** ⇒ **SM 从没尝试过 pull** |

**⇒ 若是死锁（`out` 堵在空 OSR 上），它【正是在等数据】⇒ `TXSTALL` 应该置位。而它是清的 ⇒ SM 根本没在等数据，而是【压根没发出 pull 请求】。**
**⇒ 所以机制不是"堵住"，而是【autopull 从未触发】—— SM 一路跑下去、从不问 FIFO 要数据。**

**✅ 下一步（很小）**：读失败变体的 `SHIFTCTRL`（`0x502000d0`），确认 `AUTOPULL=1`、`PULL_THRESH=20` 是否**真的落地**：
- **落地了却仍不补** ⇒ 是 **RP2350 上 autopull 触发条件与该类指令不兼容**（要换设计）
- **没落地** ⇒ 是 **配置没写进去**（好修得多）

## ❌ 已排除的歧路（第 34 轮算过，别再试）

**"整体按比例放慢让信号自洽"**
> 想法：既然每条指令要 ~13 周期，那**把像素时钟也一起除以 13**，让链路在 1/13 速度下自洽。

**算术上不成立**：最大位流 ≈ 252÷13 ≈ **19.4 Mbit/s** ⇒ 像素时钟最大 ≈ **1.94 MHz**；而**最小的标准模式 320×240@60 也要 12.6 MHz** ⇒ **还差 6.5 倍，连最小模式都放不下。**

**⇒ 结论：串行器必须真的到 ~252 Mbit/s（至少 ~126）。没有绕过办法 —— 解开那个指令代价是唯一路径。**
