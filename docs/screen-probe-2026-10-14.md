# 屏幕侧测量与结论（2026-10-14）

## 0. 用户实测结论（这是记录，不是我的推断）

- 用**电脑**直连这块屏幕：**场景切换时的斜向撕裂同样存在** ⇒ **撕裂不是** HSTX/PIO 通路的问题 ✓
- 电脑与屏幕的**协调握手走 USB**，不走 HDMI ✓
- 电脑输出 **1080p**，屏幕**做了压缩**，且压缩算法不高明 ✓

## 1. 屏幕是谁（本机实测）

| 项目 | 值 |
|---|---|
| 显示器节点 | `DISPLAY\KTC2154`（EDID 名称 **"W21.5HDMI"**，2009，EDID 1.3）；`DISPLAY\BNQ802F`（**BenQ BL2480T**，2021，EDID 1.4） |
| EDID 存档里还有 | `DISPLAY\LDK049B` = **LDK-LE256**，原生 2560x1440@60（241.5MHz），当前不在 PresentOnly 列表 |
| KTC 的时序 | 首选 **1920x1080@60**（148.5MHz，htotal 2200 / vtotal 1125）；另有 **1360x768@60**（85.5MHz）；标准时序含 1280x?/1600x? |
| BenQ 的时序 | 首选 1920x1080@60（148.5MHz）；标准时序 1920/1680/1600/1280 |
| USB 侧 | `USB\VID_26AE&PID_8506` ⇒ **HID 触摸屏**（COL01）+ **符合 HID 标准的供应商定义设备**（COL02）⇒ 那个"握手/控制"通道就是 COL02 ✓ |
| 显卡 | AMD Radeon R9 380；系统里另装了 **OrayIddDriver**（向日葵虚拟显示器驱动 ✗，可能干扰分辨率/时序） |

## 2. 对我们的意义

- **撕裂不是我们的锅** ✓（电脑直连也这样）⇒ 之前把"画面不稳"全归到自家通路上是方向错了 ✗
- ~~可试方向：给屏幕喂它自己列出的模式（如 1360x768@60），也许撕裂更少~~
  〔2026-10-14 注：**已否掉** ✗ —— 电脑直连时喂的正是 KTC 的**首选原生 1920x1080@60** ✓，撕裂照样存在 ⇒ **换模式不是解药** ✓。撕裂是该面板处理"场景切换"时的固有行为，与输入模式无关 ✓〕
- 供应商 HID（COL02）是**只读探测**目标 ✓：先看 HID 描述符有什么用法页/报表长度；**不盲写** ✗（盲写可能改坏屏幕设置）
- 做屏幕实验前建议先**停掉 Oray 虚拟显示器** ⇒ 避免时序被它带偏 ✓

## 2.5 对项目目标的结论（2026-10-14）

- **"斜向撕裂"这一项已归因到屏幕** ✓，我们的 HSTX/PIO 通路不为它负责 ✓；目标里"稳定画面"的**验收方式需要改** ✗：
  不能再把"屏幕是否撕裂"当作衡量自家通路的标准，否则永远判不出来 ✓。
- 自家通路仍未被真正看过一眼 ✗（PiZero 一直没接上）⇒ 该看的是：**除了这块屏固有的撕裂之外，我们的画面有没有额外的伪影**（错色 / 缺 lane / 花屏 / 黑屏）✓。
  ⇒ 验收口径建议：**用固化在屏幕上的已知图案**（如 8 色竖条 ✓）对照，能分辨出"屏固有撕裂"与"我们信号错"两类问题 ✓。

## 3. 身份已确认（2026-10-14 用户确认）

- **台架上那块屏 = `DISPLAY\KTC2154`** ✓（EDID 名称 "W21.5HDMI"，2009 年，EDID 1.3）
- **`DISPLAY\BNQ802F` = BenQ BL2480T 是用户的电脑显示器** ✓（与台架无关）
- ⇒ 由此可推：KTC 支持的模式只有 **1920x1080@60 / 1360x768@60 / 1280x? / 1600x?** ⇒ 我们的 640x480p60 **不在它的模式表里** ✗ ⇒ 屏幕必然要缩放它 ✓
  ⇒ 值得试的对照：若能出 **1360x768@60** 或 **1280x720p**（它列出的模式 ✓），缩放器负担更小，撕裂/压缩伪影可能减轻 ✓（未验证）
- KTC 是**触摸屏** ✓（USB `VID_26AE:PID_8506` 的 HID 触摸 + 供应商通道 COL02 ✓）
