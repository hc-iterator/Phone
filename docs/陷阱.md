# 一、判断篇（想错了：结论 / 假设 / 验证方式）

> 这类错代价最大：它不会立刻报错，而是**让你在错的地基上继续施工**。

### 陷阱 1 —— 把"我以为"当成"我量过"

**病征**：推理写得像结论，然后**在错的地基上继续施工**；这个项目的坑**几乎都不是"想不出来"，而是"记混了"**。
**怎么避**：**把"我以为"和"我量过"分开写。** 没实测的一律显式标注"**待验证**"；
存档的结论必须能指到**哪一条实测数据**支撑它。
**2026-10-02 加严**：写**状态**时连**证据 + 日期**一起写，写不出来就写"**待查**"（`docs/工作守则.md` §二）。

### 陷阱 2 —— 押注一个假设，而不是设计能证伪它的实验

**病征**：PSRAM 那次押"芯片根本没焊、自动检测假阳性"（依据是微雪 wiki 的 "a reserved PSRAM pad"）——
**这个假设听起来非常合理，而且能解释每一条现象**，结果一测就翻了。
**怎么避**：动手前先问 **"什么结果能证明我错了？"** 然后**去测那个结果**。
一个"能解释所有现象"的假设**恰恰最危险**（解释力强 ≠ 正确）。
**二手资料（wiki、README、别人的帖子）不能替代实测。**

### 陷阱 3 —— 混用不同时刻的读数，当成"矛盾"

**病征**：`MPU_CTRL` 一会儿读到 0、一会儿读到 5，当成"未解之谜"追了一阵。
**真相**：内核从来没配过 MPU（`src/kernel.c` 里只有宏定义）⇒ 运行期它就是 0；
崩溃后 `reset()` 进了 bootrom，**5 是 bootrom 配的** ⇒ 两个读数**不是同一个时刻的世界**。
**怎么避**：看到"矛盾的读数"，**先问它们是不是在同一时刻、同一状态下取的**；
读寄存器时把**触发条件**一起记下来（复位了没？谁在跑？）。

### 陷阱 4 —— 提前收敛：一有假设就去找支持证据

**病征**：假设定了之后就**挑支持它的现象**，忽略不支持的现象；错 4 里"关音频更糟"这个事实**当场就在提示我**了。
**怎么避**：假设**一次写两个**（并列），同时找各自的证据。
每轮排查结束时问：**"这一轮有没有出现我解释不了的现象？"** 有就记下来 —— 那通常就是下一个突破口。

### 错 2 —— 两条错误结论写进文档，养活了好几轮

| 错误结论 | 真相 |
|---|---|
| "处理程序入口读到 `CONTROL.nPRIV == 1` ⇒ 处理程序是非特权态" | **Handler 模式必然特权。** 那个读数描述的是**线程**的状态 |
| "线程返回后的特权态由栈帧 xPSR 恢复，所以要清 xPSR 的 bit0" | **彻底的无操作。** Thread 模式的 IPSR（xPSR bit[8:0]）恒为 0，bit0 本来就是 0 |

第二条让上一轮那个"SYS_EXIT 修复"**等于什么都没做**，而我还以为修好了。
**真正的机制**：**`CONTROL.nPRIV` 跨异常进入和返回都原样保留**；
要让线程变回特权，必须**由处理程序去改 `CONTROL.nPRIV`**。

```c
/* ✅ 用【行为验证】判断特权态；❌ 别读 CONTROL.nPRIV */
/* MPU_TYPE(0xE000ED90) 是特权只读寄存器：特权读 → 非 0（实测 0x800 = 8 个区域）；
 * 非特权读 → 会触发 MemManage 或得 0 */
static bool is_privileged(void) { return *(volatile uint32_t *)0xE000ED90u != 0u; }
/* ✅ 切回特权态：改 CONTROL.nPRIV（nPRIV 会持续生效）—— mrs %0,control → c &= ~1u → msr control,%0 → isb */
```

> **规则**：**判断特权态永远用行为验证**，不读 `CONTROL.nPRIV`。**没实测过的推理不许写成结论。**

### 错 3 —— 只读一个计数器就宣布"程序死了"

**陷阱**：看 `dvi0.dvi_frame_count` 冻结在 38，就判断整个程序挂了。
**同一次 halt 时 Core0 已经画到 5139 帧**，活得好好的 ——
`g_dvi_loop_frames`（Core0 画图）和 `dvi0.dvi_frame_count`（Core1 引擎）**是两回事**。
**怎么避**：两个核的计数器一起读 —— `printf("Core0=%u  Core1=%u\n", g_dvi_loop_frames, dvi0.dvi_frame_count);`
已固化成脚本 `tools/frames.ps1`，一次输出两个值。

### 错 4 —— 把"关掉某个功能"当成"排除变量"

**陷阱**：做对比实验（关掉 HDMI 音频），预期"关掉它路径更简单，应该更稳"。
**结果完全相反** —— 开音频能跑 107 帧，关掉只剩 **1 帧**。
**原因**：音频模式下那套 DMA 控制块数组**正好填满、没有零区**，指针跑过头只会踩进隔壁通道的**非零**块
（画面会花，但链条活着）；关掉音频反而让数组尾部露出**全零槽**，一踩就永久停摆
⇒ **音频不是病因，它是在替另一个 bug 打掩护。**
**怎么避**：遇到"**关掉某功能反而更糟**"，第一反应**必须**是
**"这个功能是不是在无意中掩盖着另一个更底层的问题？"**
想要"关掉某功能来简化问题"之前，先问 **它现在到底在替我挡着什么？**

### 险 1 —— 差点去"修"一个不存在的 bug

**陷阱**：读 `_set_data_cb` 时认定它漏了 `channel_config_set_enable(&c, true)`，准备动手加。
**动手前查了两处**：仓库里 vendored 的上游 `third_party/libdvi/dvi_timing.c`：**也没有这一行**；
SDK 的 `dma_channel_get_default_config`：**第 440 行就是 `channel_config_set_enable(&c, true)`**。

"它少写了一句" 往往等价于 "默认值已经是对的了"。

### 险 4 —— 差点把"引擎出了 107 帧"当成"屏幕出过图"

### 险 5 —— 手边就有权威证据，我却凭印象下结论

| # | 我说的 | 真相 | 证据在哪 |

| 1 | "RTD2660H 不在自打板上，它跟着屏模块走" | **所有芯片都在自打板上** | 是**我推断**的，用户从没这么说 |

   → `文档与代码规范`/`资源表`/`小本本`；都查不到才搜网页。
2. 说"占 X"之前先问自己：**我是"看到"的还是"觉得"的？** 觉得的必须标"**待查**"，不许写成结论。
3. `docs/资源表.md` 里任何一格填"我猜它占这个"，**都必须在同一行注明证据来源**；没来源的只能写"待查"。

### 险 6 —— 用户要的是"排障环境"，我给了"第二份工程"

# 二、代码篇（写错了：内核代码 / 构建配置）

> 这类错**改完大多能立刻验证**（编译、跑自检），所以通常一轮内能抓到；但一旦抓不到就特别贵。

### 错 1 —— 弄反了"谁欠谁"：naked 处理程序用了 r5 却没保存

**陷阱**：把系统调用号放在 `r5` 里，还写注释"r5 是本函数专用（r4-r11 是 callee-saved）"。
方向搞反了 —— 异常进入**只压 r0–r3、r12、lr、pc、xPSR 八个字，不保存 r4–r11**
⇒ callee 是**我这个处理程序**，是我欠被中断代码一个 `r5`。
**现象**：`main` 把 `&_impure_ptr` 常驻在 `r5` 里复用，跑过一次 SVC 后 `r5` 变成调用号，
下一次 `fflush(stdout)` 就成了 `fflush(野地址读出的值)` → `FILE*` 是奇数地址 → `LDRSH` 非对齐
→ HardFault（`CFSR = 0x01000000` = UNALIGNED，出错指令 `ldrsh r0,[r4,#12]`）。
**代价**：好几轮，现象看起来**特别像**特权态没恢复，把方向整个带偏了。

```asm
isr_svcall:
    push {r4, r5, r6, r7, lr}      @ ← 加这 20 字节，异常帧所有偏移同步 +20：
    ldr r0, [sp, #20]              @ 原来是 [sp, #0]   (r0)
    ldr r1, [sp, #24]              @ 原来是 [sp, #4]   (r1)
    ldr r2, [sp, #48]              @ 原来是 [sp, #28]  (xPSR)
    str r0, [sp, #20]              @ 写回返回值，原来是 [sp, #0]
    pop {r4, r5, r6, r7, lr}       @ ← 加这对；再 ldr r1, =0xFFFFFFF9 / bx r1
```

> **规则**：naked 异常处理程序里，**凡用到 r4–r11 中任何一个，入口必须自己 push、返回前 pop**。
> 加了 push 之后，**异常帧所有偏移要同步 +push 的字节数**。
> 同一个错当时还犯了两次（`snapshot_exception_frame`、`isr_memmanage` 也是用 r4–r7 没保存），一起修掉的。

### 错 7 —— 跨复位传状态只放一个变量

**陷阱**：只用一个 marker 记住**最后**挂死的那一步。而 `g_wt_result` 在 RAM 里、**复位就清零**
⇒ 复位后更早挂死的步会被重跑、又挂死 ⇒ 实验在两步之间**无限循环**，永远跑不完。
**怎么避**：用**位图**一次记住**全部**挂死过的步，并且**先校验来源**：

```c
#define WT_MAGIC 0x57543132u
uint32_t hung_mask = 0;
if (watchdog_hw->scratch[3] == WT_MAGIC) hung_mask = watchdog_hw->scratch[1];  /* 先校验来源！ */
uint32_t mark = watchdog_hw->scratch[0];
if ((mark & 0xFFFF0000u) == WT_MARK_BASE) {
    uint32_t idx = mark & 0xFFFFu;
    if (idx < WT_TOTAL) hung_mask |= (1u << idx);   /* 永久记下这一步 */
    watchdog_hw->scratch[0] = 0;
}
watchdog_hw->scratch[1] = hung_mask & (uint32_t)((1u << WT_TOTAL) - 1u);
watchdog_hw->scratch[3] = WT_MAGIC;
/* 循环里幂等跳过：hung_mask 命中的步直接置 2，已有结论的步 continue 不再跑 */
```

> **规则**：跨复位传状态要用**位图**（一次记住全部），不能只记"最后一个"。
> 而且**必须加 magic 校验** —— 否则新固件首次启动时会把上一版固件留在 scratch 里的值当成真数据。

### 错 9 —— `set()` 的 CMake 变量不等于编译宏

**陷阱**：`CMakeLists.txt` 里写着 `set(PICO_PSRAM_SIZE_BYTES 8*1024*1024)`，看着完全没错。
而 `build/compile_commands.json` 里它**出现 0 次** —— **根本没传给编译器**；
这个项目里**早就有一整段注释在警告这件事**，我读到了、也引用了，然后差点又踩。

```cmake
set(PICO_PSRAM_SIZE_BYTES 8*1024*1024)                       # ❌ 只活在 CMake 里，不进编译命令行
target_compile_definitions(PicoPhone PRIVATE
    PICO_PSRAM_SIZE_BYTES=8388608)                           # ✅ 对的
```
```powershell
# 改完立刻核对（这一步不能省）：数它出现了几次，0 次就是没生效
$cc = Get-Content build\compile_commands.json -Raw
([regex]::Matches($cc, 'PICO_PSRAM_SIZE_BYTES=')).Count
```

> ⚠️ **同一个判据在 ninja 构建下要换地方**（见 M14）：`compile_commands.json` 在这种 ninja 构建下
> **不存在** ⇒ 改去 **`build.ninja` 里数**（实测 `DVI_SM_CLKDIV=250` 出现 **98 次**）。

# 三、工具篇（做错了：调试器 / 烧写 / 文件与流程）

> 这类错**更隐蔽**：**工具本身没坏，是我用错了**，它照样给出"看起来正常"的结果，
> **错误输出不长得像错误**。

### 错 5 —— 在 GDB 表达式里调用目标上的函数

**陷阱**：GDB 脚本里写了 `printf "%d", psram_is_available()`。
GDB **真的去目标上执行了这个函数**，撞出一个 **假 SIGTRAP**，
报告说板子停在 `Hardfault_HandlerC ... reset()`，差点判定"我的改动把板子搞崩了"；
后来直接读 `CFSR=0 / HFSR=0` 才知道**根本没有故障**。
**怎么避**：固件里先算好写进全局变量（`g_psram_available = psram_is_available() ? 1u : 0u;`），
GDB 只 `printf "available=%u\n", g_psram_available`。

> **规则**：GDB 表达式里**只读纯内存变量**。想看的函数结果，**让固件写进全局变量**再由 GDB 读。

### 错 6 —— 用了 SDK 保留的 `watchdog scratch[4]`

**陷阱**：PSRAM 实验要靠"看门狗复位 + 断点续跑"，我把步号写在 `watchdog_hw->scratch[4]`。
续跑**从来没生效**（`resumed_from = -1`）：SDK 源码 `watchdog.c` 里
`scratch[4..7]` 是 SDK 保留的，一调 `watchdog_enable()`，自己的标记就被冲掉了。
**怎么避**：**只用 `scratch[0..3]`** —— `[0]` = 当前正在跑第几步；`[1]` = 挂死步的位图（跨复位）；`[3]` = `WT_MAGIC`（校验来源）。
（SDK 占用情况：`scratch[4]` = `WATCHDOG_NON_REBOOT_MAGIC`（`watchdog_enable()` 写的）；
`scratch[5..7]` = `watchdog_reboot()` 用的。）

> **规则**：用任何"看起来是通用资源"的东西之前，**先去 SDK 源码里搜一遍它有没有被占**。

### 错 8 —— GDB 批处理脚本被静默截断（**犯了两次**）

**陷阱**：写了 `printf -- "-- 说明 --\n"`（**`printf --` 不是合法 GDB 语法**），
又写了 `p DVI_SYNC_LANE_CHUNKS_WITH_AUDIO`（**宏不是符号，`p` 不了**）。
`gdb -batch -x 脚本` 里**任何一条命令报错，后面全部不再执行**，而且**不会说"我停了"** ——
两次都是"前半段有输出、后半段凭空消失"。
**怎么避**：`printf "\n===== 分段说明 =====\n"`（**不带 `--`**、不嵌双引号）；
`p sizeof(struct dvi_scanline_dma_list)`（**只 `p` 真符号**，`sizeof` 是合法的）；
**结尾必须有完成哨兵**：`printf "\n=== GDB_SCRIPT_COMPLETE ===\n"` —— 没有它出现，就说明被截断了。

> **规则**：① **最要紧的输出放最前面**；② 不 `p` 宏、不用 `printf --`、不在双引号里嵌双引号；③ **结尾必须有完成哨兵**。

### 错 10 —— 只 reset 不 flash = 拿新符号读旧固件（**同一个病犯了两次**）

**陷阱**：用新编译的 ELF 去读板子上**旧固件**的内存。符号全错位，读出来的数字**看着像真的**
（实测读到过 `0x09090909` 这种规律值），非常容易误判成"新代码生效了、结果如何如何"。
**是最危险的一类 —— 错得看不出来。**

```
# ❌ 错的：只复位不烧写          # ✅ 对的：先烧写并校验，再自由运行
init                             init
reset halt                       halt
                                 program "<绝对路径>/xxx.elf" verify
                                 reset run
```
采集脚本一律**先真烧写再跑**（`tools/frames.ps1`、`tools/psram_wt.ps1` 都已内建）。

**错 10（第二次）—— 拿【旧日志】当【新结果】**
**陷阱**：整理完目录后验证编译，用的检查命令是 `Get-Content debug_logs\build_log.txt` ——
而那份日志**正是我刚搬过去的那份旧的**，它打印出 `BUILD_EXIT=0`，差一点就报"整理后编译通过"。
**同一个病**：**拿旧数据当新结果**（这次不是"新符号配旧固件"，而是"新目录配旧日志"）。
**怎么避**：验证构建结果时**必须同时看产物时间戳**：

```powershell
Get-ChildItem build\PicoPhone.uf2,build\PicoPhone.elf | Select-Object Name,LastWriteTime
Get-Date    # 和上面比，必须是"刚刚"
```

> **规则**：判断"这次跑成功了吗"，**只看结论行是不够的**，必须确认
> **结论行所属的那份产物/日志是这一次生成的**（对时间戳）。
> 尤其当项目里有"历史日志归档目录"时 —— 那里的东西默认全部是旧的。

### 错 11 —— 用"扩展名"当筛选条件，把要留的文件一起扫走了

**陷阱**：整理目录时把"调试日志"定义成"根目录里 `.out` / `.err` / `.txt` 结尾的文件"，然后照着批量搬走。
**`CMakeLists.txt` 也是 `.txt` 结尾** —— 构建入口被一起搬进了 `debug_logs/`。

```powershell
$logs = Get-ChildItem -File | Where-Object { $_.Extension -in '.out','.err','.txt' }   # ❌ 按扩展名一刀切
$keep = 'CMakeLists.txt','pico_sdk_import.cmake'                                        # ✅ 再显式排除
$logs = Get-ChildItem -File |
        Where-Object { $_.Extension -in '.out','.err','.txt' -and $_.Name -notin $keep }
```
**搬完之后【立刻打印目的地目录、逐个检查】有没有误搬。**

> **规则**：**按"扩展名/名字模式"批量操作文件时，永远假设它会误伤** ——
> 这类条件**描述的是"格式"，不是"用途"**。
> 所以：**先筛，再拿一份显式的排除名单过一遍，最后打印结果核对。**

### 错 12 —— 把"整理"当成一次性动作，没管"下次运行会不会又乱"

**陷阱**：搬完文件、改完 CMake、编译通过就准备收工 —— **根目录立刻又冒出了 `build_log.txt` 和 `_commit_msg.txt`**：
`tools/build.cmd` 里写死了 `set "LOG=build_log.txt"`，`cycle.ps1` / `frames.ps1` / `psram_wt.ps1` 也都在往根目录写日志。
**整理只做了一半**：静态文件搬走了，**动态产物还在往原地生成**。
**怎么避**：`tools\build.cmd` 里把输出目标也一起搬（`if not exist debug_logs mkdir debug_logs` +
`set "LOG=debug_logs\build_log.txt"`），然后**改完必须真跑一次**，确认：
① 新日志出现在新位置（看时间戳是刚刚）；② **根目录没有重新冒出任何东西**。

> **规则**：整理目录时，**"静态文件搬走"和"生成路径改掉"是同一件事的两半**，只做一半等于没做。
> 判断标准不是"现在干净"，而是**"跑一轮之后还干净"** ⇒ 整理完**必须触发一次真实运行**再验收。

### 险 2 —— 差点把"加了静态数组"误判成"撞栈"

**陷阱**：给内核内存管理器加了 320 KB 静态数组，随后板子行为异常，
第一反应是"`.bss` 涨了 320 KB，肯定把栈撞了"。
**刹住的动作**：**先量了 ELF 布局** —— `g_sram_arena_raw` 在 `0x20008000`，
栈在 `scratch_y` 区（`0x20081800+`），**不重叠** ⇒ 排除。
**怎么避**（怀疑内存布局，先量，别先猜）：
```powershell
arm-none-eabi-size.exe -A build\PicoPhone.elf | Select-String "bss|stack|heap|scratch"
arm-none-eabi-nm.exe --numeric-sort build\PicoPhone.elf | Select-String "g_sram_arena_raw|__StackTop|__HeapLimit"
```

### 险 3 —— 差点在 GDB 里按符号名读 DMA 调试寄存器

**陷阱**：想读 `dma_debug_hw->ch[n].dbg_tcr`。而 `dma_hw` / `dma_debug_hw` **都是宏，不是符号**；
按符号解析会报错（把整个脚本截断，见错 8）或读到野地址。
**怎么避**：按地址读 —— **通道 n 普通寄存器 = `0x50000000 + n*0x40`；
调试区 = `0x50000800 + n*0x40`（+0 `dbg_ctdreq`，+4 `dbg_tcr`）**。

> **规则**：SDK 里带 `_hw` 后缀、长得像指针的东西，**先确认它是宏还是变量**。

### 错 13 —— 静默失败却报成功（换行符 + 假阳性）

**陷阱**：改 `docs/工作守则.md` 时用 `-split "`r`n"` 切行来判断锚点，但那个文件是 **LF 换行**
⇒ 整个文件被当成**一行** ⇒ `StartsWith` 一条都不匹配 ⇒
**什么都没改，脚本却打印了"✅ 已加规则 25"**。
**为什么这条比"报错"危险得多**：报错我会立刻知道；**静默成功会让我向你汇报一件根本没发生的事**。
**紧接着又犯了两个近亲**：① 插入错题时 here-string 用了**会插值**的写法，
里面的 `$(...)` 被 PowerShell **当场执行**，写进去的代码块是坏的；
② 同一次用的 `[regex]::Replace` 把**整个正文复制了两遍**（212 行 → 449 行），靠 `git checkout` 才恢复。

**怎么避（三条都必须做）**：
1. **改文件用「按行数组重组」**：`Get-Content`（它自己会正确处理 LF 和 CRLF）→
   用 `Select-String '^<锚点>'` 取 `.LineNumber` → `$lines[0..($idx-1)] + $entryLines + $lines[$idx..]`
   → `Set-Content -Encoding utf8`。**不要切字符串、也不要靠正则捕获组。**
2. **含有 `$` 或反引号的内容，一律用【单引号】here-string**（开头是 @ 加单引号、结尾是单引号加 @），
   这样 `$f` 和 `` `r`n `` 会**原样保留**。
3. **结构改动后必须【重新读文件】验证结构性不变量**，不能只查一个关键字：
   行数应 ≈ 原行数 + 新增行数；`(Select-String '^## 开工前自检').Count` **必须 = 1**；
   `(Select-String '^### 错 5 ').Count` **必须 = 1**，>1 就是被复制了。
4. ⚠️ **【验证代码本身也会错】—— 同一天又踩了三次。** ⇒ 订正：写验证时也要**防自己** ——
   **模式尽量宽**（`^## .*开工前自检`）；**异常结果先怀疑检查条件，再怀疑文件**；
   **改文件之前先 `Get-Content` 看清楚原文**。
→ 三行现场对照表见 **`docs/陷阱-归档.md` §B1**。

### 错 17 —— 桩只复现了【签名】，没复现【契约】—— 于是主机侧给真板 panic 开了豁免

**现场（2026-10-01 晚，上机实测）：** 板子在 `kres_selftest()` 第 29→30 步之间 panic，卡死在 `_exit()`。
用 SWD 在 `__assert_func` 上下断点抓到现行，读出三个字符串：
`文件 …/sdk/2.3.0/src/common/hardware_claim/claim.c` / `行号 51` / `函数 hw_claim_clear` / `表达式 hw_is_claimed(bits, bit_index)`。

⇒ 根因：`kres_dma_import()` 只写账本、**不调 `dma_channel_claim()`**；
而 `kres_dma_release()` 里**无条件**调 `dma_channel_unclaim()`
⇒ 真 SDK 的 `hw_claim_clear()` 断言"这位从没被认领过" ⇒ panic。（PIO 一路同病。）

**但真正该记的是"为什么主机侧没抓到"**：`tools/host_test/stub.c` 里是
`void dma_channel_unclaim(unsigned int channel) { if (...) g_dma_claimed[channel] = false; }`
—— **无声赋值，没有断言。** 而真 SDK 是 `dma_channel_unclaim → hw_claim_clear → assert(hw_is_claimed(...))`。
⇒ **同一份 `kernel_res.c`，主机侧 43/43 全绿，真板 panic。**

**为什么这条比普通 bug 更该防**：被测代码没错的时候，桩和真实现没差别；
**差别只在"代码写错的时候桩会不会响"** ⇒ **一个过于宽松的桩，等于给被测代码发了一张"主机侧免死金牌"**，
而主机侧自检的全部价值就在于"上不了板时也能挡住错误"。

**怎么避**：
1. **桩必须复现【契约】，不只是【签名】。** 具体检查三条：**断言**（重复认领/释放未认领）、
   **边界**（越界返回什么）、**失败路径**（满了、空了、超时了分别怎么表现）。依据是**真 SDK 源码**，不是印象。
2. **改动检查机制的收尾动作，固定成这个顺序**：① 先修桩（把契约加进去）→ ② **跑一遍，【必须失败】**
   （这一步才是"证明检查机制真的会响"）→ ③ 再修被测代码 → ④ 再跑，转绿。
   ⚠️ **跳过 ② 就等于没验过检查机制。**
3. **异常结论先怀疑检查手段。** 同一晚还差点把"`mdw` 没有输出"判成"内存读不到" ——
   其实是 OpenOCD 的命令输出根本到不了 stdout（要用 `capture` 包一层）。
   ⇒ **看到"什么都没有"时，先想想是不是"我的量具坏了"。**

### 错 18 ★★ —— 沙箱 / PowerShell 的**三条构建陷阱**（做 `tools/build_sub.ps1` 时连着踩）

> ★★ **2026-10-03 加星，而且本条属于"最该先看"的一类**：
> 其中第 1 条**项目早就写在 `tools/build.cmd` 的头部**，**但清单里没有** ⇒
> 我第一次做工具时**完全没想起来**，白挂了 4 轮。**⇒ 本条已同步进 `docs/开工前自检.md` §三 的前三条。**

**1. 沙箱禁止"把子进程输出走管道" ⇒ cmake / ninja 不能直接跑**
- **现象**：`cmake` / `ninja` 被 `| Out-Host` / `| Out-Null` 捕获时**失败或只给碎片输出**。
- **原因**：本机沙箱**禁止捕获子进程的 stdio**（命名管道被拦截）。
- **正解**：**把输出重定向到工作区内的文件，再读那个文件** —— 这正是 `tools\build.cmd` 存在的原因
  （它头部原文就写着：*the shell sandbox blocks capturing a child process's output through a pipe,
  so cmake/ninja cannot be run directly from the agent's PowerShell …*）。
- **教训**：**这条规矩早在仓库里，只是没进清单** ⇒ 说明"写在某个脚本注释里"≈ 不存在。

**2. PowerShell 反引号续行：反引号后面多一个空格就失效**
- **现象**：参数被拆散，变量甚至以**【字面量】**传给 cmake —— 报错原文
  `Target board (PICO_BOARD) is '$board'`（把 `$board` 当字符串了）。**代价**：为这一条**挂了 4 轮**。
- **正解**：**改用参数数组** `@(...)`，再用 `& $exe @args` 调用：
  ```powershell
  $cmakeArgs = @('-G','Ninja','-S',$Project,'-B',"$Project\build", "-DPICO_BOARD=$board")
  & $cmake @cmakeArgs
  ```
- **规则**：**任何超过 2 个参数的外部命令调用，一律用数组，不要用反引号续行。**

**3. `-S` / `-B` 给【绝对路径】会在 SDK 平台预检查处失败；且旧 `CMakeCache.txt` 必须先清**
- **现象**：绝对路径**在 SDK 的 platform 预检查处失败**；即使路径对，**旧的 `CMakeCache.txt` 里带着
  上次的平台参数**（`PICO_PLATFORM` / `PICO_BOARD`）⇒ 配置结果错乱。
- **正解**：`-S`/`-B` **用相对路径**；**发现旧缓存就先删掉 `build\` 整个目录**再配置
  （`build_sub.ps1` 已内建：检测到 `CMakeCache.txt` 就自动清理并提示）。

> **合并成一条可执行规则**：**要跑构建类命令（cmake / ninja / 任何会 fork 子进程的工具）时：**
> ① **不要用管道捕获输出** → 走 `.cmd` + 重定向到 `debug_logs\*.txt`，或直接印到终端；
> ② **参数用 `@(...)` 数组**，不用反引号续行；
> ③ **`-S`/`-B` 用相对路径**，并且**先确认 `build\CMakeCache.txt` 是本次的**（不是就删掉整个 `build\`）。

### 错 19 ★★ —— 三条"测量通路"上的错，同一个病根：**没做交叉验证就下结论**

> 出处：2026-10-02 深夜探针打通（`docs/历史.md`「【探针打通】」一节）+ 2026-10-03 连续性测量。

**1. 🔴 元凶：缺 `pio_gpio_init()` ⇒ PIO 永远采到 0**
- **陷阱**：`gpio_init()` **只把引脚功能设成 SIO**；而 **PIO 采样走的是 PAD 输入通路**
  ⇒ 必须把功能**交给 PIO**（`pio_gpio_init(pio, pin)`，它顺带清掉 PAD 的 ISO 隔离位）。
- **不做的后果**：PIO 读到**恒 0**，而你会去怀疑采样程序、DMA、接线 —— 全是错的。
- **实测证据（`pin_toggle` 判据）**：
  ```
  SIO 直读 = 0x55/0x54 ✓    PIO 采集 = D2P/D1P/D0P/CLKP 99.97%、D2N/D1N/D0N/CLKN 0.00% ✓
  => PATH OK (sampling + wiring verified) ✓
  ```

**2. `instr_mem` 在 RP2040 上只读回 0（写-only）⇒ 不能用它判断"程序有没有写进去"**
**陷阱**：想用读 `instr_mem` 来确认 PIO 程序加载成功 ⇒ **永远读到 0**，误判成"没写进去"。
**正解**：判断程序是否生效，要看**行为**（`SM_ADDR` / FIFO / 引脚），不要读 `instr_mem`。

**3. 把"待测板停在 BOOTSEL、引脚不驱动"误当成通路故障**
**陷阱**：待测板在 BOOTSEL 下引脚**不驱动** ⇒ 采到 0，被当成"探针通路坏了"。
**正解**：**SIO 与 PIO 同时读，做交叉验证** ——
两个都 0 ⇒ 更可能是**被采对象没在驱动**；一个有一个没有 ⇒ 才是**通路/引脚映射**的问题。

> **怎么避（一行）**：**"什么都没采到"时，先用【第二种独立手段】量同一个点**
> （SIO vs PIO、万用表 vs 示波器、两个计数器…）—— **单手段的 0 不能证明"没有"，只能证明"我没看到"。**

> **与错 13/15/17 同族**：**都是"验证手段本身不可信"**。这已经是**同一族的第五次**。
> ⇒ 所以 `docs/开工前自检.md` §一 里"异常结果先怀疑检查条件"那条，命中率最高。

### 错 21 ★★ —— 子智能体越界改主仓库，而主 AI 未审 diff 就提交（两错叠加）

**陷阱（两件事同时发生）**：

2. **主 AI 收工时 `git add -A` 没看 diff 就提交**，把它的改动混进一条毫不相关的"规矩"提交里，
   提交信息还完全不提它。打断它时它的遗言是"**让我回到主仓库检查状态并提交**" ⇒ **它本来要直接提交到主线。**

**怎么避**：

3. **主 AI 禁止 `git add -A`**；提交前必须 `git diff` 逐条看；
   合并前必须 `git status` 确认主仓库没被别的东西改过。

### 错 24 ★ —— 目标的两种"停"要分清：**`disarmed` 能自己 resume**，`paused` 才可能要重建

- ✅ **另一半也有证据（用户实测）**：**`phase=paused`** **resume 失败过** ——

**陷阱**：**把这两种状态混为一谈** —— 见到目标"没在跑"就以为必须重建（多花一轮），或反之对着 `paused` 反复试 `resume`（白耗轮次）。

2. **`phase=active` + `activation=disarmed`** ⇒ **直接 `update_goal resume`**（**不必重建**）。

   ⚠️ 另：**已有目标时 `create_goal` 会被拒**（"goal ... already exists with phase ..."）⇒

### 错 25 ★ —— 注释说"照常转发"、代码却把它"吃掉"：**靠算法镜像自测才抓出来**

**背景**（2026-10-04，debugprobe 后门 `src/backdoor.c`）：写 `ESC ESC` + 未知字节的处理时，
`default:` 分支里 `backdoor_say("... unknown command ...")` 之后写了 `return true;`
—— **错：连这个普通字节也被吃掉**。而**紧邻的注释**和调用处的注释都写着"**这个字节仍照常转发**"。
⇒ **注释与代码相反**，但**编译器不会报错、运行也不崩**（只是悄悄吞掉一个字节）。

**陷阱**：**读代码时被注释说服**；而且这类错误**在宿主机上没有 C 编译器、又不敢刷机实测**时，最容易蒙混过去。

**怎么避**：
1. 对**纯逻辑、可在宿主复现**的模块（状态机/过滤器/编码器），写一个**算法镜像自测** ——
   把 C 里每条分支**逐行照抄**到 Python，并把**每条用例的期望值显式写出来**；
2. **期望值要按"承诺的语义"写，不要按"代码当前行为"写** —— 这才是判据；
3. 测试要覆盖**分片边界**（本次关键用例就是"ESC 在上一片末尾、命令在下一片开头"）。

**证据**：镜像自测 **7 条用例**，修前**第 5、7 条 FAIL**（第 7 条直接暴露"未知字节被吞"）；
修 `return true → false` 并同步修正用例期望后 **7/7 全部通过**；重编译后 uf2
**SHA256 由 `B79FE3A0…` 变为 `1770C4D4…`** ⇒ 确实改进了固件（不是只改了测试）。

**⚠️ 边界说明**：镜像自测**只验算法语义，不等于固件实测** —— 真机行为（USB 栈、CDC 时序）
仍须刷上去量（见 `docs/当前状态.md` 2026-10-04 深夜那节）。
⇒ **重建目标时要把已被实测推翻的参数改掉**，别原样抄。

> **同族**：与陷阱 1、险 5 **同一个病根** —— 要防的是把**没验过的工具行为**当成既定事实。

### M14 —— DUT 位率与 `DVI_SM_CLKDIV`：**分频 >255 会被 PWM 截断** —— ✅ **已裁决（2026-10-04 上机）**

**根因（源码 + 实测双向确认）**：`DVI_SM_CLKDIV` 在库里作用于**两个不同的硬件**：
1. **数据 lane**：`frank_serialiser.pio:71` `sm_config_set_clkdiv(&c, DVI_SM_CLKDIV)` —— **float 分频，512 正常生效**；
2. **时钟 lane**：`frank_serialiser.c:124` `pwm_config_set_clkdiv_int(&pwm_cfg, DVI_SM_CLKDIV)` ——
   **RP2040 PWM 的分频整数字段只有 8 位（≤255）** ⇒ **512 被截断**。
   （`frank_serialiser.c:27-29`：`USE_PWM_CLOCK` 默认启用 ⇒ **时钟 lane 确实由这块 PWM 驱动**。）

⇒ **分频 >255 时，时钟 lane 与数据 lane 速率不一致** ⇒ 解码器把 CLK lane 当基准（"10 bit/CLK 周期"）就全错。
这也正好解释：为什么 `--dut-sm-clkdiv 256` 时它"CONSISTENT"（因为 CLK lane 恰好是数据率的 2 倍）。

**实测对照（同一颗 DUT，只改分频）**：

| DUT 分频 | 解码器给的标称 | 实测 `samples/CLK周期` | 速率判决 |
|---|---|---|---|
| **512**（>255，被截断） | 8 | **40.0** ⇒ 4.000 采样/位 | ❌ `INCONSISTENT` |
| **250**（≤255） | 3.90625 | **39.0** ⇒ 3.900 采样/位 | ✅ **`CONSISTENT`（差 0.16%）** |

**⇒ 对策（写进配方）**：`wboard_dvi` 的 `DVI_SM_CLKDIV` **必须 ≤255**（重建 `build_slow250` 即 250）。
要更高采样比就**提探针采样率**，不要提 DUT 分频。
- 🔧 **已真修（2026-10-04 深夜，`frank_serialiser.c`）**：改成**分频不够就放大 `wrap`** ——
  周期 = `10*K` 计数、比较值 = `5*K`，等效分频 = `clkdiv_int * K`（K 可达 6553）
  ⇒ **`DVI_SM_CLKDIV` 不再有 255 上限**，且时钟 lane 恒等于数据 lane 的 1/10；
  `≤255` 时 K=1，**行为与原来逐位一致** ✓。⇒ 以后可让 DUT 任意慢，做**无混叠深度过采样**。

**顺带**：`compile_commands.json` 在这种 ninja 构建下**不存在** ⇒ 核对宏改去 **`build.ninja` 里数**
（实测 `DVI_SM_CLKDIV=250` 出现 **98 次**）。

**子结论（同一个 DUT 上量到的采样比）**：探针 `c64`（3.94 MSa/s）× DUT 250 ⇒ **3.900 采样/位**；
探针 `c32`（7.875 MSa/s）× DUT 250 ⇒ **7.800 采样/位**（两档速率判决都 `CONSISTENT`）。
⚠️ **`clean-bit` 逐 lane 的差异（D0=0.20 / D1=0.94 / D2=0.71）不是"时间轴连续性"问题** ——
真因是**各 lane 的亚位相位偏移**（见 `docs/实测数据.md` §15.4）：给解码器加上**逐 lane 相位搜索**后，
三路 clean-bit 一起回到 **0.90~0.96**、符号相位变成 `strong`。

### M16 —— 🔴 **同步 lane（蓝/D0）的有效区从来不发数据**（2026-10-04 受控实测）

**判决**

  ⇒ 这正好解释"**屏幕点亮、画面从未正确**"：时钟锁得住、消隐期控制符号也合法，但**蓝通道像素数据从没上过线**。

  （`frank_dvi.c:353-368` 的注释已把病灶写明：把每个 lane 数组的【最后一条】改成不链
  ⇒ **代价是链条不再自持，必须由 IRQ 每行显式重新触发**；而实测**每行被 2.19 次中断打断**，
