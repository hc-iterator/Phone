## 三、已实测的事实（可以当结论用）

### 特权态模型（有 SWD 采样，不是推理）

| 采样点 | 实测 | 含义 |
|---|---|---|
| `g_probe_ctrl[0]` 第 1 次 SVC 入口 | 1 | **nPRIV 跨异常进入原样保留** |

| `g_probe_mpu_type` | 0x800 | 行为验证：特权读 `MPU_TYPE` 成功（8 区域） |

### 系统调用链路

`g_probe_svc_n=4`、`g_sys_calls=3`、`g_sys_denied=1`、`g_sys_last_no=4`、
**`g_sys_done_magic=0x5AFE0001`**（这条最关键，它最后写）、CFSR/HFSR = 0/0。

### PSRAM（2026-09-27 实测，**推翻了我自己的假设**）

- **芯片真的在 GPIO47 上**：`KGD=0x5D`（APS6404 Known Good Die）、`EID=0x46`、**8 MiB**
- SDK **认对了** GPIO47；候选脚 `{0,8,19}` 上没人答话（KGD=0x00）
- QMI M1 时序实测：`timing=0x60242202`、`clkdiv=2`(75 MHz)、`rxdelay=2`、
  `max_sel=18`(≈7.68 µs)、`min_desel=2`
- **连续写入的挂死阈值在 16 B 和 256 B 之间**：16 B 通过（6 µs）；**256 B 挂死**
- ✅ **随机读取是通的**（用户 2026-10-01 补充）：**随机读取通过；连续块读写报 error。**
  ⇒ 这条把问题的性质定住了：**不是"芯片坏"，是特定访问模式的问题**。
  ⚠️ **仍待确认**：用户说的"报 error"是**返回错误码**还是**整片挂死** ——
  两者根因不同（前者可能只是 QMI 超时返错，后者才是 `tCEM` 违约）。
- 256 B 四线制 = 512 个 QSPI 时钟 = 6.8 µs，**正好卡在 `max_select`(7.68 µs) 边界上**
  ⇒ 高度怀疑：**凡是长到必须让 QMI 主动断开片选的写入就挂死**，
  也就是 `max_select` 超过了这颗 PSRAM 的 `tCEM` 上限（**⚠️ 未验证**）
- ⚠️ 症状：写挂住之后**取指也走 QMI ⇒ 整片卡住**，SWD halt 时 PC 停在写指令上
- ⚠️ **`PICO_PSRAM_SIZE_BYTES` 没传给编译器**（`compile_commands.json` 里 0 次）；
  因为开了自动检测所以暂时无害，但要改就该用 `target_compile_definitions`
- ⚠️ `PICO_AUTO_DETECT_PSRAM_CS` 默认 = `PICO_AUTO_DETECT_PSRAM` = **1**，
  所以 `PICO_PSRAM_CS_PIN=47` 在自动检测开启时**是被忽略的**

### 内核内存管理器（2026-09-27 新增，自检通过）

- 二叉伙伴分配器（选它是因为**分出来的块天然是 2 的幂 + 自然对齐，正好喂给 MPU**）
- SRAM 竞技场实测 **128 KiB @ `0x20020000`**（声明 320 KB，`arena_fit` 挑出对齐的 128 KB）
- 自检 **24 步全过、`fail_at=0`**；峰值 = 整个池子、空闲能回到满 ⇒ 分裂与合并都正确
- PSRAM 池**默认关闭**（`KMEM_ENABLE_PSRAM=0`）：
  **绝不能让一个会挂死的内存进入分配器**

### SRAM 用量（供以后规划）

主 RAM 约用 144 KB（`.data` 24K + `.syspage` 4K + `.bss` 106K + heap 2K），
顶部 8 KB 是 scratch。**空闲约 376 KB。**

## 四、DVI 早期结论（2026-10-01）—— **⚠️ 已被 10-02 取代，只留查表项**

### 4.1 配置（重做时直接照抄）

- 方案：**PIO bitbang DVI**（`third_party/frank-hdmi-sound/`）
- **不能用 HSTX**：HSTX 硅片硬连 **GPIO12..19**，而本板 DVI 在 **GPIO32..39**
  （证据：数据手册 Table 3、SDK `io_bank0.h`、`pico_hdmi` 源码）
- 引脚：`CLK=38, D0=36, D1=34, D2=32`｜极性 `FRANK_HDMI_INVERT_DIFFPAIRS=1`（旧记录写 0，**已作废**）
- 时钟：**252 MHz**（`set_sys_clock_khz(252000)` + `FRANK_HDMI_SM_CLKDIV=1`）+ `VREG_VOLTAGE_1_25`
- ⚠️ **不要用库 README 推荐的 504 MHz** —— 实测把 Core1 打进 HardFault、Core0 卡到连 SWD 都 halt 不住
- 音频 `FRANK_HDMI_ENABLE_AUDIO=0`（在 `frank_hdmi.h`）｜**8bpp 帧缓冲 / 16bpp 编码器不是 bug**

### 4.2 「全零槽」坑（**是真的、但只算次级**；改 `frank_dvi_timing.c` 前先看）

- 根：`dvi_scanline_dma_list` 按**音频模式段数**开数组（同步 6 槽、另两通道 7 槽），非音频模式只填前 4 / 前 2 段 ⇒ 余槽全 0。
- 触发：IRQ 要在 `frank_dvi.c:454` 把控制读指针拨回第 0 段，而有效像素段只有 320 字 ≈ **25.4 µs**；
  **被拖过这个窗口**就链式读过头 ⇒ 递出全零控制块 ⇒ 数据通道 `CTRL=0`（`EN=0`）⇒ 永久停摆。
- 证据：`l0[4]/l0[5]/l1[2..6]/l2[2..6]` 实测全 0；同步通道读指针停在 `l0[5]`；三数据通道 `CTRL/TRANS/READ/WRITE` 全 0。
- **顺带解释了"开音频 107 帧、关音频 1 帧"**：音频模式段数正好填满数组、没有零区。
- 已做修复：① `frank_dvi_timing.c` 加 `_dvi_fill_unused_slots()`（空槽填成第 0 段副本）；
  ② `frank_dvi.c:384` 死等循环**加上限**，超时记 `g_dvi_tcr_timeouts` 后跳出。
- 残留签名：**lane0 的数据通道被装上 lane2 的控制块** ⇒ 指针跑出本通道数组；
  **正解是让指针在数组内环绕**（或让段数与每行触发次数严格相等），而不是只保证"非零"。

**问题：探针采样【时间轴不连续】—— 大段丢样。**

| 配置 | 边沿数 | 理论边沿 | 连续度 | `gaps>10` 占比 |

- ❌ **"DMA 优先级不够"** —— 加了高优先级后**数值无改善**（1720 → 1705）。

**关键形态（说明"怎么丢"）**：
- 有采样的间隔**中位 = 2 个采样** ⇒ 与"63 MSa/s 采 25.2 MHz"的理论值（≈1.25）接近
  ⇒ **采到的那一小段时间里速率是正常的** ✓
- 但 `gaps>10` 占 **14.6%**，**最大空洞 6190 采样 ≈ 98 µs** ⇒ **周期性大段完全没有数据** ✗
- ⇒ 形态是"**跑一小段 → 停很久 → 再跑一小段**"，**不是"均匀丢点"**。

**下一步诊断手段（已定，还没做）**：
> 在探针里加一条命令：**隔已知时间读两次 DMA 的 `transfer_count`**。
> - 若实际搬运速率 ≈ 期望（**15.75 Mwords/s**）⇒ DMA 在正常搬 ⇒ 问题在**缓冲区被别的写了 / 映射错**；
> - 若实际搬运速率 **远低于**期望 ⇒ DMA 确实**被卡住** ⇒ 再往下查 **DREQ / 总线**。

### 🔴 15.4 【2026-10-04 上机】符号解码出不来的**真根因：各数据 lane 有各自的亚位相位偏移**

#### ❌ 先作废一条我写错的结论（2026-10-04 当晚，存在约半小时）

我曾写"`in pins, 8` 是跨 8 个周期采 8 根脚、所以有偏斜"——**这是错的，已作废**。
**反证（硬数据）**：固件 `m` 在 `c64` 实测 **984,500 words/s**，而 SM 时钟 = 252e6/64 = **3,937,500 Hz**
⇒ **3,937,500 / 984,500 = 正好 4.0 个周期/字** ⇒ 32 位 ÷ 4 周期 = **8 位/周期**
⇒ **`in pins, 8` 是【一个周期并行读 8 根脚】**，没有跨周期偏斜。

#### ✅ 真根因

**DVI 允许时钟 lane 与数据 lane 之间有相位差**；三条数据 lane 是**三个独立 PIO SM**，启动时刻不同
⇒ 每条 lane 的**位边界**相对"CLK 上升沿"各有偏移。实测（`cap_os_dut250_probe64`，`samples/CLK周期 = 39`，
即 **3.9 采样/位**）：

| lane | 跳变出现的相位（mod 39 采样） | 推出的位边界偏移 |
|---|---|---|
| **D0P** | 14,18,22,26,30,34,38…（梳状，间距 4） | **≈ +2.3 采样** |
| **D1P** | 28,32,36… | **≈ +0.7 采样** |
| **D2P** | 31,35,0,4,8… | **≈ 0（对齐）** |

**而位周期只有 3.9 采样** ⇒ D0 的偏移是 **0.6 个位周期** ⇒
`tools/tmds_decode_oversampled.py` 把位槽锚在 **CLK 上升沿、不做相位补偿** ⇒
**D0 的采样点正好落在跳变附近 ⇒ clean-bit 崩**；D1 偏移小 ⇒ 0.94；
而且**跳变越密的 lane 受害越重**（D0 跳变 13422 次 vs D1 4153 次）
—— 与实测 **D0=0.20 / D1=0.94 / D2=0.71** 的形状**完全吻合**。
⇒ 符号切错 ⇒ 找不到 control 符号 ⇒ 整个 `VERDICT: FAIL`。

**⇒ 修法（解码器侧，不用改硬件）**：在建位槽时**搜索逐 lane 的亚位相位偏移**，
判据用 `clean-bit 最大化 / control 符号命中数`。`--probe-clkdiv`/参数体系不变。

#### ⚠️ 附带教训：我自己造的假象

当晚我写的三个一次性分析脚本（`debug_logs/analyze_*.py`）用了**错的字节序**
（把**最低字节**当第 0 个采样），而正确是**高字节 = 先采到的**
（固件 `sm_config_set_in_shift(&c, /*左移*/false, …)`，与 `tmds_decode_oversampled.py:140-143` 一致）。
⇒ 那批脚本报出的"1–3 采样毛刺""CLKP 只有 8 个离散间距""8.6% 时间空洞"**全是假象**；
改用正确字节序后 **CLKP 周期 = 39 采样（94%）、`<10 采样` 的间距 = 0.0%** ⇒ **采集链路本来就是干净的**。
**教训**：**任何"波形异常"结论，先用已知静态图案 + 已知动态图案各验一次字节序，再下判断。**

## 十四、SWD 三点对照（2026-10-07，用"带后门的空固件"当尺子）

**要判的问题**：`docs/陷阱.md` M1 那张「`cannot read IDR` 归因表」里还剩两条嫌疑没排除 ——
「**252 MHz 会搞坏调试口**」与「**总线上有重负载固件在跑 ⇒ AP 全 WAIT**」。

### 14.1 方法（可复现；且**主 AI 自己就能跑**，不必等人在 `/pico swd` 上敲）

1. **先造尺子**：`backdoor_only`（USB CDC + 后门 `B`/`R`/`?`，**别的什么都不干**，默认 150 MHz）
   与超频变体 `backdoor_only_oc`（同源码 + `-DBACKDOOR_OC_KHZ=252000`，vreg 1.25V =
   **照抄 `dvi_min` 正在跑的实测档** ✓ 不发明新频率）。
   两者都**自带串口后门** ✓ ⇒ 无论 SWD 通不通都走得回来（台架铁律）。
2. **每个状态先用串口问一句 `?`** ⇒ 确认「板子活着 + 当前主频」✓
   （不然 SWD 不通时无法区分"链路坏"还是"板子死" ✗ —— 这是最容易归错账的地方）
3. `pico_flash` 进目标固件，然后**直接调 openocd**（cfg 落 `debug_logs/swd_probe.cfg`）：

```powershell
# cfg 内容

# 命令

  -f interface/cmsis-dap.cfg -f target/rp2350.cfg -f debug_logs/swd_probe.cfg
```

> ⚠️ **cfg 里别加 `resume`**：openocd 的 examine **不会 halt** 目标 ⇒ 加了会多打两行
> `Error: … not halted / context restore failed, aborting resume` ✗（无害，但看着像失败 ✓ 我第一版就这么写的）
> ⚠️ **`pico_run tools/swd.ps1` 在沙箱里必死**：它要 `RedirectStandardOutput` ⇒ .NET 命名管道被拒 ✗；

### 14.2 读数（判据 = `SWD DPIDR 0x4c013477` + 两核 `Examination succeed`）
