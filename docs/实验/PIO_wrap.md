# PIO wrap 实验方案（手稿 2026-10-23「3 个新想法」之一）

> 手稿原话：
> > PIO 不是有自动循环吗？它必然有一个寄存器指向最后一条指令。它是每 SM 独有的吗？
> > 如果修改它和地址寄存器，让现状>上限，会发生什么？
> > 能否借此省略拼合时的 jmp 指令，以此省下指令时间和指令空间？
> > 这似乎能引向重大资源突破。

## 1. 机制（已查证）

| 手稿猜测 | 事实 | 依据 |
|---|---|---|
| "一个寄存器指向最后一条指令" | **`SMx_EXECCTRL.WRAP_TOP`**（5 位，0–31） | SDK `pio.h:632-634`：`execctrl = … \| (wrap << WRAP_TOP_LSB)` |
| "每 SM 独有的吗" | **是**。`EXECCTRL` 在 `pio->sm[sm]` 下，每个 SM 一套 | `pio_sm_set_wrap(pio, sm, wrap_target, wrap)` |
| "自动循环" | **是硬件行为**：指令**不自改 PC** 时，执行完 `WRAP_TOP` 自动跳 `WRAP_BOTTOM` | `pio.h:1562` 注释："if the instruction does not itself update the program_counter" |
| "省 jmp" | **成立**：`jmp` 占 1 条指令槽 + 1 周期；wrap 两者都不占 | 见下 |
| "省指令时间" | **每圈省 1 周期**（`jmp` 那条不执行了） | — |
| "省指令空间" | **省 1 条指令槽**（32 条里省 1） | — |

**关键约束**：`PIO_INSTRUCTION_COUNT = 32`，`wrap` 与 `wrap_target` 都**必须 < 32**（SDK 用 `valid_params_if` 断言）。硬件本身**不做这个检查** —— 直接写寄存器可以写进任意 5 位值。

## 2. 手稿三问的答案（待实验确认的部分标 ⚠️）

1. **寄存器是 `WRAP_TOP`，每 SM 独有** —— ✅ 已确认
2. **"让现状 > 上限"会发生什么** —— ⚠️ **未定义**。`WRAP_TOP < WRAP_BOTTOM` 时，硬件在"PC 到达 TOP"和"PC 到达 BOTTOM"两个条件重叠处行为不可预期，推测两种可能：
   - a) 立即 wrap 成死循环（PC 卡在 TOP/BOTTOM 之间）
   - b) 忽略 wrap、顺序执行到 31 再回 0
   **必须实测**，这是本次实验的核心。
3. **能否省掉拼合时的 jmp** —— ✅ 能，但有**硬限制**：
   - 只能 wrap **一个连续区间**（`[BOTTOM, TOP]`）
   - 循环体里**不能有分支**（`jmp`/`jmp x--` 会改 PC，wrap 不触发）
   - 所以"拼合"（多个 PIO 程序拼到一段里）时，**只有最外层的单层循环**能吃到这个优化

## 3. 实验设计

### 3.1 静态实验（现在就能做，不需要板子）

| 步骤 | 做什么 | 产出 |
|---|---|---|
| S1 | 写两个等价的 PIO 程序：A 用 `jmp` 收尾，B 用 wrap 收尾 | 两份 `.pio` |
| S2 | 用 `pioasm` 汇编，比较**指令条数** | A 比 B 多 1 条 |
| S3 | 数**每圈周期**：A = 循环体 + 1（jmp），B = 循环体 | B 每圈省 1 周期 |
| S4 | 把 B 放进 32 条槽的极限场景（DVI 串行器这种满槽程序） | 证明"省 1 条槽"在满槽时是**真收益** |

#### 3.1.1 已完成：单循环对照（2026-10-23）

```
loop_jmp   : e001 / e000 / 0000   → 3 条（末尾 jmp 0）
loop_wrap  : e001 / e000          → 2 条（WRAP_TOP=1）
```

#### 3.1.2 已完成：拼合对照（**手稿真正关心的场景**）

**两阶段拼进同一 SM**（阶段 A 三条 + 阶段 B 三条，整体一个连续循环）：

```
two_stage_jmp  : e001 e000 a042 0004 | e001 e000 a042 0000   → 8 条，8 周期/圈
                  └─ 阶段A ─────┘ jmp  └─ 阶段B ─────┘ jmp回0
two_stage_wrap : e001 e000 a042 e001 e000 a042                → 6 条，6 周期/圈
                  └─ 阶段A ─────── 阶段B ─────┘（WRAP_TOP=5，无 jmp）
```

| | 指令数 | 每圈周期 | 阶段间 jmp | WRAP_TOP |
|---|---|---|---|---|
| jmp 版 | 8 | 8 | 2 个 | 7 |
| **wrap 版** | **6** | **6** | **0 个** | **5** |

**结论**：拼合后只要**整体是一个连续循环**，把 `WRAP_TOP` 设到最后一条，**阶段间 jmp 全部省掉**，每圈省 **2 周期 + 2 指令槽**。

> 这正是手稿说的"修改行尾识别寄存器，省略拼合时的 jmp"——**实测成立**。
> 源码：`PIO_wrap_src/two_stage_jmp.pio` / `two_stage_wrap.pio`（`pioasm` 汇编产物 `.hex`/`.h` 同目录）。

**限制**（必须记住）：
- wrap **只能替代无条件回跳**。`jmp X--`（条件/计数跳转）替不了 —— SDIO 的 `response_loop` 就是这种。
- 拼合后的整体**不能有分支**（一旦有 `jmp X--`，wrap 窗口就被打断）。

### 3.2 动态实验（需要板子）

| 步骤 | 做什么 | 判据 |
|---|---|---|
| D1 | 正常配置 `WRAP_TOP=31, WRAP_BOTTOM=0`，跑已知程序 | 行为与 jmp 版一致（用 `SMx_ADDR` 读 PC 轨迹） |
| D2 | 故意设 `WRAP_TOP < WRAP_BOTTOM`（例：TOP=3, BOTTOM=10） | **记录实际行为**（卡死 / 跑飞 / 忽略） |
| D3 | 设 `WRAP_TOP=31`、`WRAP_BOTTOM=1`（跳过指令 0） | 验证 wrap 是否真的从 1 开始 |
| D4 | 在循环体里加 `jmp x--`，观察 wrap 是否被"打断" | 确认"自改 PC 的指令不触发 wrap" |
| D5 | 用 SWD 直接写 `EXECCTRL`（绕过 SDK 断言） | 验证"硬件不检查非法值" |

**工具**：`tools/swd.ps1`（读 `PIO0->SM0_EXECCTRL`、`SM0_ADDR`）；或 Picocmd（若已实现）。

### 3.3 与"拼合"的关系（真正的问题）

手稿关心的是 **PIO 拼合**（多个功能塞进一个 PIO 的 32 条槽）。wrap 的收益：

- **省 1 条槽/程序**：7 个程序拼一起就省 7 条 —— 但**每个程序的循环边界不同**，而 **wrap 只能设一组**（`WRAP_TOP/BOTTOM` 是 SM 级，不是程序级）
- ⇒ **只有"当前在跑的那一个程序"能吃到 wrap**，切换程序要重设 `WRAP_TOP/BOTTOM`（改 `EXECCTRL` 是**立即生效**还是**等下一条指令**？也要测）

**所以"重大资源突破"的假设要打折**：wrap 不是"每个程序都省 jmp"，而是"**当前程序**省 jmp"。真要突破，得靠**程序切换时动态改 wrap 窗口**（这本身有开销）。

## 4. 结论（现阶段）

- ✅ 手稿的**寄存器猜测完全正确**（`WRAP_TOP`，SM 独有）
- ✅ "省 jmp"**成立**：省 1 指令槽 + 每圈 1 周期
- ⚠️ "重大资源突破"**可能不成立**：wrap 窗口是 **SM 级**，拼合的多程序共享不了
- ❓ "现状 > 上限"的行为 **必须实测**（D2 是核心实验）
