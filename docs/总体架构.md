## §A 总体架构（2026-09-29 用户定的方向）

> **【用户定】= 用户口述的；【我提议】= 我补的推导与风险核算。**
> 两者要分得清，别把我的推导当用户的要求。

### A.1 两个阶段

【用户定】**现在的设备叫「技术验证」，跑通之后肯定要打板。**

| | **阶段 1：技术验证**（现在这块微雪 RP2350-PiZero） | **阶段 2：自打板** |
|---|---|---|
| 目的 | 把内核 / 权限模型 / 资源分配 / 显示通路 / 加载器**全部跑通** | 把验证过的东西**固定成硬件** |
| 显示 | PIO bitbang DVI @ GPIO32–39，**Core1 被软件 TMDS 永久占用** | **HSTX @ GPIO12–19**，硬件 TMDS ⇒ **Core1 解放** |
| 硬件瑕疵 | **容忍**（ETA6096 已烧、引脚被 40pin 占掉、PSRAM 时序待查） | 修掉 |
| 射频 | 无（RP2350 本身没有射频） | 模块 |
| 副核 | 无 | **可选：RP2040 经 SPI** |

> ### ⚠️ 由"技术验证"这个定位推出的最重要一条
>
> **硬件差异必须关在一层里（板级支持层 / BSP）。**
>
> 阶段 2 的硬件**不一样**：显示后端从 PIO 变 HSTX、引脚全换、
> PSRAM 时序不同、多出射频、可能还有副核。
> **如果内核到处直接写死引脚号和寄存器，打板那天整个内核要重写 ——
> 阶段 1 的成果会归零。**
>
> ⇒ **这件事现在就要做**：引脚、时钟、外设实例、显示后端、存储后端，
> 一律经一层板级配置取用，不许散落在各子系统里。

### A.2 总线与引脚分配

【用户定】**SD 卡走 SDIO，不占 SPI；所以 SPI 现在是空的。**

| 总线 / 外设 | 阶段 1（微雪） | 阶段 2（自打板） |
|---|---|---|
| QSPI CS0 | 16MB Flash | 16MB **1.8V** Flash |
| QSPI CS1 | 8MB PSRAM（`0x11000000`） | 16MB **1.8V quad** PSRAM |
| SDIO 4-bit | TF 卡座 | TF 卡座（**承重墙**：应用从这加载） |
| DVI / HDMI | PIO bitbang（占 **Core1** + 3 个 PIO SM） | **HSTX**（不占 CPU） |
| **SPI** | **空闲** | 空闲，**或**给副核 / 射频 |
| USB | 已用（CDC 调试口 + Reset 接口） | 待定 |

**阶段 2（正式版）的显示链路【用户 2026-09-29 定】：
所有芯片都在自打板上（含 RTD2660H），裸屏也固定在自打板上、用 FPC 软排线连接。**

```
RP2350B ──HSTX(TMDS)──> HDMI ──> RTD2660H（自打板上）──LVDS/TTL──> FPC ──> 裸屏
```

⇒ **自打板要自己设计显示这一整块**：RTD2660H + 它的固件 SPI flash + 背光驱动 + FPC 座。
⇒ 因此 **RTD2660H 的 3.3V/317 mA 与 1.8V/578 mA 必须进电源预算**
（见 `小本本.md` 的硬件章节；我 2026-09-29 曾记错成"不用"，已改正）。
**HDMI 不能省。**

备选（未决定，见 `小本本.md`）：RTD2660H 还有 **8-bit ITU-R BT.656 数字视频输入**
（不需要 TMDS，Core1 可解放，但受 SD 制式限制）和 **外部 MCU 控制接口**
（可省掉它的固件 flash，但寄存器手册不公开、风险高）。
模拟输入（VGA/AV/分量）**本方案排除**：RP2350 没有 DAC。

### A.3 副核方案（RP2040 经 SPI）

【用户定】**如果出现"设计到无法兼容"的冲突**，可以考虑加一颗 **RP2040 当副核**，
与 RP2350B 走 **SPI** 通信。**同一块 PCB 上，SPI 可以不分频、直接跑主频。**

【我提议】**动手前必须算清两件事，否则会踩坑：**

**① SPI 是「1 位 / 时钟」，带宽由双方中慢的那一方决定。**

| 要送什么 | 需要带宽 | SPI 够不够？ |
|---|---|---|
| **控制平面**（网络协议栈、按键、状态、音频小包） | 几十 KB/s ~ 几 MB/s | ✅ **绰绰有余** |
| **数据平面：整帧视频**（640×480 @60Hz，8bpp） | **18.4 MB/s ≈ 147 Mbit/s** | ⚠️ **吃紧**：需要 ≥150 MHz SCK 且零协议开销 |

⇒ **结论**：副核适合跑 **"控制平面 + 独立外设"**
（射频协议栈、音频合成、按键/传感器）；
**不适合直接送视频整帧**（除非只送变化区域、或压得更狠、或上四线 SPI）。

> ⚠️ **表里的数字是按纸面算的，不是实测。** 定方案时必须实测，

**📌 2026-09-29 补充（已查 SDK 源码）：SPI 链路的上限是 `clk_peri / 2`。**
（`spi.c`：`prescale` 最小 2、`postdiv` 最小 1。）
副核 RP2040 侧 `clk_peri` 最高 133 MHz ⇒ **SPI ≤ 66.5 MHz ⇒ ≈ 8.3 MB/s**。
⇒ **控制平面绰绰有余；数据平面（视频）差得远** —— 与上面那条结论一致。
**后路**：用 **PIO 并行链路**（8 位 + 时钟）可到几十 MB/s，**引脚要提前留出来**。
> 并且要查清**副核那颗芯片**（RP2040 主频 133 MHz）自己的 SPI 上限
> —— 链路速率由**慢的那一方**决定。

**② 副核会引入跨芯片同步问题**（画面撕裂、缓冲延迟、复位时序），
所以它是**"冲突到无法兼容"时的出路，不是首选。**
