## §9 应用 ABI（用户 2026-09-29 开始设计）

### 9.1 用户给的分类（三条轴）

| 轴 | 分法 |
|---|---|
| **通用性** | **C 函数**（啥语言都能调） / **C++ 函数** |
| **权限** | **一般** / **后台** / **特权** |
| **类型** | ① **command**（printf / cout / cin、字号 / 字色 / 背景色 / 字体）② 权限相关 ③ 显示相关 ④ 网络 / 蓝牙相关 ⑤ 音频相关 ⑥ 其他 ⑦ **调试（2026-09-29 新增）** |

### 9.2 ⭐ 关键结构认识：三条轴对应【三种完全不同的机制】

| 轴 | 实现上它是什么 | 什么时候决定 |
|---|---|---|
| **类型** | **调用号分段**（编号） | 编译期固定 |
| **权限** | **内核运行期校验** | 每次调用 |
| **通用性** | **语言绑定**（头文件 / 内联包装） | 编译期，**不产生新 ABI** |

⇒ **三条轴正交，可自由组合。** 例：

| 函数 | 通用性 | 权限 | 类型 |
|---|---|---|---|
| `sys_console_printf` | C | 一般 | command |
| `Screen::text()` | C++（**包同一个调用号**） | 一般 | 显示 |
| `sys_net_send` | C | **后台** | 网络 |
| `sys_mem_claim` | C | **特权** | 权限 |

### 9.3 调用号分段表

| 段 | 类型 | 说明 |
|---|---|---|
| `0x000–0x0FF` | **内核保留** | 应用不许使用 |
| `0x100–0x1FF` | **command**（文本 / 控制台 / 字体 / 颜色） | |
| `0x200–0x2FF` | **权限相关** | 大部分是特权 |
| `0x300–0x3FF` | **显示** | |
| `0x400–0x4FF` | **网络 / 蓝牙** | 多数要后台权限 |
| `0x500–0x5FF` | **音频** | |
| `0x600–0x6FF` | **其他** | |
| `0x700–0x7FF` | **调试（新增）** | ⚠️ **最低权限 = 特权** —— 否则任何应用都能读内核内存 |

**每个调用号再带一个「最低权限等级」**：`一般 < 后台 < 特权`。
⇒ **权限是"调用号的一个属性"**，不是函数名的一部分。

### 9.4 ⭐ 调用 ABI（**这里需要你拍板一处**）

用户原话：**"应用函数就是按着 4 字节对齐一个个摆在这里…`void sys_call_func ()=0x0001;`"**

**这句话有两种读法，差别很大：**

| 读法 | 内核怎么知道是几号调用 | 判定 |
|---|---|---|
| **A. 写入的【地址】= 调用号** | 读 **`SCB->MMFAR`** 就行 | ✅ **一行代码** |
| B. 写入的【值】= 调用号 | 必须**反汇编出错的那条 store 指令**，才知道写进了哪个寄存器 | ❌ 麻烦且脆 |

⇒ **强烈建议 A**（也和你说的"按 4 字节对齐一个个摆"完全吻合）：
**槽位的地址就是调用号。**

**推荐 ABI：**

```
r0–r3      = 参数（超过 4 个 ⇒ 传一个指向参数块的指针）
写入地址    = 系统页基址 + 调用号 × 4     ← 内核读 MMFAR 得到调用号
r0（写回异常帧）= 返回值
```

**⚠️ 两个必须做对的细节：**

1. **必须把异常帧里的 PC 往前推进**（跳过那条 store 指令），
   否则从异常返回后会**永远重复触发**。
2. **返回值要写回异常帧的 r0**，应用才拿得到。

### 9.5 ⭐ 每次调用 = 一次异常 ⇒ API 必须鼓励「批量」

> **一次系统调用 = 一次 MemManage 异常 ≈ 几百个周期。**

⇒ **绝不能让 API 变成"一个字符一次调用"** —— 画一句话几百次异常，必卡。

**所以 command / 显示类 API 应该做成【命令缓冲】：**

```
应用侧：往自己的命令缓冲里追加命令（纯内存写，不进内核）
        ↓ 攒一批
一次系统调用提交整条命令缓冲
内核侧：校验权限（一次）→ 逐条执行
```

**这正好和 PPL 是同一个思路**（PPL 本身就是"跨度的命令流"）。

**而且格式化（`%d` 之类）留在应用侧做** ——
**内核不该做格式化**：内核越薄越好，而且格式串解析本身是个攻击面。

### 9.6 权限模型的三个等级

| 等级 | 谁可以调 | 例子 |
|---|---|---|
| **一般** | 任何应用 | 画自己的窗口、读时钟 |
| **后台** | **持有「后台令牌」的应用** | 网络收发、定时唤醒 |
| **特权** | **只有内核 / 系统应用** | 认领外设、改内存保护、安装应用 |

**"后台"要定义清楚：**

- 应用在**安装时声明**需要后台能力 ⇒ 用户/系统授予 ⇒ 内核记一个令牌；
- **重要规则**：**后台应用不许往"可见屏幕"画** ——
  它的显示调用被限制在**自己的离屏表面**。
  ⇒ **否则后台应用会抢前台画面，"单前台多后台"就不成立。**

**被拒绝的调用必须记下来**（调用号 + 次数），
否则"我的应用为什么不工作"没法查。
（现有代码已有 `g_sys_denied` / `g_sys_last_no`，方向是对的。）

### 9.7 C++ 层：只做包装，不许有自己的 ABI

- **纯头文件 + 内联**，编译后落到的还是**同一批调用号**；
- 提供 `Screen` / `Console` / `Net` / `Audio` / `Perm` 等类；
- ⚠️ **不要上完整 iostream**（太重）：做成**轻量 `operator<<`** ——
  先格式化进缓冲区，**再一次性提交**；
- ⚠️ **别混淆两套 stdio**：
  | 用途 | 出口 |
  |---|---|
  | **调试** | 串口 / USB CDC（`printf` 到电脑） |
  | **应用** | **屏幕**（画字） |
  **这两者不能是同一个入口**，否则应用一 `printf` 就往串口喷。

### 9.9 ⭐ C / C++ 标准库封装（用户 2026-09-29 要求：方便上手）

> **用户要求**：应用端接口做成 **"C/C++ 标准库封装格式 + 剩余函数"**，方便上手。

**做法：提供 newlib 的 syscall 桩（stub），把标准库接到这套 API 上。**

| 标准库入口 | 桩函数 | 接到哪 |
|---|---|---|
| `printf` / `puts` / `putchar` | **`_write`** | **屏幕控制台**（不是串口！） |
| `getchar` / `scanf` / `cin` | **`_read`** | 输入（按键 / 触摸） |
| `malloc` / `free` / `new` | **`_sbrk`** | **应用自己的堆区域** |
| `fopen` / `fread` | `_open` / `_read` / `_lseek` | **SD 卡文件系统** |

⇒ **这样标准 C/C++ 代码可以原样跑** —— 这就是"方便上手"的最短路径。

#### ⭐ 它顺手解决了"必须批量"这个要求

> **stdio 必须开【全缓冲】（`setvbuf(_IOFBF)`）。**
> 开全缓冲之后，**一次 `printf` 一整行 = 攒够了一批 = 一次系统调用** ✓

⇒ 前面 §9.5 那个"绝不能让 API 变成一个字符一次调用"的难题，
**靠标准 stdio 的缓冲机制自动满足了。** 两件事不冲突，反而互补。

#### ⚠️ `malloc` 这一条同时就是越权保护

- `_sbrk` 只能在这个应用**自己的 MPU 区域**里增长；
- **涨出区域就返回失败**（`(void*)-1`），而不是让堆撞进内核或别的应用。
- ⇒ 这也是 §2"每个应用 1 个区域（代码+数据+栈）"那条的实际落点。

#### C++ 侧的包装

- 提供轻量 **`Console` / `Screen` / `Net` / `Audio` / `Perm` / `Debug`** 类；
- `cout` / `cin` 用**轻量流包装**（不要完整 iostream），内部同样走缓冲 + 批提交；
- **"剩余函数"（本系统特有、标准库里没有的）用同样的命名风格和头文件风格**，
  让标准 API 和自有 API 看起来是一家的。

### 9.10 调试函数（新增类型 ⑦）

| 段 | `0x700–0x7FF` |
|---|---|
| **最低权限** | ⚠️ **特权** —— 调试能读内核内存、能改探针，绝不能对普通应用开放 |
| **典型调用** | 写探针变量、取 `kernel_mark` 阶段号、取各模块 `g_<mod>_selftest_*`、强制某条路径、开关优化（例如"强制整块回灌"那个调试开关） |

**它其实是规范 5「状态上报统一格式」的【编程接口版】。**
- 规矩不变：`g_<mod>_selftest_{status, steps, fail_at}`；
- 调试 API 让**应用/工具**能读这些值，而不必每次都挂 SWD。

## §9B 插件系统（用户 2026-09-29 提出）

> **用户原话要点**：
> "插件"可以是**字库、输入法、存储库**等等这种东西，**接入后可以提供一些调用入口，走系统转接**。
> 所以系统实际上得维护一个**调用表**。
> 应用理应可以**要求系统接入必须插件** ——
> 换句话说，**应用启动时系统必须接入它要求的插件**。

### 9B.0 插件的目的与决策（用户 2026-09-29 澄清）

> **【用户定】做插件就是为了三件事：**
> **① 复用 ② 切软件不用重加载 ③ 省内存。**
> **"你打游戏的时候不必为键盘留 PSRAM"** ——
> **它相当于系统的可加载模块。当然从 PSRAM 装。**
> **【用户定】插件是系统预安装的，应用无权变更。**

#### ⭐ 三个目的推出的硬要求：生命周期 = 【引用计数】

| 目的 | 对设计的要求 |
|---|---|
| **① 复用** | 插件**只有一份**，多个应用共享 |
| **② 切软件不用重加载** | **插件驻留**，**不跟应用一起卸载** |
| **③ 省内存** | **引用计数归零 ⇒ 卸载**；不需要的应用不加载它 |

> ⇒ **插件的生命周期由「引用计数」决定，不是「跟应用同生共死」。**

**这直接把 §9B.7 那条精确化了：**

| 声明 | 准确含义 |
|---|---|
| `requires` | **保证它在驻留集里（引用计数 +1）**；应用退出**不减到卸载**，只要还有别人在用 |
| `optional` | ⚠️ **已经在驻留集里就用；【不主动加载】** —— 否则就违背了"省内存" |

> ⚠️ 如果 `optional` 会触发加载，那"打游戏不必为键盘留 PSRAM"就落不了地。

#### ✅ "系统预装 + 应用无权变更"消掉了一大堆麻烦

| 原本的问题 | 现在 |
|---|---|
| 插件从哪装、要不要签名 | ✅ **不需要** —— 随系统镜像一起 |
| 谁授权插件权限 | ✅ **不需要应用授权流程** —— 系统预装即受信 |
| **第三方恶意输入法**（我上一轮提的安全顾虑） | ✅ **从根上消失** |
| 缺插件怎么办 | ⚠️ 从"运行期常见"变成**构建期问题** ⇒ 依赖检查大部分可以在**构建/装机时**做完 |
| ABI 版本匹配 | 退化成**系统版本检查** |

#### ⚠️ 但插件有两种形态，不该混为一谈

| 形态 | 例子 | "加载"是什么意思 |
|---|---|---|
| **① 纯数据插件** | **字库**（字形位图）、主题、词库 | **只要注册一个描述符**（在哪 / 多大 / 什么格式）；<br>**系统用自己的代码去读它** ⇒ **不需要映射、不需要重定位** |
| **② 代码插件** | **输入法**、**存储库驱动** | 需要真正**加载代码**（映射 / 拷贝 / 重定位） |

> ⇒ **纯数据插件更省、更快、更安全（数据不会被执行）。**
> **字库应该做成①**，输入法和存储库是②。

#### ⚠️ 一个技术警告：从 PSRAM **执行代码**有代价

- PSRAM 在 **QMI** 上，取指要过缓存，而且**会和底图流 / 资源读抢同一条总线**（§2b 算过）；
- 还会**冲刷指令缓存**（§2b 也提过）。

**三个选择：**

| 做法 | 代价 |
|---|---|
| **代码在 Flash（XIP）**，数据在 PSRAM | ✅ 和"大部分代码放 Flash"一致；**推荐** |
| 代码拷进 **SRAM** 执行 | 快，但 SRAM 很贵（阶段2 帧缓冲就占 300 KB） |
| 代码**直接在 PSRAM 执行** | ⚠️ 抢总线 + 冲刷指令缓存；热路径别放这儿 |

> **建议：代码随系统镜像放 Flash（XIP 执行），插件的【数据】（字形、词库）放 PSRAM 按需加载。**
> 这样"省内存"省的是数据 —— 而**数据本来才是大头**。
> ⚠️ 若坚持让代码也在 PSRAM 里跑，必须接受上面那两条代价，并且**不能把热路径放进去**。

### 9B.1 ⚠️ 先说一个必须先解决的冲突：系统页装不下

我之前排的调用号段表是：

| 段 | 类型 |
|---|---|
| `0x000–0x0FF` | 内核保留 |
| `0x100–0x1FF` | command |
| `0x200–0x2FF` | 权限 |
| `0x300–0x3FF` | 显示 |
| `0x400–0x4FF` | 网络/蓝牙 |
| `0x500–0x5FF` | 音频 |
| `0x600–0x6FF` | 其他 |
| `0x700–0x7FF` | 调试 |

**`0x000–0x7FF` = 2048 个槽 × 4 字节 = 8 KB。**
而现有计划里系统页是 **4 KB（1024 槽）** ⇒ **已经装不下了。**

**⇒ 而且如果让插件再占槽位，系统页还得继续变大。**

### 9B.1b 插件内存策略（用户 2026-09-29 定）

> **【用户定】插件预留一块内存，做【惰性卸载】机制，【引用计数】做强行保留机制。**
> **【用户定】针对内存碎片化：插件【定大小】（比方 16 KB），
> 剩下空间分给"不重要、短生命"的变量。**
> **【用户定】插件的资源（图像、音频等）走【统一的系统托管路径】。**

#### 两级策略（用户提的，很干净）

| 机制 | 作用 |
|---|---|
| **引用计数** | **强行保留** —— 计数 > 0 ⇒ **必须留**（这是硬信号） |
| **惰性卸载** | 计数归零 ⇒ **只是"可以回收"**，**不急着走**；<br>**等真的缺内存了再收** |

⇒ 效果：**切软件时插件不重加载（省时间），内存紧了又能腾出来（省内存）** ——
**两个目的同时满足**。这就是把插件当成一种**缓存**来管。

#### ⭐ 定长块顺手解掉碎片问题

> **碎片只在"需要精细回收"的地方才有害；可以【整块丢弃】的区域不怕碎片。**

| 区域 | 分配方式 | 为什么不怕碎片 |
|---|---|---|
| **插件池** | **定长块**（例 **16 KB** 一块，N 块） | **每块一样大 ⇒ 天然没有碎片**（就是 slab / 定长池） |
| **临时区** | 剩下的空间，给**短命 / 不重要**的变量 | **可以整块作废**（reset 一次全丢）⇒ 碎片无所谓 |

**和现有分配器的关系**：`16 KB = 2^14` 正好是**二叉伙伴分配器的一个阶**
⇒ 插件块可以直接从 `kmem` 拿同一阶的块，**不会产生跨阶碎片** ✓

⚠️ 一个要考虑的点：**短命变量若图快，应该落在 SRAM；若图大，落 PSRAM。**
但**"整块作废"这个机制两边通用**。

#### ✅ 笔误更正：插件代码放 **Flash** 更好（定案）

| 放什么 | 放哪 |
|---|---|
| **插件代码** | ✅ **Flash（XIP 执行）** —— 用户更正：之前说"从 PSRAM 装"是笔误 |
| **插件数据 / 工作区** | **PSRAM**，按上面的**定长块**分配 |

⇒ 和 §2b"大部分代码放 Flash"一致 ✓

#### ⭐ 16 KB 缓存可分 —— 分配原则很明确

用户指出：**那 16 KB 的 XIP 缓存是 Flash / PSRAM 可分的。**

**分配原则：把缓存主要给 Flash（代码），PSRAM 那边给很少甚至不给。**

理由：

> **底图流是【一次性的顺序读】—— 读过就不再读，缓存对它毫无用处，
> 反而会把这些行挤掉，把代码缓存冲掉。**

⇒ 缓存应该**留给"会被反复读"的东西**：**代码**（循环、热函数）；
**PSRAM 的流式数据不需要缓存**。

#### 插件资源走【统一系统托管路径】

- 插件的**图像 / 音频 / 字体**一律走**系统的资源路径**，不自己发明加载方式；
- 落到实现上就是 **`kres`**：**插件是 `kres` 的一类所有者**，
  它占的资源全部记在账上，卸载时按 `owner` 一次性回收（§9B.8）；
- 资源格式也统一（图像用 **PPL**，见 §C）。

### 9B.2 ✅ 解法就是你说的「走系统转接」

> **插件调用【不占系统页槽位】，只走一个固定的「插件转接」入口。**

```
系统页里固定一个槽：plugin_call（比如放在 0x600「其他」段）
应用调：plugin_call(plugin_id, entry_id, 参数…)
        ↓
内核查【调用表】把这次调用转接给对应插件的入口
```

**好处一次解决三件事：**

1. **系统页不用再变大** ⇒ 可以停在 **8 KB**（`0x000–0x7FF`）；
2. **插件数量不受槽位限制**；
3. **"调用表"落在内核侧**（不在 MPU 只读页里）⇒ 可以动态增删。

⇒ 这也正是你说的"**走系统转接**"的字面意思。✅

### 9B.3 内核侧的调用表

| 字段 | 含义 |
|---|---|
| `plugin_id` + `entry_id` | 插件与入口标识 |
| **handler** | 转接目标 |
| **owner** | **哪个插件注册的**（用于卸载时回收） |
| **min_privilege** | ⚠️ **由系统授，不由插件自称** |
| **abi_version** | 版本匹配（见 §9.4 的版本号那条） |

**⚠️ 硬规则：插件【不能】给自己的入口声明特权级。**
权限由**系统（内核 / 用户授权）**决定 ——
否则任何插件都能自称特权，整个权限模型就废了。

**这张表天然属于 `kres` 那一套**：插件就是**一类资源所有者**，
卸载时按 owner 回收它注册的全部入口。

### 9B.4 ⚠️ 一条 ABI 约束：参数不能跨地址空间传指针

插件如果是**独立进程**，那它和应用**不在同一个地址空间** ⇒
**应用传过去的指针在插件里毫无意义**。

⇒ **插件调用的参数必须【按值传递】，或者【由内核代拷】。**

**好消息：这和 §9.5 的「命令缓冲」天然契合** ——
应用提交的是**一块缓冲**（不是一堆指针），内核**把缓冲整块拷进插件**即可。

### 9B.5 两类插件（成本 / 隔离 / 权限完全不同）

| | **系统级插件** | **应用级插件** |
|---|---|---|
| 住在哪 | 系统进程 / 内核侧 | **装在应用自己的地址空间里** |
| 调用成本 | 一次转接（要代拷参数） | **直接函数调用，零开销** |
| 隔离 | ✅ 有 | ❌ 和应用同域（插件崩=应用崩） |
| 权限 | 可以高（要授权） | **只能跟宿主应用同级** |
| 适合 | **存储库 / 输入法 / 系统字库** | 应用自带的字库、自带的小工具 |

**用户举的三个例子落在哪：**

| 插件 | 建议 | 理由 |
|---|---|---|
| **字库** | **两边都要** | 系统字库给所有应用共用；应用也能自带私有字库 |
| **输入法** | **系统级 + 后台权限** | 它要跨应用工作 |
| **存储库** | **系统级 + 特权** | 要直接碰块设备 |

### 9B.6 ⚠️ 输入法有一个必须知道的安全含义

> **输入法能看到【所有】输入。**

⇒ 它是**天生高敏感**的组件：
- 必须**后台权限**（要在别的应用前台时工作）；
- 它的**显示调用**要能画候选词 ⇒ 这跟 §9.6"后台不许画可见屏幕"**冲突**，
  必须**开一个明确的例外**（例如"输入法被前台应用请求时，可以画在指定的候选区"）；
- **不能让任意第三方输入法随便装** —— 至少要用户明确授权。

### 9B.7 应用声明依赖 + 启动时接入

**应用清单里声明依赖：**

```
requires: [ font_cjk@1, ime_pinyin@2 ]     ← 必须有，缺了不让启动
optional: [ storage_exfat@1 ]              ← 有就用，没有就降级
```

**启动时的行为（用户要求）：**

1. 加载器**逐条解析**依赖；
2. **必需插件缺失 ⇒ 拒绝启动**，并**明确告诉用户缺哪个**（不能默默崩）；
3. 可选插件缺失 ⇒ 正常启动，那个入口解析成"**不可用桩**"，调用返回错误码；
4. **版本不匹配（ABI 版本）⇒ 也算缺失**。

> ⚠️ **副产品**：必需插件要**在应用第一次调用之前就加载完**
> ⇒ 增加启动延迟 + 占用内存（字库可以很大 ⇒ 放 PSRAM）。

### 9B.8 卸载与回收

**插件被卸载时：**

- 它的入口**必须变成"插件已走"的桩**，立刻返回错误 ——
  ⚠️ **绝不能变成野指针**（否则应用下一次调用直接崩）；
- 通知所有依赖它的应用（或直接杀掉它们）；
- 按 **owner = 该插件** 回收它在 `kres` 里认领的资源。

### 9B.9 待用户拍板

1. **插件是独立进程，还是装进宿主应用的地址空间？**
   （我建议：**存储库/输入法 = 独立进程；字库 = 两种都支持**）
2. **插件从哪装** —— 跟应用一样从 SD 装？
3. **谁授权插件的权限** —— 用户确认，还是只信系统签名？

## 系统调用机制设计（内存越权触发）

> 本文是整个项目的**地基**：代码可以重写，这套机制定了就很难改；凡涉及具体地址、寄存器、API 的地方都经过核实。
> 本文件只保留**架构决策**与**系统调用 ABI 约定**；实测数据在 `docs/实测数据.md`，
> 硬件决策在 `docs/硬件设计.md`，**当前状态在 `docs/当前状态.md`**。
> （"§9.4 / §9.5"指的是**本文件正文**的节号。）

### 一、要实现的机制（决策：用"写内存"而不是 `SVC` 指令）

应用代码**不能直接调用内核函数**，而是通过**访问一块它没有权限的内存**来请求服务：

```
应用写系统页 → MPU 判其不可访问 → MemManage 异常 → 内核确认"合法请求"
            → 特权态代执行 → 修正返回地址，应用从下一条指令继续
```

| | 写内存（本设计） | `SVC` 指令（传统做法） |
|---|---|---|
| 触发指令 | `STR` — **单条 16/32 位指令** | `SVC #imm` |
| 跳过故障指令 | 读指令长度 +2 或 +4 | 固定 +2 |
| 需要反汇编吗 | 不需要（`STR` 编码简单） | 不需要 |
| 编译器参与 | 无（普通指针写入） | 需要内联汇编 |

**关键优势**：`STR` 是单条指令，内核只需把保存的 PC 加 2 或 4 就能干净返回；**不需要碰指令反汇编**，也不怕编译器生成跨页的 `LDM/STM`。

### 二、硬件事实（已核实）

```
XIP_BASE   0x10000000    flash 执行区
PSRAM      0x11000000    QMI CS1（8MB，实为 XIP CS1）
SRAM_BASE  0x20000000    SRAM（RP2350B 共 520KB）
```

| 约束 | 数值 / 影响 |
|---|---|
| MPU 区域总数 | **8 个** —— 极其紧张，必须精打细算 |
| 特权级 / 栈 / 异常 | Cortex-M33 特权 / 非特权两态（**应用跑非特权态**，用 PSP）；MemManage 异常默认优先级可配 |

（SDK 自带 CMSIS，ARMv8-M 风格 MPU API 可用：`ARM_MPU_SetRegion(rnr, rbar, rlar)` 设区域、`ARM_MPU_Enable(ctrl)` 启用。）

### 三、内存布局设计（草案）

```
SRAM 0x20000000
  ├─ 内核代码 + 数据（特权可读写执行）   ← MPU region 0
  ├─ 内核栈（MSP）                       ← MPU region 1
  ├─ ★ 系统调用页（应用可写，内核读）    ← MPU region 2
  │    0x2004_0000 ~ 0x2004_0FFF (4KB)
  ├─ 应用 A 代码 + 数据 + 栈             ← MPU region 3
  ├─ 应用 B 代码 + 数据 + 栈             ← MPU region 4
  └─ …（最多再挤几个应用）
```

> ⚠️ **`0x2004_0000` 是草案示意值，不是事实。** `.syspage` 由链接器放进自定义段
> （`__attribute__((section(".syspage"), aligned(4096)))`），实际地址**以链接结果为准**。
> 实测期望的出错地址是 **`0x20006000`**（见 `src/kernel.h` 自检读法）。
> ⇒ 写代码**不要引用本节这两个数字**，用符号 `g_sys_page` 取基址。
> （2026-10-01 补：同一事实两处不同值且互不声明，正是规范 1 要防的。）

**区域预算（决策）**：8 个总配额 = 内核代码/数据 1 + 内核栈 1 + 系统调用页 1 + **每个应用 1**（代码+数据+栈合并成一段连续区域）
⇒ **剩余 5 个 → 最多 5 个应用。这是硬上限**；要更多应用，就得改成"应用按需换入换出 MPU 配置"。

### 四、系统调用页协议（ABI 约定）

系统页 4KB，按 4 字节对齐划分：**地址本身编码了调用号**（省一次读取），参数放在系统页固定偏移的参数块里。

```
系统页基址 + 0x00  ← 调用号 0：获取系统版本
系统页基址 + 0x04  ← 调用号 1：申请内存（参数在固定偏移）
系统页基址 + 0x08  ← 调用号 2：打开文件
...
```

**应用侧形态**（`syscall_params` 结构 + 应用看到的调用写法）：

```c
struct syscall_params {
    uint32_t arg0;
    uint32_t arg1;
    uint32_t arg2;
    uint32_t result;   // 内核回填
};

// 头文件里定义，应用直接调用
static inline int syscall_open(const char *path) {
    SYSCALL_PARAMS->arg0 = (uint32_t)path;
    // 下面这句触发异常，返回值由内核填好
    *(volatile uint32_t *)SYSCALL_PAGE_OPEN = 0;
    return (int)SYSCALL_PARAMS->result;
}
```

**内核侧流程**：

```
MemManage_Handler:
  1 读 MMFAR（出错地址寄存器）       2 确认地址落在系统页内 → 否则是真错误，杀掉应用
  3 从地址算出调用号                 4 读参数块
  5 特权态执行操作                   6 结果写回参数块
  7 从异常栈帧取出 PC                8 读该地址的指令，判断 16 位还是 32 位
  9 PC += 2 或 4                    10 返回
```

**第 8 步是唯一需要读指令的地方**，而且只判长度、不解码内容 —— 这是本设计最省事的关键。

### 五、要先验证的命门（单核裸机即可）

```
[ ] 1 配置 MPU：系统页"非特权可写、内核可读"  [ ] 2 测试函数跑非特权态（CONTROL.nPRIV=1）
[ ] 3 测试函数往系统页写一个数               [ ] 4 MemManage 异常被触发
[ ] 5 异常里读 MMFAR，确认识别正确            [ ] 6 内核代执行一个简单操作（比如 printf）
[ ] 7 正确跳过故障指令，应用继续往下跑        [ ] 8 应用**碰内核内存时**是"真报错"（不只是系统页）
```

**这 8 条全过，整个架构才成立**；一条不过，就要改设计。

### 六、待定问题

- 应用代码放 flash（XIP）还是 SRAM？—— 影响 MPU 区域划分和性能
- 应用能执行内核代码吗？—— 决定 MPU 是否要设 XN（不可执行）位；双核怎么分？—— 影响调度器设计
- 系统页只有 4KB —— 4KB / 4 = **1024 个调用号**，够用
- 异常里能不能调 printf？—— 不能直接调，要延迟到任务上下文
- 另有 4 条架构决策待用户拍板（射频形态、帧缓冲放 SRAM 还是 PSRAM、两级特权模型、应用 ABI 约定）
  —— ⚠️ **这 4 条的现状已变**：射频**已澄清**、帧缓冲**已定 SRAM**；
  **当前完整的待拍板清单在 `docs/需求.md` §六**（别处不再维护这一份）。
### 七、与 RTOS 的关系（决策）

**不用现成 RTOS。** 理由：本设计的核心（MemManage 里改 PC 实现系统调用）需要在**任务切换的那一刻**配置 MPU；
用现成 RTOS 就得改它的移植层才能挂进去，而 RP2350 的官方 FreeRTOS 移植**强制关闭 MPU**（`configENABLE_MPU 0`），改起来比自己写还费劲。
> 〔**2026-10-05 核验并补出处**：拉 `raspberrypi/FreeRTOS-Kernel` 实测 —— `portable/ThirdParty/GCC/RP2350_ARM_NTZ/README.md:42` 写 `#define configENABLE_MPU 0`，`:67` 原文 **There is no support for enabling MPU for user/handler mode within FreeRTOS** ⇒ **该结论截至今日仍成立** ✓（复验：`git clone --depth 1 --filter=blob:none --no-checkout https://github.com/raspberrypi/FreeRTOS-Kernel`，再读该 README）〕
> 〔**但更本质的理由**：`configENABLE_MPU 0` 的 FreeRTOS 里**任务默认是特权态** ✗ ⇒ 应用可以直接关掉 MPU ⇒ **无法安全承载不可信应用** ✗ —— 这才是「主核必须自研」的根本原因 ✓，比「官方 config 被强制为 0」更硬。〕
> 〔**另**：同一移植的 `port.c` 里有 **58 处 `#if ( configENABLE_MPU == 1 )`** 门控（继承自上游 ARMv8-M 的 CM33 移植）⇒ 障碍是「**该移植不维护这条路**」，而非「FreeRTOS 做不到」。〕
**代价**：调度器要自己写（任务切换约 200-300 行）。**收益**：隔离层天然在手里，每一行都可控。
