## §C 图像资源格式：PPL（用户 2026-09-29 提出）

> **【用户定】名字**：`PPL` = **Picture PreLoad**（用户自创）。
> **【用户定】基本形态**：按固定分辨率（480×320）组织的一串像素 + **使用说明**：
> "画多少像素、跳过多少像素、再画多少像素……" 外加位深、长宽等基本信息。

### C.1 它在图形学里的名字，以及为什么它是对的

用户描述的东西有现成的学名：**跨度列表（span list）+ 行程编码（RLE）**。
（想查资料就用 "span list" / "RLE sprite" 这两个词。）

**关键点：它正好是"CPU 配置的 DMA 写/跳链"能直接消费的格式。**
也就是说 —— **资源格式和渲染器是一起设计的**，这正是它最大的价值：

| 好处 | 说明 |
|---|---|
| **零解码** | 数据本身就是 DMA 的目的格式，CPU 几乎不参与 ⇒ 才追得上光栅 |
| **跳过 = 透明** | 天然支持"叠加到已有画面" |
| **只存要画的像素** | 小图标 + 大片透明 ⇒ 表情包体积可以极小 |
| **实现简单** | 不需要 zlib / Huffman，几百行就能读写 |

### C.2 与 JPG / PNG 的分工（**不是竞争，是分工**）

| 用途 | 建议格式 | 理由 |
|---|---|---|
| **表情包 / 图标 / UI 元素** | **PPL** | 小、带跳过（透明）、**能直接喂 DMA** |
| **照片 / 壁纸** | **JPG** | 压缩比最高；但 **无 alpha、有损** |
| 带透明的无损大图 | PNG | 有 alpha；但**解码要 ~32KB zlib 窗口 + CPU** |

**可行性核对（RP2350B，我查过）：**

- **PNG 可行**：DEFLATE 需要 32 KB 窗口 + 上一行缓冲（480×2B = 960 B）。
  PNG 的行滤波**只引用上一行** ⇒ 可以**逐行解码**直接喂帧缓冲。128 KB 竞技场装得下。
- **JPG 可行**：baseline 顺序式，按 MCU 行（8/16 行）输出，工作区约 10~20 KB。
  RP2350 的 Cortex-M33 **有 FPU**（实测 DVI 跑完 `CONTROL` 的 FPCA/SFPA 是置起来的）
  ⇒ IDCT 不慢。
- ⚠️ **两者都不适合动画**（CPU 开销大）。**动画和表情包走 PPL。**

### C.4 跨行语义（用户 2026-09-29 问，已定）

**结论：允许跨行。而且这是对的 —— 因为跨度定义在【目标缓冲区的线性地址】上，不是"行内坐标"。**

```
一个跨度 = "往前跳过 N 个像素（不动），然后把后面 M 个像素连续写进去"
```

这句话里**没有"行"的概念**。渲染器就是纯粹线性的：按线性地址跳、按线性地址写。
⇒ **跨行对渲染器完全免费** —— 它压根不需要把跨度拆开。

#### 但编码器必须遵守一条规则

> **只有当"图像宽度 == 帧缓冲 stride"时，才可以让跨度跨行。**

否则会写错位置：

| 情况 | skip 的值 | 能不能跨行 |
|---|---|---|
| **满宽图**（图宽 == stride，例：480 宽画到 480 宽的缓冲） | **0**（下一行紧接着上一行，地址连续） | ✅ 能 —— 整张图可以**合并成一个跨度** |
| **窄精灵**（图宽 < stride，例：64 宽的图标放在 480 宽的缓冲里） | **`stride − 宽度`**（+ 左右偏移差） | ❌ 不能 —— 跨过去会写到下一行**错误的 x** |

⇒ **"填满一行必须跳过 0 个"这个理解要修正为**：
**skip 的值由 `stride − 本行要画的宽度` 决定**；满宽图恰好为 0，窄精灵就是那个差值。

#### 由此得到的两条实用结论

1. **满宽不透明图（壁纸）**在 PPL 里可以**只用一个跨度**（省掉 320 条行头记录）。
2. **渲染器实现极其简单**：不需要行状态机，只要
   `目标地址 += skip；搬 M 个像素；目标地址 += M`。

### C.6 怎么用 DMA 实现（2026-09-29）

#### 第一句话：**"跳过"在 DMA 层面根本不存在**

跳过不是一种 DMA 操作 —— 它只是**把下一个跨度的写地址往后挪**。
所以整个 PPL 渲染归结为一件事：

> **按顺序，为每一段跨度配置"源地址 / 写地址 / 长度"三样东西。**

#### 用"控制通道 + 数据通道"的链式结构

这个套路**本项目已经跑通过**（DVI 引擎就是同一套机制），所以不是纸上方案：

```
跨度控制块数组（SRAM，每块 4 个 32 位字）
        │  顺序读
        ▼
   控制通道 ──每次搬 4 个字，写进──> 数据通道的 4 个寄存器
                                        │
                                        ▼
                                    数据通道：从 PPL 像素流读 M 个像素
                                              → 写到帧缓冲的线性地址
                                        完成 → CHAIN_TO 触发控制通道 → 装下一段
```

**一个跨度控制块 = 4 个 32 位字**（和 DVI 库里 `dma_cb_t` 布局一样）：

| 字段 | 含义 |
|---|---|
| `read_addr` | PPL 像素流里**这一段**的起始地址 |
| `write_addr` | **帧缓冲基址 + 该跨度的线性偏移**（跳过就体现在这里） |
| `transfer_count` | **M = 这一段要写几个像素** |
| `ctrl` | `INCR_READ｜INCR_WRITE｜SIZE_8｜DREQ_FORCE｜CHAIN_TO=控制通道` |

**关键细节：**

1. **数据通道的 DREQ 必须设成 `DREQ_FORCE`** —— 内存到内存搬运不吃外设触发，
   不设它通道会一直等一个永远不来的 DREQ。
2. **控制通道的"写"要回卷**：它每次写 4 个字到数据通道的 4 个寄存器，
   所以写地址要在 **16 字节窗口内回卷**：
   `channel_config_set_ring(&cfg, true, 4)` —— 写侧环形，读侧线性前进。
   （这正是 DVI 库的做法，已验证可行。）
3. **启动**：控制通道指到控制块数组第 0 块 → 启动 → 之后整条链自动跑完。

#### 传输宽度怎么选（**这里有个真陷阱**）

| 方案 | 能表达的 M | 代价 |
|---|---|---|
| **8 位**（`DMA_SIZE_8`） | **任意 M**（1 像素也行） | 每个像素占一次总线事务 |
| 32 位 | **M 必须是 4 的倍数** | 总线事务少 4 倍 |

⇒ 若用 32 位，**1~3 像素宽的细线就没法搬**（要塞给 CPU）。
**建议：先统一用 8 位。** 粗算一下够不够快：写满整屏 150 KB，
252 MHz 下大约 **不到 1 ms** —— 完全够用。

#### "筛子"问题在 DMA 层面的**量化代价**

每段跨度都要先搬 **4 个字**的控制块，才能搬 M 个像素的数据：

| M | 控制开销 : 数据 | 说明 |
|---|---|---|
| M = 480（满宽） | 4 : 480 ≈ **0.8%** | 极划算 |
| M = 64（图标行） | 4 : 64 ≈ **6%** | 可以接受 |
| **M = 1（竖直细线）** | **4 : 1 = 400%** | ⚠️ 控制开销是数据的 **4 倍** |

⇒ 这就是"**别做成筛子**"的准确含义：**不是不能做，而是每多一个极短跨度，就要付 4 个字。**

#### 两个能大幅省事的优化

1. **控制块可以"一次生成、每帧只改一个字"。**
   同一个精灵反复画时，**每帧只需要改每个块的 `write_addr`**（加上新的 (x,y) 偏移），
   `read_addr` / `transfer_count` / `ctrl` 全不用动。**每帧成本 = 跨度数 次单字写入。**
   （DVI 库里 `dvi_update_scanline_data_dma()` 就是这么干的 —— 只改 `read_addr` 一个字。）
2. **静态 UI 根本不用改**：位置固定的元素，控制块建好就再也不用碰。

#### 三条必须守的

1. **控制块池要有上限**：跨度数超过池容量就把一次 blit 拆成多次。
   （例：上限 256 跨度 × 16 字节 = **4 KB** SRAM。）
2. **必须裁剪**：跨度写到帧缓冲末尾会越界，编码器/渲染器都要保证不越界。
3. **优先级**：**扫描输出（DVI）的 DMA 优先级要高于 blitter**，
   否则搬运突发时会把扫描线饿死（本项目在 DVI 上已经吃过 FIFO 欠载的苦）。
   ⇒ blitter 用**普通优先级**，不要跟扫描输出抢。
### C.7 半区渲染（用户 2026-09-29 完整澄清 —— **已确认**）

> ⚠️ **这个设计当初没写进文档。** 2026-09-29 我在仓库里 `grep 半区` **一个字都没找到**，
> 只能凭对话重建 —— **文档失误**（指令本规则 22"定期维护所有文档"）。
> 本节是**用户澄清后的正式版**。

#### 设计（【用户定】原话要点）

- **屏幕分上下两半做渲染。**
- 有一张**底图（底板图）**：**480×320，常驻 PSRAM**。
- **正在被 HSTX 推送的那一半，同时被 DMA 从 PSRAM 压入底图**，
  并且**保证「压入速率 < 推送速率」**。
- **另一个半区交给应用渲染。**

#### 为什么"压入比推送慢"就能保证不撕裂

因为**写指针永远追不上读指针**：

```
HSTX 读指针  ──────────────▶   快（按视频时序固定）
DMA  写指针  ─────────▶        慢（故意压低）
             ↑ 永远落后 ⇒ 绝不会覆盖"还没被读走"的那一行
```

⇒ **这是由速率关系保证的，不是靠时间窗碰运气** —— 比"算准时间"稳得多。

#### 为什么非这么麻烦：SRAM 太小

| 方案 | 需要 SRAM | 结论 |
|---|---|---|
| 565 一帧（480×320×2B） | **300 KB** | 已经很贵 |
| **565 双缓冲** | **600 KB** | ❌ **不可能**（总共 520 KB） |
| **分半区（本方案）** | **一帧的量（两半合起来）** | ✅ **用"时间复用"换到等效双缓冲** |

⇒ **分半区 = 用"每帧两次原子提交"换掉"第二块帧缓冲"。这是它全部的价值。**

#### 带宽核算（验证可行性）

| 项 | 数字 |
|---|---|
| 底图每半区 | 480×160×2B = **150 KB** |
| 半帧时间（60Hz） | **≈ 8.3 ms** |
| ⇒ 压入所需平均带宽 | **≈ 18 MB/s** |
| PSRAM 四线 75 MHz 理论上限 | ≈ **37.5 MB/s** ⇒ 占一半，**可行** ✓ |
| 扫描期瞬时读速率 | ≈ **30 MB/s** ⇒ **"比推送慢"很容易满足** ✓ |

#### ⚠️ 三个必须解决的问题

**1. 压入必须有"提前量"，否则压不完。**
若压入从"本半区开始被扫描"时才启动，它**永远比扫描慢** ⇒ 只会越落越远 ⇒
**半区结束时底图还缺一块**。
⇒ 必须在**另一半被扫描的时候就开始压**（拿到半帧提前量），
进入本半区时它**落后但不缺**。

**2. 这条设计把 PSRAM 从"可选"变成"承重墙"。**
底图常驻 PSRAM，而**我们连 256 B 连续写都还没跑通**（`max_select` 假设未验证）。
⇒ **PSRAM 可靠性从"待办"升级为关键路径上的阻塞项。**

**3. 速率监视器**（用户的 DMA → PIO → IRQ 想法）在这里的正确定位是
**"追上了就刹车"的看门狗** ⇒ 见 C.8。

#### ✅ 已确认（用户 2026-09-29）

1. **两个半区都在 SRAM 里**（一帧的量 @565 = 300 KB）。
   **PSRAM 绝对不做帧缓冲** —— 理由见 `docs/文档与代码规范.md` **规范 2b**「总线带宽核算」。
2. 压入的对象确实是**"正在被推送的那一半"**。

### C.8 速率监视器（用户 2026-09-29 提的 DMA → PIO → 累加 → IRQ）

> **用户原话**："像素总数可以让一个专门 DMA 报给 PIO 做累加，超过之前触发 CPU irq 中断"

**定位**：它是 §C.7 那套速率设计的**看门狗** ——
一旦压入进度**追上光束**，立刻中断、让 CPU 刹车/调整。

**硬件能力核对：**

| 手段 | 能做"累加"吗 | 说明 |
|---|---|---|
| **PIO 直接累加** | ❌ **不行** | PIO 指令集只有 `JMP / WAIT / IN / OUT / PUSH / PULL / MOV / IRQ / SET` + 侧集 + 延时，**没有加法指令** |
| **PIO 倒计时** | ✅ 等效 | 把预算预装进 X，每来一个像素 `jmp x--`，归零时 `IRQ`。功能等价，但**每像素耗一个 PIO 周期** |
| **硬件插值器（interpolator）** | ✅ **真会加** | RP2350 有 **2 个**，`ACCUM0 += ACCUM1` ⇒ 可以做**真正的求和** |
| **定时器闹钟** | ✅ 最省 | 若只需要"到点提醒"，`add_alarm_in_us()` 直接给中断，**不占 DMA / PIO** |

> ⚠️ **建议：先别做硬件。**
> **软件记账**（每次 blit 累加像素数、超预算就推迟到下一个半区）**不占任何资源**，
> 足够先把这套速率设计验证通；等它被证明不够（比如需要**异步硬刹车**）再上硬件。
