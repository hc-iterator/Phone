### 14.7 ✅ 2026-10-01 深夜·已排除：DMA 列表本身完全正确

**手段**：gdb 直接打印结构体本体（`p dvi0.dma_list_active`），**不经我手解码**。

```
struct dvi_scanline_dma_list { dma_cb_t l0[6]; dma_cb_t l1[7]; dma_cb_t l2[7]; }
dma_cb_t = { read_addr, write_addr, transfer_count, ctrl }

l0: write_addr=0x50200010(TXF0)  ctrl=0x0080421B → TREQ_SEL=0 CHAIN_TO=2  ✅
l1: write_addr=0x50200014(TXF1)  ctrl=0x0082821B → TREQ_SEL=1 CHAIN_TO=4  ✅
l2: write_addr=0x50200018(TXF2)  ctrl=0x0084C21B → TREQ_SEL=2 CHAIN_TO=6  ✅
```

⇒ **每 lane 的目标 FIFO、DREQ、CHAIN_TO 全对。** 之前那套"整排错位一个 lane"是
**读活体寄存器时的假象**，不是硬件错。
（位域用 SDK 定义复核：`TREQ_SEL=(ctrl>>17)&0x3F`、`CHAIN_TO=(ctrl>>13)&0xF`。）

**每行搬运字数**（列表内容）：lane0 = 8+48+24+320+8+8 = **416 字**；
lane1/lane2 = 80×6+320 = **800 字**。（lane0 是同步 lane，tc 模式不同属正常。）

**⇒ 至此已排除**：sys_clk、PIO/PWM 分频、timing 模式、音频、TCR 等待、DMA 列表/DREQ。
**剩下的方向**：IRQ 里那句 `dvi_update_scanline_data_dma()`（有有效扫描线时每行重建 active 列表）
是不是耗时主因 —— 这是唯一还没量过的每行工作。

### 14.8 ⭐⭐ 2026-10-01 深夜·推论：瓶颈在 Core1（编码端）而不是 DMA/PIO【后被 14.9 翻案】

**已排除**（见 14.7 与本节）：
- `dvi_update_scanline_data_dma()`：last 0 µs / max 2 µs ⇒ 不是它
- IRQ 里那段 TCR 等待：last 502 µs / max 1854 µs ⇒ **它只是在"观察"慢，不是原因**
- 我加的"超时重排整条链"：`g_dvi_tcr_timeouts=0`、`tmo_lane=0xFFFFFFFF` ⇒ **一次都没跑，无辜**
- 总线争用：`frank_hdmi_init` **已经把 Core1 与 DMA 读写设为高总线优先级**

**⚠️ 一个被长期误用的数字**：`g_dvi_loop_frames` **不是显示帧率**。
Core0 的主循环是 `draw_test_pattern(); make_tone(); sleep_ms(16);` ⇒ 47/s 只是
"重画测试图 + 睡 16ms"的速率。**DVI 引擎整个跑在 Core1**（`multicore_launch_core1(frank_hdmi_run_core1)`）。

**★ 真正的引擎产出计数器**（此前从没读过）：`frank_hdmi_heartbeat_lines` / `_frames`
—— 在 `core1_main()` 的循环里每行自增。**6 秒实测**：

| 计数器 | 6 秒值 | 换算 | 应有 |
|---|---|---|---|
| `frank_hdmi_heartbeat_lines`（Core1 产出行数） | **1725** | **287 行/秒** | 31500 |
| `frank_hdmi_heartbeat_frames` | 7 | 0.6 fps | 60 |
| `g_dvi_irq_count`（引擎实际显示行数） | 3810 | 635 行/秒 | 31500 |
| `dvi0.dvi_frame_count` | 8 | 1.33 fps | 60 |

⇒ **Core1 每秒只吐 287 行**，引擎显示 635 行/秒（差的那部分在放"红色错误行"）。
⇒ **Core1 是瓶颈端。**

**每行 CPU 工作量**：`encode_one_scanline_16bpp()` 要调 3 次
`tmds_encode_data_channel_16bpp()`（**已确认在 RAM**，`frank_tmds.c:83` 带 `__not_in_flash_func`），
外加两次 `queue_remove_blocking`（其中 `q_tmds_free` 实测为空）。
⇒ 287 行/秒 ⇒ **每行约 3.5 ms**（应 ≲30 µs）。

**🔴 而根子上是个设计取舍**：库的注释写明它**假定 CPU 跑到 TMDS 位时钟的 2 倍**：

> "libdvi's TMDS serialiser SMs and PWM pixel clock are configured with
>  DVI_SM_CLKDIV=2 … Concretely: typical CPU clock is 504 MHz driving a 252 MHz TMDS link."

本项目跑 **252MHz + DVI_SM_CLKDIV=1** —— **位时钟是对的（252MHz），但 CPU 只有一半周期去做每行的 TMDS 编码**。
而当初选 252MHz 正是因为**实测 504MHz 会把这块板子跑挂**（Core1 进 HardFault、Core0 卡到连 SWD 都 halt 不住）。

⇒ **"稳定（252MHz）"与"编码吞吐（需 ~2×）"是一对矛盾**，这是 4.6 fps 的结构性原因。

**下一步（未做）**：量 `encode_one_scanline_16bpp` 内部三段（`q_colour_valid` 等待 /
3 次编码 / `q_tmds_free` 等待）各占多少 —— 判定是"算力不够"还是"被队列阻塞"。
若是算力 ⇒ 只能抬主频（并解决 504MHz 的稳定性）或降低编码量（半分辨率/灰度）。

### 14.9 ⭐⭐⭐ 2026-10-01 深夜·翻案：卡在"等空闲 TMDS 缓冲"【后被 14.24 推翻】

**实测 `encode_one_scanline_16bpp` 内部三段**（µs）：

| 段 | last | max | 占比 |
|---|---|---|---|
| 等 `q_colour_valid` | 0 | 2 | ~0% |
| **等 `q_tmds_free`** | **4341** | **103331** | **99.4%** |
| 纯 3 次 `tmds_encode_data_channel_16bpp` | **25** | 28 | 0.6% |
| （整行合计） | 4367 | 103357 | |

⇒ **编码只要 25 µs（行预算 31.7 µs，绰绰有余）。Core1 有 99.4% 时间在等空闲缓冲。**

**🔴 严重订正 14.8**：上一轮说"Core1 算力不够"**是错的**。Core1 是**受害者**：
它想产 31500 行/秒，却只能拿到 287 次缓冲。

**真正的瓶颈回到引擎行率**：TMDS 缓冲由**引擎的 DMA IRQ** 归还，而引擎只跑
**635 行/秒**（`g_dvi_irq_count`），所以缓冲回收速率就是 635/s。

⇒ 引擎每行周期 ≈ 1572 µs，其中几乎全是 **TCR 等待** ⇒ **数据通道搬 ~416 个字要 1572 µs
（3.8 µs/字），而按设计只需 79 ns/字 —— 慢 48 倍**。而 PIO FIFO 是空的（等数据）、
DMA 配置复核全对。

**⇒ 待查（下一轮）**：为什么 PIO 每字要 3.8 µs（设计 79 ns）？
候选：① SM 实际时钟远低于 252MHz；② DMA 对 DREQ 的响应被某种节流；
③ 通道在"完成 → CHAIN_TO → 控制通道重装填"之间丢了触发（但从 `tcr_timeouts=0` 看，最终是完成了的）。

**⚠️ 方法论教训（本次第 7 次）**：我在 14.8 里凭"287 行/秒"就断言"Core1 算力不够"，
**没有先量它内部各段**。⇒ **"慢"和"谁慢"是两件事，必须量到段级再下结论。**

### 14.10 🔴 2026-10-01 深夜·重要：跑着的 DVI 固件会把 SWD 调试口占死

**现象**（连续多次 halt/resume 采样时发生）：

```
Info : SWD DPIDR 0x4c013477          ← DP 层【能读】
Warn : Too long SWD WAIT, issuing DAPABORT
Error: Failed to read memory at 0xe000ed00    ← AHB-AP 过不去
Error: [rp2350.dap.core0] Examination failed
```

⇒ **DP 层正常、但内存/AP 访问全部 WAIT 超时** ⇒ **总线被占死，调试访问进不去。**

**试过的救援（都无效）**：
- `rp2350-rescue.cfg`（设救援位 → 清零 → 打印 `Now attach a debugger...`）⇒ 之后复查仍 `Examination failed`
- 普通 `reset halt`、`reset` ⇒ 同样失败

⇒ **只能【物理断电 / 按 RUN】才能恢复。**

**🔴 这条很可能是历史悬案的真相**：项目文档里长期写着"SWD 物理层断开、四种速率全
`cannot read IDR` ⇒ 怀疑接线/GND"。**但这次的证据指向另一个原因：跑着的固件把总线占死。**
⇒ 以后遇到"调试口不通"，**先怀疑目标在跑重负载代码，而不是先怀疑接线**
（与 14.1 里"探针被判不能用"是同一类错误归因）。

**⚠️ 对今后作业的影响**：只要 DVI 引擎在跑，SWD 就可能随时失联。
⇒ **要稳定调试，应烧一个"不启动 DVI 引擎"的固件**（或让引擎可被内核停掉），
只在需要看画面时才让它跑。

**当前状态（2026-10-01 深夜，用户断电重启后）——失效方式变了，这是关键线索：**

| 阶段 | 症状 | 判读 |
|---|---|---|
| ① 断电**前** | DP 可读（`DPIDR`）+ **AP 全 WAIT** ⇒ `Examination failed` | 总线被跑着的固件占死 |
| ② 断电**后** | **`Error connecting DP: cannot read IDR`**（100/500/1000 kHz 全不行） | **DP 层都读不到 ⇒ 按 `指令本` 规矩 10：先查共地/接线**（断电时线可能松了）|

⚠️ **两个阶段要分清**：①是"目标占死总线"，②是"物理链路"。**别把②当成①的延续** ——
这正是项目历史上把原因归错的那类错误。

**重启后目标板 USB 恢复枚举了**（`PID_0009` + **COM7** + Reset 接口）⇒ 芯片在跑。
但**串口只在启动瞬间有输出**（固件主循环不打印），事后接上去读不到东西 ⇒ **不能拿串口替代 SWD 读变量**。

#### ⚠️ 用户澄清（2026-10-01 深夜）：**共地有 5 条（算电脑 USB 内部共地是 6 条）**

用户原话：**"足足5条，算上电脑USB内部共地6条！"**

**🔴 这 5 条地的来历（用户 2026-10-01 深夜亲述，本会话最重要的一条发现）：**

> **"每次你说查共地，我都加一根，加一根。"**

⇒ **这是一条【文档引发的硬件故障】**：
- 规矩 10 的原意是"**地必须共通**"——描述的是一个**状态**；
- 但原文写成 **"`cannot read IDR` 先查共地"** —— 一个**动作**；
- 被反复读成 **"再加一根地线"** ⇒ **加一根、加一根，加到 5 条** ⇒ **地环路**；
- **⇒ 规则本身制造了它想消除的那个故障。**

**✅ 规矩 10 已按此重写**（`docs/工作守则.md`）：不再写"查共地"这种可执行成"加线"的动作，
改成**直接说清三种原因 + 正确做法是【减到单点接地】**。

**⚠️ 通用教训（值得进 `docs/陷阱.md`）**：**规矩要写"目标状态"，不要写"可以反复执行的动作"。**
"先查 X"这种写法，在用户被反复打扰、又不懂底层原理时，**会被执行成"反复做 X"**，
而 X 往往是**有累积副作用的**（加地线、加压、加重试、加延时……）。

⇒ **"先查共地"这条建议在这里是错的** —— 地不是不够，是**太多**。
多套供电 + 多条地线 = **地环路（ground loop）**，各点电位不再相等，
SWD 的参考地就在漂。**`cannot read IDR` 的典型成因之一正是这个。**

**✅ 正确做法与"加地线"相反**：
- **只留一条地线**（单点接地），其余拔掉
- **只留一套供电**（这条文档里早就写过："建议调试时只留一套供电"）

### 14.14 ⭐⭐⭐ 2026-10-01 深夜·根因坐实（结构上）：没有自复位环 + 三个 lane 数组内存连续

**完整转储 40 条**（1–20 = `dma_list_error`，21–40 = `dma_list_active`）：

```
l0[6]:  tc = 8, 48, 24, 320, 8, 8         全部 write=TXF0  TREQ=0  CHAIN_TO=2
l1[7]:  tc = 80, 320, 80, 80, 80, 80, 80  全部 write=TXF1  TREQ=1  CHAIN_TO=4
l2[7]:  tc = 80, 320, 80, 80, 80, 80, 80  全部 write=TXF2  TREQ=2  CHAIN_TO=6
```

1. ✅ **确认：列表里【没有任何一条】的 `write_addr` 指向控制通道**（`0x50000080/0x100/0x180`）
   ⇒ **没有"自复位"条目**。
2. ✅ 每条都 `CHAIN_TO` 回**自己 lane 的控制通道** ⇒ 控制通道被重触发后会**接着读下一条**。
3. 🔴 **而三个数组在内存里是【连续】排列的**：

```
l0[0..5]  0x2005ad24 ─┐
l1[0..6]  0x2005ad84 ─┤ 紧邻
l2[0..6]  0x2005adf4 ─┘ 止于 0x2005ae64
```

**⇒ 机制**：lane0 的控制通道（ch2）读完 `l0[5]` 后，下一次读到的是 **`l1[0]`** ——
于是它把 l1 的参数（`write=TXF1`、`TREQ=1`、`CHAIN_TO=4`）**写进了 lane0 的数据通道 ch3**；
再往下滚就是 l2 的参数（`TXF2`/`TREQ=2`）。
**⇒ 这正是 §14.13 实测到的 `ch3/ch5 = TXF2 / TREQ_SEL=2`，不是读竞争，是【读越界】。**

**⇒ 还能解释"IRQ 只剩 635 次/秒"**：**扫描线结束的 IRQ 靠【同步 lane】的数据通道 CHAIN_TO 触发**；
同步 lane 一旦越界，它的 `CHAIN_TO` 就变成**隔壁 lane 的控制通道** ⇒ **同步链断掉** ⇒
"一行结束"不再按点发生 ⇒ IRQ 率崩到 635/s ⇒ 全链变慢。
**这与目标描述里那句"链条丢了触发"是同一件事。**

**⚠️ 仍未闭合的算术**：按"每字 3.8 µs"，一行 416 字要 1572 µs；而实测 READ_ADDR 显示控制通道
走了 **2~4 遍**列表，两者乘不上。⇒ **越界在结构上确凿，但它是否就是【最初那一下】还需一次实验。**

### 14.17 2026-10-01 深夜·因果链补完 + 修法设计（未实施，后被 14.18 否掉）

#### A. 这是一个【正反馈环】

```
控制通道读越界
  → 每个越界条目都在【重新编程数据通道】（写它的 READ/WRITE/COUNT/CTRL，
    TRANS_COUNT 被反复重置）
  → 数据通道的 320 字传输【永远完不成】
  → dbg_tcr 上不去 → 处理程序那段等待被拖长（实测 502~1854 µs）
  → _dvi_load_dma_op() 更晚才把读指针拨回第 0 段
  → 越界更严重  ⟲
```

**⇒ 它同时解释了三个此前拼不上的数**：
① 每字 3.8 µs（应 79 ns，慢 48 倍）—— 传输被反复打断；
② `tcr_timeouts=0`（守卫从没打满）—— 传输**最终**还是完成了，只是极慢；
③ 活体 READ_ADDR 显示走了 2~4 遍列表 —— **越界是自持的**。

**⇒ 上一任的 `_dvi_fill_unused_slots()` 治好了"永久死机"（`EN=0`），
但尾部副本仍然【继续链、继续重新编程数据通道】，所以环还在转。**

#### B. ⚠️ 为什么"让尾条不链"是【错】的修法

尾部那些"空白副本"**是故意的**：**处理程序重建列表期间，链条必须靠它们活着**。
若尾条 `CHAIN_TO` 指向自己 ⇒ 链条停下 ⇒ 而 `_dvi_load_dma_op()` 用的
`dma_channel_configure(..., false)` **只装填不触发** ⇒ **没人再启动控制通道 ⇒ 引擎直接挂死。**
（这正是目标描述里那句"数据通道一旦停住就无人重新触发它"。）

#### C. ✅ 正确修法：**自复位尾条**（让控制通道把读指针拨回第 0 段）

**原理**：`dma_cb_t` 的 `write_addr` 可以指向**任意地址**。控制通道执行一个条目时，
只是把该条目的 4 个字写进 `write_addr`。**所以只要把一个尾条的 `write_addr`
指向【控制通道自己的寄存器】，它就变成"重装自己"的自复位条目。**

**具体做法（放在 `_dvi_load_dma_op()` 里最合适 —— 那里同时有 `dma_cfg` 和列表指针）**：

1. 每个 lane 备一个 4 字的"重装描述块" `s_ctrl_reload[3]`（`dma_cb_t` 大小，静态）；
2. `_dvi_load_dma_op()` 配好控制通道之后，**把它 4 个寄存器的当前值快照进 `s_ctrl_reload[i]`**
   （即 `{read_addr=该 lane 第 0 段地址, write_addr=&ch[chan_data], transfer_count=4, ctrl=...}`）；
   —— 用快照而不是重算，**避免手抄 `_dvi_load_dma_op` 里的配置逻辑**；
3. 把**该 lane 数组的最后一个槽位**改写成：
   `{read_addr = &s_ctrl_reload[i], write_addr = &dma_hw->ch[chan_ctrl], transfer_count = 4, ctrl = <写4字、无DREQ、CHAIN_TO=自己>}`；
4. ⇒ 链条走完真实段 + 空白段后，最后一条**把控制通道读指针拨回第 0 段并重新使能它**，
   环被切断，且不依赖处理程序的时序。

**保留 `_dvi_fill_unused_slots()` 的空白副本**（它们仍是处理程序重建期间链条的"续命"段），
只是最后一条从"空白"换成"自复位"。

### 14.21 2026-10-01 深夜·打脸与修正：`FLEVEL` 读反过，但结论经 `FSTAT` 复核后仍成立

**RP2350 的 `FLEVEL` 是【4 位一个字段】，不是"低 16 位 TX / 高 16 位 RX"：**

```

TX1 = bits 11:8    RX1 = bits 15:12
（TX2/RX2、TX3/RX3 在 16 位以上）
```

⇒ 此前看到的 `FLEVEL = 0x00080000`，置位的是 **bit19 ⇒ TX2 字段 = 8（满的）**。
**我"TX 位为 0 ⇒ FIFO 空 ⇒ PIO 饿死"的解读是错的，方向甚至相反。**
**⇒ 这是第 10 次寄存器解码错误，而它一直是我整条"PIO 饿死"推理的基石。**

**✅ 改用 `FSTAT`（非粘滞、字段独立）复核后，结论仍成立：**

```

  TXEMPTY (bits 27:24) = 0xf    ⇒ 【所有 TX FIFO 空】⇒ SM 在等数据 ✅
  RXFULL  (bits 3:0)   = 0x7    ⇒ RX 全满（★ 见下）
FLEVEL = 0x00000000             ⇒ 全空（与 TXEMPTY 一致；上次 0x00080000 是瞬时）

⇒ **"PIO 饿死"这次是站得住的（独立证据），但它不再是我原来那条推理链的产物。**

**★ 新疑点（未验证）**：`RXFULL = 0x7` —— RX FIFO 是满的，而这是个**只做 `out`** 的串行器，
程序里没有 `in`/`push`。**猜测是 `FJOIN_TX=1` 时 RX 状态位无意义（假象），但没证实。**

**🔴 核心矛盾原封不动**：`TXEMPTY=0xf`（PIO 饿死）**+** DMA 配置逐项按 SDK 复核全对
—— **两者不可能同时成立。**

### 14.25 2026-10-01 深夜·段不能砍（引擎冻死）+ 一个能对上数的模型 + 我的仪表有漏洞

之后的方向就明确了：**换一种不用 `out pc` 的串行器写法**（例如用 `mov pindirs` / 固定的两位输出）。

### 14.37 🎯🎯🎯 2026-10-01 深夜·根因定案：`out pc, 1` 约 14.6 时钟【后被 14.54 改写为 side-set 代价】

**做法**：把三种写法的循环放进**同一个固件、同一个 helper、同一套 PIO/SM/DMA 配置**，
唯一差别是循环体本身：

```
V0  out pc, 1 ×2（无 opt）    : 4738 µs
V1  out pc, 1 ×2（有 opt）    : 7722 µs
V2  pull block + jmp 0 [18]   :  324 µs   ✅ 正好 = 4096 × 79 ns（= 20 时钟/字 × 4096）
g_bench_done = 7（三个全部跑成功）
```

**⇒ 同样 20 时钟/字的预算、同样的 FIFO/DMA/时钟，`pull` 版 324 µs、`out pc` 版 4738 µs。**

**⇒ 根因：`out pc, 1` 在这块 RP2350 上每次执行约 **14.6 个时钟**，而不是 1 个。**

#### 它一次解释了此前所有反常（这就是那个"所有构建共有"的量）

- DVI 串行器用 `out pc, 1` 输每一个 bit ⇒ **实际 TMDS 位时钟约 17 Mbit/s，而非 252 Mbit/s**
- ⇒ 帧率在所有构建里不变（最小固件 / 完整固件 / 音频开关 / 我所有补丁）
- ⇒ TX FIFO 恒空（SM 比设计慢 ~15 倍）
- ⇒ 行时长差 **12 倍**（12 ≈ 14.6）
- ⇒ 与"`dbg_tcr == 320` 77% 等不到"也自洽（供给远慢于预期）

#### 下一轮：换掉串行器写法

**方向**：设计一个**不写 PC** 的 1-bit/时钟串行器。约束是 side-set 的两位必须互补
（`0b10`/`0b01`），而"发哪一对"目前靠 `out pc` 选指令来编码。

候选（待验证周期数）：
1. `out x, 1` → `mov pins, x`（2 指令/bit ⇒ 126 Mbit/s，仍只到一半）
2. 找一条**直接把 1 个 bit 输出到两个引脚**的指令组合
3. 若都不行 ⇒ 可能需要把 TMDS 符号的编码方式改成"每 2 bit 一次指令"的打包形式

**⚠️ 这条结论同时意味着**：`dvi_min`、完整固件、以及库里所有的节拍假设**都建立在"1 bit/时钟"上**，
而这个前提在 RP2350 上不成立 ⇒ **修好串行器是唯一能让整条链回到设计速率的事**。

### 14.38 ⚠️ 2026-10-01 深夜·判别：不是 `out pc` 特有，而是"每 bit 一条 out + autopull"

再加一个变体 `out pins, 1 ×2`（编码 `0x7001` / `0x6801`，同结构但写 PINS 而不是 PC）：

```
V0  out pc, 1 ×2      : 4739 µs   ❌
V2  pull block + jmp [18] :  324 µs   ✅ 对照
V3  out pins, 1 ×2    : 4217 µs   ❌【也一样慢】
g_bench_done = 0xf（四个全部跑成功）
```

**⇒ `out pins, 1` 一样慢 ⇒ §14.37 里"`out pc` 这条指令贵"的说法【不准确】。**

**⇒ 慢的是这个模式本身：每 bit 一条 `out` + autopull ⇒ 每字约 292 时钟（≈14.6 时钟/bit）。**

#### 剩余未分离的差异只有一个

| | 循环 | 取数据方式 |
|---|---|---|
| V2 ✅ 324 µs | `pull block` + `jmp [18]` | **显式 pull** |
| V0/V3 ❌ ~4.7 ms | 每 bit 一条 `out` ×2 | **autopull（阈值 20）** |

**⇒ 下一轮要分离的是【autopull 本身】。**

#### 下一轮的实验（同时是候选修法）

**关掉 autopull，改显式 `pull`**：展开成 20 条 `out` + 1 条 `pull`（21 条指令的循环）。
预期 21 时钟/字 ≈ 86 ns。**这正是库自带 `dvi_serialiser_debug` 变体的结构。**

- 若 ~350 µs ⇒ **autopull 是罪魁**，展开+显式 pull 可用
- 若仍 ~4.7 ms ⇒ 是"每 bit 一条 `out`"的固有代价，需换更粗的输出粒度

**⚠️ 一个尚未解决的约束**：`side_set 2` 的取值是**每条指令固定**的，
而 TMDS 的**数据正是靠"选哪条指令执行"来编码** ⇒ 展开成 21 条固定指令后，数据无处可放。
⇒ 下一轮必须一并解决（可能需要改成"用 `out pins` 输出数据 + side-set 只做固定互补"的形式）。

### 14.39 ⚠️ 2026-10-01 深夜·实验没跑成，但把板子救回来了（两条工具教训）

**我想加的变体**：展开 20 条 `out` + 1 条显式 `pull`（关 autopull），预期 21 时钟/字 ≈ 86 ns。

**结果**：我的改动引入回归 ⇒ 固件**挂在基准里**，DVI 从未启动：

```
frank_hdmi_heartbeat_lines = 0     dvi0.dvi_frame_count = 0
g_bench_done = 0     pc = 0x10003246
```

**✅ 定位手法（值得记）**：`arm-none-eabi-addr2line -f -C -e <elf> 0x10003246`
⇒ 直接给出 `dma_channel_is_busy`（`dma.h:932`），反汇编确认是一个
`ldr r3,[r3,#16] / tst r3,#0x4000000 / bne` 的自旋 ⇒ **DMA 通道永远 BUSY，SM 一个字节没消费。**

**⇒ 两条教训：**

1. **`dma_channel_wait_for_finish_blocking()` 没有超时** —— 基准里一旦 SM 不吃，**整个固件跟着挂死**。
   任何新的基准变体都必须用**有界的轮询**（带计数器）替代它。
2. **改基准 = 改固件的启动路径**（基准跑在 DVI 之前）⇒ **它挂住就等于整机挂住**，
   所以基准的改动风险远高于它的"诊断"身份给人的印象。

**✅ 收尾做得对**：用 addr2line 从 halt 住的 PC 定位 → 回退到最后一个已知可用版本（`881792b` 的四变体版）
→ 重编译重烧 → **读回三个计数器确认恢复**（心跳 8991 在涨、帧数 38、`g_bench_done=0xf`）。
**没有丢下一块挂住的板子。**

### 14.40 ✅ 2026-10-01 深夜·基准改成有界轮询，验证通过 ⇒ 从此挂不死

把 `run_variant()` 里的 `dma_channel_wait_for_finish_blocking(ch)` 换成有界轮询：

```c
uint32_t guard = 20000000u;
while (dma_channel_is_busy(ch) && --guard) { tight_loop_contents(); }
uint32_t dt = time_us_32() - t0;
```

**验证（烧写后读回）**：

```
V0 out pc ×2    : 4739 µs   ✓ 与改前逐位一致
V2 pull（对照） :  325 µs   ✓
V3 out pins ×2  : 4217 µs   ✓ 与改前逐位一致
g_bench_done    = 0xf       ✓ 四个全跑成功
心跳            = 6741 在涨 ✓ DVI 照常运行
```

**⇒ 没破坏任何东西，而基准从此不会再挂死整机。**

#### 顺带修掉一个盲点

**§14.39 那个"全零"其实并不能说明是哪个变体挂的** —— 因为所有结果都只在
`pio_dma_bench_run()` **末尾**统一写入。现在有界轮询**超时也会返回已用时间**
⇒ 哪个变体挂了、挂了多久，一眼可见。

**✅ 下一轮可以放心跑那个 autopull 判别了**（展开 20 条 `out` + 显式 `pull`，预期 ≈86 ns/字）。

### 14.41 2026-10-01 深夜·V4（展开+显式 pull）是死路；有界轮询救了一次

```
V0  out pc ×2 + autopull        :   4741 µs
V2  pull + jmp [18]（对照）     :    324 µs   ✅
V4  展开 20×out + 显式 pull     : 873016 µs   ❌❌  g_bench_done = 0x1f
心跳                            = 8000 在涨 ✓【固件没挂】
```

**✅ 第 13 轮的"有界轮询"当场见效**：V4 的 873 ms 就是守卫超时的时长（说明 DMA 在守卫内从未完成，
即那个程序**根本不消费**），**而固件照常启动**。若还是旧的阻塞等待，这一轮又会挂死整机。

**⇒ V4 这个方向是死路**（展开成固定指令后，数据无处可放的问题之外，它连消费都不工作）。

#### 🔴 但更重要的：我发现自己前面一个【混淆】

| | 每字 | 它在做什么 |
|---|---|---|
| V2 ✅ 324 µs | 79 ns | **只 `pull` + 延时 —— 一个 bit 都不输出** |
| V0 ❌ 4741 µs | 1157 ns | 每字输出 20 个 bit（每 bit 一条 `out`） |

**⇒ V2 只证明了"DMA + FIFO 能喂多快"，它【根本没测串行器的节拍】。**
**⇒ 所以 §14.33/§14.36 里"pull 版正常、out 版慢 14.6 倍"这个对比是【混淆】的**
（两者做的事根本不同）。

**⇒ 真正剩下的问题只有一个：**

> **为什么一条"输出 1 个 bit"的 `out` 要花 ~14.6 个周期？**

（20 × 14.6 = 292 周期/字 ✓ 与 V0 实测吻合。）

**⇒ 下一轮的方向**：查 `out pins, 1` / `out pc, 1` 的单条代价来源 ——
候选：① 每个 bit 都在改引脚引起的总线/IO 代价；② autopull 每次触发时的停顿；
③ RP2350 上 `out` 的流水线代价。**需要一个能单独隔离"1 条 out 的周期数"的实验。**

### 14.42 2026-10-01 深夜·`out null` 隔离不成立；并发现基准里一个会误导人的缺陷

**想做的隔离**：`out null, 1` ×2（同结构、同 side-set，但不碰引脚/PC/内部寄存器）
⇒ 若它也慢，代价在 `out`/autopull 机制；若它快，代价在"每 bit 改引脚"的 IO。

**实测**：

```
V0  out pc        :   4739 µs
V2  pull（对照）  :    325 µs
V5  out null      : 873016 µs   ❌ ← 与 V4 的数【一模一样】
g_bench_done      = 0x3f（六个都标成"跑完"）
心跳              = 11453 在涨 ✓【固件没挂】
```

**⇒ 873016 µs 两次出现且完全相同 ⇒ 那是【守卫超时的固定时长】** ⇒ V5 也是"DMA 从没完成、
根本不消费"。

**⇒ 最可能的原因：`out null` 不推进移位计数器**（NULL 是丢弃、不算移出）
⇒ autopull 永不触发 ⇒ 一个字节都不从 FIFO 取 ⇒ 超时。**⇒ 这个隔离设计错了。**

#### 🔴 顺带发现基准里一个会误导人的缺陷

**守卫超时时 `run_variant` 仍返回 `ok = true`** ⇒ `g_bench_done` 显示"六个都跑完"，
**而 V4/V5 实际是超时**。我上一轮就是把 873 ms 读成"跑完了但很慢"。

**✅ 应该修**：守卫用尽 ⇒ 返回 `ok = false`（并在结果里区分"耗时"与"超时"）。

**⇒ 下一轮的更可靠做法**：不要再用 `out null` 这类"语义可疑"的指令做隔离，
而是**在正常能跑的 `out pins` 变体上换参数**（例如把 autopull 阈值从 20 改成 10，
看每字耗时是否随之减半 ⇒ 直接算出"每条 out 的周期数"）。

### 14.43 2026-10-01 深夜·阈值会决定"消不消费"；修掉了骗了三次的谎报

**实验**：在会消费的 `out pins, 1` ×2 变体上，把 autopull 阈值 20 改成 10。

```
V2  pull（对照）        :    325 µs
V3  out pins，阈值 20   :   4217 µs
V6  out pins，阈值 10   : 873016 µs   ❌ ← 【第三次】出现同一个数
g_bench_done = 0x7f（七个都标成"跑完"）
```

**⇒ 873016 µs 出现三次（V4/V5/V6）且完全相同 ⇒ 那是【守卫的固定超时时长】**
⇒ **任何等于该值的结果都意味着"超时、根本没消费"**（这是一条有用的判读签名）。

**⇒ 而 V6 超时说明：autopull 阈值一改，SM 就【完全不消费】了**，不只是变慢。
⇒ 阈值会决定"消不消费"，这是一条很硬的线索，但**原因未明**。

#### ✅ 修掉了那个骗了我三次的缺陷

`run_variant()` 结尾原来是**无条件** `*ok = true;`，所以超时也报成功。

**改成**：`*ok = (guard != 0);`

**验证**：`g_bench_done` 从 `0x7f` 变成 **`0x0f`** ——
**正好只有 V0/V1/V2/V3（真跑完的）置位，V4/V5/V6（超时的）正确标为失败。**

**⇒ 基准从此不再谎报，后续实验不会再被这个坑误导。**

> ## 真根因（都是 RP2350/RP2350B 相关，库是按 RP2040 + 小引脚号写的）

> **② ★★★ 数据脚方向从来没被设成输出** —— `frank_serialiser.pio` 里原文：
> ```c

> # 🏆🏆🏆 第 48 轮：**找到了"从来没有画面"的根因 —— RP2350B 的 PIO GPIO 基址**
>
> **SDK 原话（`hardware/pio.h`，RP2350 专属段落）**：
> > *"On RP2350B, there are 48 pins but each PIO instance can only address 32 pins
> > (the PIO instance either addresses pins 0-31 or **16-47** based on `pio_set_gpio_base`).*
> > ***If `PICO_PIO_USE_GPIO_BASE != 1` then bit 5 of the pin number is ignored.***"
>
> **⇒ DVI 用的引脚是 32~39，而 `32 = 0b100000` —— bit 5 正是被忽略的那一位！**
>
> | 现象 | 解释 |
> |---|---|
> | **`PINCTRL=0x14000000`（`OUT_BASE=0`/`SET_BASE=0`）** | SDK 把 **bit5 抹掉**了 ⇒ 我传的 32/34/36 → 0/2/4 |
> | **`EXECCTRL=0x0001f000`（`SIDESET_BASE=0`）** | 同上 ⇒ **不是"配置没写进去"，是【被抹掉了】** |
> | **从来没有画面** | **PIO 实际在驱动引脚 0~7，而不是 32~39** ⇒ 那 8 根 DVI 引脚上什么都没出来 |
> | **帧率 5 / 40 fps 都能测到** | 数据流（DMA/FIFO/SM）是通的，但**信号从未到达 DVI 引脚** |
>
> **✅ 修法（两处）**：
> 1. **编译定义 `PICO_PIO_USE_GPIO_BASE=1`**（否则 SDK 继续忽略 bit 5）
> 2. **DVI 初始化里加 `pio_set_gpio_base(cfg->pio, 16)`**（窗口 16~47 ⇒ 覆盖 32~39）
>
> **⇒ 这是 fork 为 RP2040 写、而 RP2350B 特有的坑。工程里 `pio_set_gpio_base` 只在 SDIO 的
> `#ifdef PICO_SDIO_GPIO_BASE_16` 里出现过，DVI 这条路上【从来没人设过】。**
> **⚠️ 这也意味着：在本轮之前，我们测到的所有"帧率"都只是【数据流速度】，
> 与"信号有没有出去"无关 —— 而信号【一直没出去过】。**
>

> **🔴 2026-10-01 深夜·第 29~31 轮的重大更新（压缩后先看这段）**

> **突破**：把 `frank_serialiser.pio` 的 **`.side_set 2` 去掉** ⇒ 帧率 **3.3 → 18.1 fps（5.5 倍）**。

> **⇒ 那 ~13 周期/条 的代价，就是【side-set 每周期切换差分对引脚】。**

> **⚠️ 但由此得到一个三角约束（这是现在最卡的地方）：**
>
> | 写法 | 引脚有输出 | SM 会 pull | 速度 |
> |---|---|---|---|
> | `out pc,1` **+ side-set**（库原版） | ✅ | ✅ | ❌ 3.3 fps |
> | `out pc,1` **无 side-set** | ❌ | ✅ | ✅ 18.1 fps |
> | `out pins,1` / `out x,1` / `out null,1` | ✅ | **❌ 停摆** | — |
>
> **已多次坐实（真实 DVI + 基准都复现）**：**写 X / PINS / NULL 这些非 PC 目标，会让 SM 彻底停止 pull**
> —— **且与 side-set 无关**。
>
> **⚠️ 第 36 轮更正 + 新线索（把 `FLEVEL` 按 SDK 权威布局逐字段重解）**：
> ```
> 失败现场 FLEVEL = 0x00080808
>   TX0 = 8【满】  RX0 = 8   TX1 = 8【满】  TX2 = 0【空！】
> ```
> **⇒ 不是"三个都满"，而是【SM0 和 SM1 卡住、SM2 还在消费】。**
> **⇒ 而正常工作时（无 side-set 的 40 fps 版）`FLEVEL = 0`（三个全空，都在消费）。**
> **⇒ 于是谜题从"所有 SM 都停"缩小成："为什么三个跑同一个程序的 SM 会有不同命运？"**
> —— 这是个更有抓手的问题（下一步应逐 SM 读 `ADDR`/`INSTR`/`FSTAT` 对比，而不是笼统看 `FLEVEL`）。
>
> **✅ 第 37 轮：健康状态的逐 SM 参照系（跟失败变体对比用）**
> ```
> 健康（库原版、5 fps）：PIO0 CTRL=0x7  FSTAT=0x0f000f07  FDEBUG=0x07000000  FLEVEL=0
> SM0 = SM1 = SM2 【三个完全一样】：
>   CLKDIV=0x00010000  EXECCTRL=0x0001f000  SHIFTCTRL=0x680e0000
>   ADDR=0  INSTR=0x000070a1(=out pc,1 side 0b10)  PINCTRL=0x14000000
> ```
> **⇒ `FSTAT` 的 `TXEMPTY=0xf`（三个 TX FIFO 全空）+ 三个 SM 都停在 `ADDR=0`（第一条 `out`）
> ⇒ 完全自洽：健康状态下三个 SM 都在第一条 `out` 上等 FIFO 数据，这正是 DREQ 节流设计的正常样子。**
> **⇒ 失败变体（`out pins,1`）则表现为 TX0/TX1 满、TX2 空 ⇒ 拿这张表逐项比就能看出差异。**
>
> **🎯 第 38 轮：两边的对照想通了，机制是一个【死锁】**
>
> | | FIFO 状态 | 含义 |
> |---|---|---|
> | **健康（原版、5 fps）** | **空**（`TXEMPTY=0xf`） | SM 停在 `out` 上等数据 ⇒ **它把数据【消费掉了】** |
> | **失败（`out pins`）** | **满**（TX0/TX1=8） | SM 也停在 `out` ⇒ **但它【从没消费过】** |
>
> **⇒ 两边都"停在 `out` 上"，区别是【FIFO 是被喂进去的、还是被吃掉的】。**
> **⇒ 指向死锁：`out` 在等一个**空的 OSR**，而 **autopull 从未触发** ⇒ FIFO 灌满后互相等住。**
> **⇒ 也就是说：失败变体里【autopull 根本没在工作】——**
> 这跟"写非 PC 目标 ⇒ SM 停止 pull"那条规律一致，现在它有了机制：
> **不是 SM 停了，而是 `out` 堵在空 OSR 上、autopull 又不补。**
>
> **✅ 判别（下一轮，一次 halt 就够）**：在失败变体上读
> **`FDEBUG`（`0x50200008`，看 `TXSTALL` 粘滞位）+ `SHIFTCTRL`（确认 `AUTOPULL`/`PULL_THRESH` 真的落地）**。
> - 若 `AUTOPULL=1` 且 `PULL_THRESH=20` 都在、却仍不补 ⇒ **autopull 的触发条件与该指令不兼容**（那是 RP2350 的行为差异）
> - 若某个字段没落地 ⇒ **就是配置没写进去**（更好修）
>
> **🎯🎯 第 39 轮：用【已有数据】就把上面那一步做完了，而且它【否证了死锁假设】**
>
> **权威位域（`$SDK/src/rp2350/hardware_regs/include/hardware/regs/pio.h`）：**
> `TXSTALL = 27:24` · `TXOVER = 19:16` · `RXUNDER = 11:8` · `RXSTALL = 3:0`
>
> | | `FDEBUG` | 含义 |
> |---|---|---|
> | **健康（原版、5 fps）** | **`0x07000000`** | bit24/25/26 置位 ⇒ **三个 SM 的 `TXSTALL` 都置位** ⇒ 它们在等 FIFO（DREQ 节流下的正常现象） |
> | **失败（`out pins`）** | **`0x00000000`** | **`TXSTALL` 全清** ⇒ **SM 从没尝试过 pull** |
>
> **⇒ 若是死锁（`out` 堵在空 OSR 上），它【正是在等数据】⇒ `TXSTALL` 应该置位。而它是清的
> ⇒ SM 根本没在等数据，而是【压根没发出 pull 请求】。**
> **⇒ 所以机制不是"堵住"，而是【autopull 从未触发】—— SM 一路跑下去、从不问 FIFO 要数据。**
>
> **✅ 下一步（很小）**：读失败变体的 `SHIFTCTRL`（`0x502000d0`），确认 `AUTOPULL=1`、`PULL_THRESH=20` 是否

> # 🎯🎯🎯🎯🎯 第 46 轮：**找到了 —— `WRAP_TOP = 31`，而它应该是 1**

> 0x0001f000 = 0000 0000 0000 0001 1111 0000 0000 0000
>                        bits16:12 = 0b11111 = 31   ← ★
>                        bits11:7  = 0b00000 =  0
> ⇒ WRAP = [0, 31]  —— 整个 PIO 指令内存；而这条程序只有 2 条指令 ⇒ 应该是 [0, 1]
> ```
>
> ## 这一条解释了**全部现象**
>
> | 观察 | 解释 |
> |---|---|
> | **`out pc,1` 能工作** | 它**每周期都分支到 0/1** ⇒ **根本不碰 wrap** |
> | **`out x`/`out pins`/`out null` 停止 pull** | 它们靠 PC 自增 ⇒ **0→1→2→…→31 一路执行 30 条垃圾指令**（PIO 内存里还放着 debug UART 程序），根本不在 DVI 的节奏上要数据 |
> | **`ADDR = 9`** | **就是走到一半被我抓到的** |
> | **FIFO 灌满、`TXSTALL` 全清** | 它没在执行那条 `out` |
> | **只跑 1 行就停** | 第一遍还正常，之后开始绕垃圾 |
>
> **⇒ "只有 `out pc` 能工作"根本不是 autopull 的怪癖，而是【它是唯一不依赖 wrap 的写法】。**
>
> ## ⇒ 真相是**两个独立的 bug**
>

> **⇒ 两个都修掉 ⇒ "不分支 + 引脚有输出"的写法 ⇒ 点亮屏幕。**

### 14.44 ⭐ 2026-10-02·把算术钉死：每条 `out` 额外花约 13.6 个周期

**从已有实测能唯一确定的两条：**

```
V2  pull + jmp [18]  （20 周期/字的预算，【没有 per-bit 的 out】）:  324 µs ⇒  79 ns/字 = 20 周期
V0  out pc,1 ×2      （【同样】20 周期/字的预算，但有 20 条 out）: 4739 µs ⇒ 1157 ns/字 = 292 周期
                        差值：20 条 out 额外花掉 272 个周期 ⇒ 【每条 out ≈ 13.6 周期】
```

**✅ 顺带证明了一件重要的事**：V2 的 79 ns/字 **恰好等于 20 个 252 MHz 周期**
⇒ **SM 的时钟确实跑在 252 MHz，`clkdiv=1` 是真的生效的。**
⇒ **所以"每条 `out` ≈ 13.6 周期"不能用"SM 时钟慢了"来解释。**

#### 已排除的两个解释

- **不是 FIFO 供给不足**：V2 同样依赖同一个 DREQ/FIFO，却稳定拿到 20 周期/字
  ⇒ **DMA 有能力每 20 周期送一个字** ⇒ V0 里不该饿死。
- **不是 `out pc` 特有**：V3（`out pins,1`，不碰 PC）同样 ~4217 µs（§14.38）。

#### ⇒ 剩下的可能

1. **RP2350 上 `out` 指令本身的流水线代价**（每次改变输出目标/pin 状态都要额外周期）
2. **autopull 每次触发时的固定停顿**——但按阈值 20 算，每 20 bit 才触发一次，
   若那就是 272 周期，则停顿集中在 pull 上
3. 我的基准里三个变体共有的某项配置（虽然已经尽力对齐）

**✅ 下一步的判别（便宜且干净）**：
**在 V0（会消费、~4739 µs）上把 `clkdiv` 从 1 改成 2** ——
- 若耗时**正好翻倍** ⇒ 说明代价是**真实的 SM 周期**（支持可能 1 或 2）
- 若**几乎不变** ⇒ 说明那 13.6 周期不是 SM 时钟驱动的，而是某种**固定时延**（如 IO/总线往返）
  ⇒ 方向立刻改写

**⚠️ 必须用"会消费"的变体**（`out pc`/`out pins` + autopull 20），不要再用 `out null`/阈值 10/展开那些
已证明**根本不消费**的形式（§14.42/§14.43）。

### 14.45 🔴 2026-10-02·clkdiv=2 也不消费 ⇒ 浮现"只有唯一一组配置会消费"的模式

**实验**：在 V0（会消费）上把 `clkdiv` 从 1 改成 2。

g_bench_done = 0x0f   ← 只有 V0-V3 成功，V4–V7 全标失败 ✅【§14.43 的谎报修复在正常工作】
```

**⇒ 只是把分频改成 2（本该只是慢一倍），SM 就【完全不消费】了。**

| 变体 | 消费？ |
|---|---|
| **V0：`out pc,1` ×2 + autopull 阈值 20 + clkdiv 1** | ✅ **只有它** |
| V1 同 V0 但 `.side_set 2 opt` | ❌ |
| V3 `out pins,1` ×2 | ❌ |
| V5 `out null,1` ×2 | ❌ |

### 14.49 🔴 2026-10-02·纯分析："DMA 一直 BUSY"的含义被读错 ⇒ 问法要改

**我此前把基准里"守卫超时"读成"SM 不消费"。** 但推一下就发现这个读法站不住：

```
若 SM 是停的 / 被禁用的 ⇒ 它的 TX FIFO 就是"不满"
                        ⇒ DREQ 一直有效
                        ⇒ DMA 会【立刻】把 4096 字搬完并结束（根本不会 BUSY）
若 DMA 一直 BUSY ⇒ DREQ 从未有效 ⇒ 【FIFO 一直是满的】⇒ 只能是 SM 根本没在 pull
```

**⇒ ⇒ 所以 V1/V3/V5/V6/V7 那些"超时"变体，不是"慢"，而是【SM 完全不 pull】。**

#### 于是问法必须改

**旧问法**（我前面几轮一直在问）："为什么一条 `out` 要 ~13 个周期？"
**新问法**：**"为什么一改【目的地 / autopull 阈值 / 分频】，SM 就彻底不再 pull 了？"**

而且新的问法**更容易回答**：SM 是否 pull 是可以用**寄存器直接看出来的**——
halt 后读该 SM 的 `SHIFTCTRL`（确认 AUTOPULL 和 PULL_THRESH 真的落地）、
`FSTAT`（它的 TXEMPTY 位）、以及 `addr`/`instr`（它在不在执行、停在哪条）。

**⚠️ 而这也解释了为什么"只有 V0 会消费"看起来那么反常** ——
如果原因是"某个配置项没落地 / 某个字段互相覆盖"，那确实会出现"只有一组精确组合能工作"。

**✅ 下一轮的优先动作（比继续换参数值钱得多）**：
**在一次 halt 里把某个"不 pull"变体的 SM 寄存器全部读出来**
（`SHIFTCTRL`、`EXECCTRL`、`PINCTRL`、`CLKDIV`、`ADDR`、`INSTR`、`FSTAT`），
**和 V0 的同一组寄存器逐字段对比** —— 差异会直接指出是哪个配置没落地。

### 14.50 ⭐ 2026-10-02·纯分析：把结论与那个可疑的基准解耦

**下一步应该是：直接改 DVI 的串行器写法，看帧率是否跳上去。**
候选（按把握排序）：
1. **把 `out pc, 1` 换成"先把 1 bit 取到寄存器、再一次性写两脚"的形式**（避免每 bit 都做 PC 写/分支）
2. **一次输出多个 bit**（例如每 2 bit 一条指令），把指令数砍半
3. 查 RP2350 手册里 `OUT` 的周期表（§14.48 那三条外部线索里可能有）

**⚠️ 但先记住**：DVI 的 SM 配置**已经逐字段验证正确**，所以这不是"配置没写对"，
而是**这个写法在该芯片上的固有代价** —— 换写法才是正路。

### 14.51 ⭐ 2026-10-02·纯设计：一个可能真能修好的串行器写法

#### 根本约束（为什么现在必须每 bit 写一次 PC）

```
.program dvi_serialiser
.side_set 2
	out pc, 1  side 0b10     ← 数据【靠"选哪条指令"】编码
	out pc, 1  side 0b01
```

side-set 的取值是**每条指令固定**的，所以"发 `0b10` 还是 `0b01`"只能靠**跳到不同的指令**来表达
⇒ **必须每 bit 写一次 PC**（`out pc, 1`）。**而 PC 写正是我实测"每 bit ~13 周期"的头号嫌疑。**

#### ✅ 破法：把数据从"选指令"搬到"引脚值"

```
out pins, 2      ← 一条指令输出 2 个 bit 到引脚 p、p+1；【不写 PC】
```

**只要 TMDS 编码器把【每个 TMDS bit 预先展开成 2 bit】（`0b01` 或 `0b10`），
`out pins, 2` 一条指令就正好输出一个 TMDS bit 的差分对 —— 与现在完全等价。**

#### 代价（要改的地方，按工作量排）

| # | 要改什么 | 说明 |
|---|---|---|
| 1 | **`frank_serialiser.pio`** | 两条 `out pc,1 side …` → 一条 `out pins,2`（配合 autopull 阈值） |
| 2 | **`frank_serialiser.c` 的 SM 初始化** | 要设 `out_pins` 基址为该 lane 的差分对、并调整 `out_shift` 阈值（每个 TMDS bit 现在占 2 个 OSR bit） |
| 3 | **TMDS 编码器**（`frank_tmds.c` / `tmds_encode.S`） | 输出要**从"每字 2 个 10-bit 符号"变成"每字 16 个展开后的 2-bit 对"** ⇒ 这是最大的一块 |
| 4 | **DMA 表的字数** | `h_active_pixels / DVI_SYMBOLS_PER_WORD` 之类的口径要跟着变（数据量翻倍） |

**⚠️ 风险**：第 3 项要动 TMDS 编码，是本项目最"数学"的一块。
**⇒ 更稳的中间态应先试**：**只把 `out pc,1` 换成 `out x,1` + `mov pins,x`**（2 条指令 1 bit，
不写 PC），若它比现在快，就说明"PC 写"确实是代价所在，再决定要不要上第 3 项。

### 14.52 🔴🔴 2026-10-02·换写法让引擎只跑 1 行就停，但换来一条很硬的规律

**实验**：把 `frank_serialiser.pio` 的两条 `out pc, 1 side …` 换成
**`out x, 1 side 0b10` + `mov pins, x side 0b01`**（2 条指令 1 bit，**不写 PC**）。

**结果**：

```
FRAMES = 0     HB-LINES = 1          ← 只跑了 1 行
FLEVEL = 0x00080808                  ← 【三个 TX FIFO 全满】⇒ SM 停止 pull
SM0 ADDR = 9
```

**⇒ 引擎停摆。已回退（`git checkout` 该 .pio）并重烧验证恢复：33 帧/10 秒、770 行/秒、`FLEVEL=0`。**

#### ⭐ 但由此浮现一条**横跨基准与真实 DVI 的硬规律**

| 程序 | SM 是否还在 pull |
|---|---|
| **`out pc, 1` ×2（原版）** | ✅ **在 pull** |
| `pull block` + 延时 | ✅ 在 pull |
| **`out x, 1` + `mov pins, x`（本轮，真实 DVI）** | ❌ **停止 pull（FIFO 全满）** |
| `out pins, 1` ×2（§14.38，基准） | ❌ 停止 pull |
| `out null, 1` ×2（§14.42，基准） | ❌ 停止 pull |
| 阈值改 10 / 分频改 2 / 展开版（§14.43/14.45） | ❌ 停止 pull |

**⇒ 只写 `pc`（以及显式 `pull`）能维持 pull；写 `X` / `PINS` / `NULL` 都会让 SM 彻底停住。**

**⇒ 这把"我的基准有毛病"与"真实 DVI 一换写法就死"两件事**连成了同一条规律** ——
它不再是"我基准的 bug"，而是一个**真实、可复现、且非常反直觉的 PIO 行为**。

**⚠️ 而它反过来也说明**：`out pc, 1` 这个"怪写法"**并不是随便写的** ——
它可能是**唯一**能让 autopull 在这颗芯片上正常工作的形式。
**⇒ 所以我一度想"换掉它"的方向，恐怕是错的。**

**✅ 下一轮方向（改写）**：不再试图换掉 `out pc`，而是**搞清"为什么只有写 pc 能维持 pull"**。
候选：① `out` 到非 PC 目标时**不推进/不检查移位计数器**（故 autopull 永不触发）；
② 到 PC 时因**分支重启流水线**而恰好给了 autopull 时机。
**判别**：把 `out x, 1` 换成 `out x, 1` **但阈值设成 1**（每 bit 都尝试 pull）看是否恢复 ——
若恢复，则"计数器不推进"成立。

### 14.53 ⭐⭐ 2026-10-02·纯分析：线索推到终点且量化很干净【后被 14.54 改写】

#### 理论：`out pc, 1` 本该【已经满速】

```
每 bit 一条 `out pc, 1`（它按数据位跳到另一条指令）
⇒ 每字 20 条指令 ⇒ 若每条 1 周期 = 20 周期/字 = 79 ns
⇒ 而这【正是设计目标】—— DVI 的列表就按"每字 20 bit"算的（tc = 640/2 = 320）✓
```

**⇒ 这个写法在理论上【不需要任何改动】就能满速。**

#### 实测：每条 `out pc` 约 13.6 周期

```
实测 292 周期/字（= 1157 ns）× 20 条指令/字 ⇒ 每条 ≈ 13.6 周期
```

**⇒ 于是得到了一个干净的量化结论：**

> **`out pc` 这个分支在 RP2350 上每条要 ~13 个周期。**
> **SM 时钟 252 MHz ÷ 13 ≈ 19 Mbit/s，而目标是 252 Mbit/s ⇒ 差 13 倍**
> **⇒ 与全程实测的"12~13 倍"完全吻合。**

#### 这解释并统一了三件事

1. **为什么换任何写法都更快不了**：换成 `out x`/`out pins`/`out null` 会**让 autopull 死掉**（§14.52）
2. **为什么"1 bit/时钟"这个前提从没人质疑**：**它在 RP2040 上是对的**，
   而 `out pc` 的分支代价大概是 RP2350 特有的（PicoDVI 是给 RP2040 设计的）
3. **为什么所有构建都慢同样的倍数**：这是**指令级的固有代价**，与内核/子系统/我的补丁都无关

#### ⇒ 真正的修法被逼成两个必要条件（缺一不可）

- **必须是【不分支】的写法**（否则每条 ~13 周期）
- **同时必须能让 autopull 正常工作**（否则 SM 停摆）

**⇒ 而 §14.51 那个 `out pins, 2`（2bit 预展开）方案，恰好同时满足这两条。**
**⇒ 它仍然是正解方向 —— 只是必须先解决"为什么非 PC 目标会让 autopull 死掉"。**

**✅ 下一轮第一件事**：**在基准里用 `out x, 1` + 阈值 1 做判别**（§14.52 已写好做法）。
若它恢复 pull ⇒ "移位计数器只在写 PC 时推进"成立 ⇒ 那就要**用别的方式喂计数器**
（例如周期性插入一条 `out pc` 之类）—— 那才是让 `out pins, 2` 方案可行的关键。

### 14.54 🎉🎉🎉 2026-10-02·最新一轮：去掉 side-set ⇒ 帧率 3.3 → 18.1 fps（5.5 倍）

**实验**：把 `frank_serialiser.pio` 的 `.side_set 2` 去掉，两条指令也不再带 `side`：

```asm
.program dvi_serialiser
.origin 0
	out pc, 1        ; 数据仍靠"选指令"编码，但不再每周期切换差分对引脚
	out pc, 1
```

**实测（12 秒）**：

```
FRAMES       = 217  ⇒ 【18.1 fps】   （改前 33/10秒 = 3.3 fps）⇒ 5.5 倍
FLEVEL       = 0                    ⇒ SM 正常 pull ✓（不是"停住"造成假快）
SM0 INSTR    = 0x000060a1           ⇒ 正是"无 side-set 的 out pc,1"编码 ✓
TCR-TIMEOUTS = 4                    ⇒ 几乎不超时
```

**⇒ ⇒ 那 ~13 周期/条的代价，就是【side-set 每周期切换差分对引脚】。**

#### 🔑 而它直接指出了真正的修法

我前面那次 `out x, 1` + `mov pins, x` 的尝试之所以失败，**是因为它还带着 `.side_set 2`** ——
它同时吃了**"side-set 的代价"**和**"让 autopull 死掉"**两个问题。

**⇒ 正确做法：去掉 `.side_set`，改用 `mov pins, x` 驱动引脚**（不再靠 side-set 切换）。

#### 距离目标

```
用户第一阶段目标：点亮屏幕、30 fps 就够
现在：18.1 fps  ⇒ 只差 1.7 倍
```

**⚠️ 但"点亮屏幕"还有另一个前置条件**：面板锁定靠的是 **TMDS 位时钟**（要 ~252 MHz）。
**当前位流仍未达标**（18.1 fps 说明 SM 仍远慢于 1 bit/周期）——
**⇒ 必须先把"1 bit/周期"做到，面板才可能锁上。**

### ⚠️ 2026-10-02 · 【修正】"换编码器函数"这条走不通，真正要做的是**移植一个不复制版 asm 循环**

```

**⇒ 而且"横向复制"在这个路径里的机制是：**

```
pixwidth = h_active_pixels = 640

### 🎯 2026-10-02 · 【最关键】"横向像素复制"的确切机制与不复制版的实现路径

**机制（已读 asm + 表注释确认，不再需要猜）：**

```
frank_tmds.S:75  tmds_encode_loop_16bpp:
    lsls r2, #2                     ; 输出字节数 = n_pix * 4  ⇒ 每输入像素产出 4 字节 = 2 个符号
1:  ldmia r0!, {r4, r6}             ; 每轮读 2 个 32 位字 = 4 个 RGB565 像素
    do_channel_16bpp r2, r4, r5     ; 经 interp0/interp1 查表：PEEK0→r4, PEEK1→r5
    do_channel_16bpp r2, r6, r7
    stmia r1!, {r4, r5, r6, r7}

而库注释原文：
  "The symbol table contains each control symbol *twice*, concatenated into
   20 LSBs of table word, so we can always do word-repeat."
```

**⇒ 结论：复制不是循环写两遍，而是【表项 = 同一符号的两份（2×10bit）】，
配合 `DVI_SYMBOLS_PER_WORD=2`（PIO 每次推进吃 20bit = 2 个符号）⇒ 一次查表供两个符号。**

**⇒ 不复制版的正确实现路径：**

| 步骤 | 内容 |
|---|---|
| 1 | 生成一张"单份符号"的表（表项 = 1 个 10bit 符号 + 10bit 填充），或直接由现有表右移 10 位取单份 |
| 2 | 改 asm 循环：查表得到**两个相邻像素各自的符号**后，`orr`/`lsls` 拼进同一个 32 位字再 `stmia` |
| 3 | 输出字数减半（`lsls r2, #1`），DMA 表长口径随之调整（`h_active / DVI_SYMBOLS_PER_WORD`） |
| 4 | 逻辑画布宽 320 → **640**（源像素数要等于 h_active） |
| 5 | 帧缓冲 640×240×1B = 153,600 B（+77KB）⇒ 从 `KMEM_ARENA_CAPACITY`(320KB, kernel_mem.c:86) 挪 |
| 6 | 输出仍 640×480p60 ⇒ 252MHz / SM_CLKDIV=1 / PWM 像素时钟都不变 ✓ |

**⚠️ 第 2 步每 2 像素多约 4 条指令 ⇒ 行内编码耗时上升 ⇒ 实施后要重量行率（当前 61fps，有余量）。**

**当前状态：构建绿色、板子未动、工作树干净。**
