### 阶段1 —— `docs\DVI攻坚流水-阶段1.md`（2026-10-01 深夜前半）

**覆盖**：原始 22–781 行。最早一批实测（`dvi_frame_count` 4.6 fps / `g_dvi_irq_count` 2400 线每秒 / 慢约 13 倍）、
gdb 工具教训、"SWD 会被反复 halt 搞死"与**共地 5 条线的来历（用户原话）**、控制通道读越界、
上一任 AI 留在源码注释里的半套修复、`DVI_TCR_WAIT_GUARD` 10 万→2000 的突破。

**结论**：
- **配置层面逐项按 SDK 复核全对**（DMA 列表 / `TREQ_SEL` / `CHAIN_TO` / SM 分频 / `SHIFTCTRL` / `FLEVEL` 位域），
  慢 13 倍**不是配置错** —— 但每查一轮就错一次寄存器解码（共 10 次），教训是**只用 gdb 按符号读**。
- `14.8`"瓶颈在 Core1 算力"被 `14.9` 翻案：Core1 有 **99.4% 时间在等空闲 TMDS 缓冲**，纯编码只要 **25 µs**。
- 引擎侧确实有结构缺陷：**控制通道 `READ_ADDR` 跑到 lane 数组之外**（14.13/14.14 用 gdb 符号地址坐实）；
  上一任早已诊断并只用 `_dvi_fill_unused_slots()` 做了半套兜底（14.16，注释在 `frank_dvi_timing.c:341-387`）。
- `14.17` 的自复位尾条设计与 `14.18` 的 `DREQ_FORCE` 都被实测**否掉**（收口 287→315 行/秒；`DREQ_FORCE` 315→23）。
- **唯一有效的修复**：`DVI_TCR_WAIT_GUARD` 100000→2000（`frank_dvi.c:137`）⇒ 1.3 → **5.0 fps**
  （14.19）—— **有效，但不是最终根因**。
- 14.23 把配置层查空后**改用最小对照固件** ⇒ 这是后面所有进展的转折点（"为什么走到下一步"）。

### 阶段2 —— `docs\DVI攻坚流水-阶段2.md`（2026-10-01 深夜后半）

**覆盖**：原始 782–1424 行。`src/pio_dma_bench.c` 最小基准、段不能砍、"软件洗清"、
帧率顽固不变、三把尺子（基准 / `dvi_min` / 累加器）、基准的两次自伤与修复。

**结论**：
- **硬件与配置都无罪，问题在库的用法**：最小基准 **8.5 ns/字** vs 引擎 **~845 ns/字**（约 100 倍）⇒
  嫌疑指"每行的 6~7 段链条往返"（14.24/14.25 的模型 859 µs vs 实测 845 µs ✅）。
- **软件彻底洗清**（14.26 完整仪表 + 14.34 累加器平均 **61 µs = 15.8% CPU**）⇒
  **帧率在所有构建里顽固不变**（链条结构、处理器耗时、音频、最小固件…都试过）⇒ 限速方是"所有构建共有"的量（14.34）。
- 排除：DMA 响应慢 DREQ（14.33，20 时钟版误差 **0.6%**）、`.side_set 2 opt`（14.36 反而更慢 1.6 倍）、
  "列表没走完"（14.32 **推翻** 14.26，实测控制通道刚好各走完自己整段）。
- **两把尺子被建成且可复用**：基准 `pio_dma_bench` 挂不死（14.40 有界轮询）且不谎报（14.43 `*ok = (guard != 0)`）；
  **判读签名：结果 == `873016 µs` ⇒ 超时、根本没消费**；`dvi_min` 与完整固件一样慢 ⇒ 与内核/SDIO/PSRAM 无关。
- 嫌疑收敛到"**每 bit 一条 `out` + autopull**"这个模式（14.35/14.37/14.38）—— ⚠️ 后被 `阶段4 §14.54` 改写为
  "**代价来自 side-set**，不是 `out` 本身"。

### 阶段3 —— `docs\DVI攻坚流水-阶段3.md`（§14.0 旧结论摘要 + 第 29~54 轮）

**覆盖**：原始 1425–2064 行。2026-10-02 的"最新状态/收工状态"两块、**板上九处改动表**、
以及倒序的最早一批"第 29~54 轮"（"引脚上永远没信号"的两条真根因就在这一段）。

**结论**：
- **2026-10-02 最新状态（原文标注"本节为准"）**：**屏幕已点亮**、引擎稳定 **61.3 fps**（行频 31.5 kHz，
  正是 640×480p60 所需）、**竖条纹/隔行已修**；剩两件事：**20%/6 像素异常带** 与 **红色偏弱**。
  ⚠️ 该 61.3 fps **当时未记编译器版本** ⇒ 见本文件开头的统一注。
  ⚠️ **帧率口径至今没对齐**：10 秒窗口 60.6/61.6 fps（第 50/51 轮）vs **60 秒长跑只有 24.85 fps**（第 52 轮更正）。
- **两条 RP2350/RP2350B 特有的真根因**（"引脚上从来没信号"的真正原因）：
  ① `pio_set_gpio_base(cfg->pio, 16)` —— RP2350B 的 PIO 只能寻址 0~31 或 16~47，DVI 用 32~39
  且 SDK 会**忽略 bit 5**；② **数据脚方向从来没被设成输出** —— `3u << data_pins`（32/34/36）是
  **32 位移位溢出 ⇒ 掩码 = 0**，6 根数据脚一直是输入。铁证：修复前后 `CHANGES_32..39` 从全 0 变成全部在翻转。
- 第 46 轮：**`WRAP_TOP = 31`（应为 1）**也是真问题之一 —— "只有 `out pc,1` 能工作"不是 autopull 怪癖，
  而是**它是唯一自带分支、不依赖 wrap 的写法**。
- **第 52 轮用户质问**（原话在阶段3）换来本册最贵的一条教训：
  **当指标不经过目标本身时，它涨得再漂亮也不能当成功**（"帧率"从来不是画面的证据）。
- 已排除的歧路：**"整体按比例放慢让信号自洽"**（算术不成立：19.4 Mbit/s ⇒ 像素时钟 1.94 MHz，
  连 320×240@60 要的 12.6 MHz 都差 6.5 倍）—— 别再试。

### 阶段4 —— `docs\DVI攻坚流水-阶段4.md`（2026-10-02 定案与收尾）

**覆盖**：原始 2065–2731 行。§14.44–§14.54（"13.6 周期"模型的成立与动摇、抓到 `EN=0` 现场、
实验分离出限速方、**去掉 side-set ⇒ 18.1 fps**）+ 附录B补「屏幕亮了之后的收尾阶段」。

**结论**：
- **只有唯一一组精确配置会消费**（`out pc,1` + autopull 20 + clkdiv 1）；任何扰动
  （`opt` / 输出目标 / 阈值 / 分频 / 展开）都**让 autopull 彻底死掉**而不是变慢（14.45/14.49/14.52 的硬规律表）。
- 抓到"链条丢了触发"的现场：`CH7 CTRL=0x00058606 ⇒ EN=0`（越界读来的垃圾控制块）——
  而防住它的防线**正是自己用 `#if 0` 关掉的那个**（14.46）；打开后问题 2 消失（`dbg_tcr=320`、
  超时占比 63~77% → 28%），**帧率不变（4.7→3.5 fps）⇒ 用实验分离出"它不是限速方"**（14.47）。
- **本阶段最后一轮（14.54）**：去掉 `.side_set 2` ⇒ **帧率 3.3 → 18.1 fps（5.5 倍）**，
  `FLEVEL=0` 证明不是"停住造成的假快" ⇒ **那 ~13 周期/条的代价 = side-set 每周期切换差分对引脚**。
  正确修法：**去掉 `.side_set`，改用 `mov pins, x` 驱动引脚**（`out x,1` + `mov pins,x` 那次失败是因为**它还带着 side-set**）。
  距用户第一阶段目标（30 fps）只差 **1.7 倍**；但**面板锁定还要求位流到 ~252 Mbit/s**，仍未达标。
- 收尾阶段（附录B补）：**颜色问题的源码级结论**（编码/映射/调色板/引脚驱动**全部正确** ⇒
  "红消失"不在这几处，最大嫌疑是**接收端把 RGB 当 YCbCr 解**）；**修竖条纹的确切方案**
  （横向像素复制 = 表项里同一符号两份 + `DVI_SYMBOLS_PER_WORD=2`；fork 走 interp+asm 路径、
  **没有** libdvi 的 SIO `fullres` 符号 ⇒ 要**移植一个"每像素只产 1 个符号"的 asm 循环**）；
  **Core0 会周期性重启**（引擎计数单调递增 ⇒ 不是整片复位）；**好区/坏区会对调** ⇒
  三 lane 水平错位在漂移（同步 lane 的 DMA 分段结构与数据 lane 不同）。

## 〔2026-10-05 晚 **实测**：画面恒定的根因 = **Core1 结构性产能不足**（关掉阶段1 §十四 开篇那条"唯一没排除"的 `sys_clk` 线索 ✓）〕

**症状**：屏幕恒定（纯白 → 最终"无信号"），切颜色 / 切图案 / 改帧缓冲**全部无效** ✗，但 app 侧一切正常（见下）✓。

**已排除的（逐条实测，都不成立 ✗）**

| 假设 | 实测 | 结论 |
|---|---|---|
| 帧缓冲没画对 | `G` 键转储：纯白=`01 01…`、条纹=`02 02\|00 01 00 01…` | **正确** ✓ |
| 引擎没指向我们的缓冲 | 新增 getter ⇒ `engine_fb == g_fb` **YES** ✓ | **指向正确** ✓ |
| 等待队列卡住 | `[wait] colour=0/18 valid=1/19 free=0/1390` | **都不等** ✓ |
| **`sys_clk` 不是 252MHz** | `[clk] clk_sys=252000000 Hz` | **就是 252** ✓（阶段1 开篇那条线索关闭 ✓）|
| 停机/未归位 | 遥测持续在出（`irq` 在涨）、心跳在跳、无 `[STALL]` | **在跑** ✓ |

**根因（直接测量 ✓）**

```
Core1 主循环一圈 = 43 µs   ⇒ 产能 = 1/43µs = 【23,255 圈/秒】  ✗
640×480@60 的时序需要        = 【31,500 行/秒】               ✗
⇒ 差 26% ⇒ 永远追不上 ⇒ TMDS 环里拿不到新数据 ⇒ DMA 重复旧行 ⇒ 画面恒定 ✗
编码耗时 enc≈27µs/行（三次 tmds_encode）+ 其余约 16µs = 43µs（不是被等待，是在干活 ✓）
```

**为什么会突然要 31.5k** ✓：`docs\DVI攻坚流水-阶段3.md` §14.0「板上九处改动」表（原本文件 :1449-1459）
- 第 6 条 `DVI_VERTICAL_REPEAT 2→1`（修掉竖条纹 ✓）
- 第 8 条 `FRANK_HDMI_LOGICAL_HEIGHT 240→480`（**配合第 6 条**：每行不再发两遍 ✓）
⇒ 两条合起来把**每帧要编码的行数翻倍**（240→480）✗ ⇒ 需要 28800 行/秒 ✗ > 产能 23255 ✗

**⇒ 两条出路（供决策 ✓）**
- **A. 回到 `REPEAT=2` + `LOGICAL_H=240`** ✓ ⇒ 只需 **15.75k 行/秒** ✓ < 23.3k ✓✓（余量 48% ✓）
  代价：**可能带回当初那个"竖条纹/隔行"** ✗ —— 但那正是当初改 #6 的原因 ✓
  （`frank_dvi.c:673,680` 用 `v_ctr % DVI_VERTICAL_REP` 决定是否重发同一逻辑行 ✓）
- **B. 把 Core1 提快 ≥35%** ✗ —— 例如减少 `enc` 的 27µs（`docs\DVI攻坚流水-阶段4.md` §附录B补 提过
  "每像素只产 1 个符号"的 asm 路径 ✓）
  代价：移植/优化工作量，且要重新验证 ✓

**⇒ 尚未验证**：A 方案的实际效果（`n/irq` 是否升到接近 1.0、画面是否出现）——
这是下一步该做的 A/B 实验 ✓（**别把它当结论** ✗）。
