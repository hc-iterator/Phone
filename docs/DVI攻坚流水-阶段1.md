### 14.7 ✅ 2026-10-01 深夜·已排除：DMA 列表本身完全正确

**手段**：gdb 直接打印结构体本体（`p dvi0.dma_list_active`），**不经我手解码**。

```
struct dvi_scanline_dma_list { dma_cb_t l0[6]; dma_cb_t l1[7]; dma_cb_t l2[7]; }
dma_cb_t = { read_addr, write_addr, transfer_count, ctrl }

l0: write_addr=0x50200010(TXF0)  ctrl=0x0080421B → TREQ_SEL=0 CHAIN_TO=2  ✅
l1: write_addr=0x50200014(TXF1)  ctrl=0x0082821B → TREQ_SEL=1 CHAIN_TO=4  ✅
l2: write_addr=0x50200018(TXF2)  ctrl=0x0084C21B → TREQ_SEL=2 CHAIN_TO=6  ✅
```

⇒ **每 lane 的目标 FIFO、DREQ、CHAIN_TO 全对。** 之前那套"整排错位一个 lane"是**读活体寄存器时的假象**，不是硬件错。（位域用 SDK 定义复核：`TREQ_SEL=(ctrl>>17)&0x3F`、`CHAIN_TO=(ctrl>>13)&0xF`。）

**每行搬运字数**（列表内容）：lane0 = 8+48+24+320+8+8 = **416 字**；lane1/lane2 = 80×6+320 = **800 字**。（lane0 是同步 lane，tc 模式不同属正常。）

**⇒ 至此已排除**：sys_clk、PIO/PWM 分频、timing 模式、音频、TCR 等待、DMA 列表/DREQ。**剩下的方向**：IRQ 里那句 `dvi_update_scanline_data_dma()`（有有效扫描线时每行重建 active 列表）是不是耗时主因 —— 这是唯一还没量过的每行工作。

### 14.8 ⭐⭐ 2026-10-01 深夜·推论：瓶颈在 Core1（编码端）而不是 DMA/PIO【后被 14.9 翻案】

**已排除**（见 14.7 与本节）：
- `dvi_update_scanline_data_dma()`：last 0 µs / max 2 µs ⇒ 不是它
- IRQ 里那段 TCR 等待：last 502 µs / max 1854 µs ⇒ **它只是在"观察"慢，不是原因**
- 我加的"超时重排整条链"：`g_dvi_tcr_timeouts=0`、`tmo_lane=0xFFFFFFFF` ⇒ **一次都没跑，无辜**
- 总线争用：`frank_hdmi_init` **已经把 Core1 与 DMA 读写设为高总线优先级**

**⚠️ 一个被长期误用的数字**：`g_dvi_loop_frames` **不是显示帧率**。Core0 的主循环是 `draw_test_pattern(); make_tone(); sleep_ms(16);` ⇒ 47/s 只是"重画测试图 + 睡 16ms"的速率。**DVI 引擎整个跑在 Core1**（`multicore_launch_core1(frank_hdmi_run_core1)`）。

**★ 真正的引擎产出计数器**（此前从没读过）：`frank_hdmi_heartbeat_lines` / `_frames` —— 在 `core1_main()` 的循环里每行自增。**6 秒实测**：

| 计数器 | 6 秒值 | 换算 | 应有 |
|---|---|---|---|
| `frank_hdmi_heartbeat_lines`（Core1 产出行数） | **1725** | **287 行/秒** | 31500 |
| `frank_hdmi_heartbeat_frames` | 7 | 0.6 fps | 60 |
| `g_dvi_irq_count`（引擎实际显示行数） | 3810 | 635 行/秒 | 31500 |
| `dvi0.dvi_frame_count` | 8 | 1.33 fps | 60 |

⇒ **Core1 每秒只吐 287 行**，引擎显示 635 行/秒（差的那部分在放"红色错误行"）。⇒ **Core1 是瓶颈端。**

**每行 CPU 工作量**：`encode_one_scanline_16bpp()` 要调 3 次 `tmds_encode_data_channel_16bpp()`（**已确认在 RAM**，`frank_tmds.c:83` 带 `__not_in_flash_func`），外加两次 `queue_remove_blocking`（其中 `q_tmds_free` 实测为空）。⇒ 287 行/秒 ⇒ **每行约 3.5 ms**（应 ≲30 µs）。

**🔴 而根子上是个设计取舍**：库的注释写明它**假定 CPU 跑到 TMDS 位时钟的 2 倍**：

> "libdvi's TMDS serialiser SMs and PWM pixel clock are configured with
>  DVI_SM_CLKDIV=2 … Concretely: typical CPU clock is 504 MHz driving a 252 MHz TMDS link."

本项目跑 **252MHz + DVI_SM_CLKDIV=1** —— **位时钟是对的（252MHz），但 CPU 只有一半周期去做每行的 TMDS 编码**。而当初选 252MHz 正是因为**实测 504MHz 会把这块板子跑挂**（Core1 进 HardFault、Core0 卡到连 SWD 都 halt 不住）。⇒ **"稳定（252MHz）"与"编码吞吐（需 ~2×）"是一对矛盾**，这是 4.6 fps 的结构性原因。

**下一步（未做）**：量 `encode_one_scanline_16bpp` 内部三段（`q_colour_valid` 等待 / 3 次编码 / `q_tmds_free` 等待）各占多少 —— 判定是"算力不够"还是"被队列阻塞"。若是算力 ⇒ 只能抬主频（并解决 504MHz 的稳定性）或降低编码量（半分辨率/灰度）。

### 14.9 ⭐⭐⭐ 2026-10-01 深夜·翻案：卡在"等空闲 TMDS 缓冲"【后被 14.24 推翻】

**实测 `encode_one_scanline_16bpp` 内部三段**（µs）：

| 段 | last | max | 占比 |
|---|---|---|---|
| 等 `q_colour_valid` | 0 | 2 | ~0% |
| **等 `q_tmds_free`** | **4341** | **103331** | **99.4%** |
| 纯 3 次 `tmds_encode_data_channel_16bpp` | **25** | 28 | 0.6% |
| （整行合计） | 4367 | 103357 | |

⇒ **编码只要 25 µs（行预算 31.7 µs，绰绰有余）。Core1 有 99.4% 时间在等空闲缓冲。**

**🔴 严重订正 14.8**：上一轮说"Core1 算力不够"**是错的**。Core1 是**受害者**：它想产 31500 行/秒，却只能拿到 287 次缓冲。

**真正的瓶颈回到引擎行率**：TMDS 缓冲由**引擎的 DMA IRQ** 归还，而引擎只跑 **635 行/秒**（`g_dvi_irq_count`），所以缓冲回收速率就是 635/s。
⇒ 引擎每行周期 ≈ 1572 µs，其中几乎全是 **TCR 等待** ⇒ **数据通道搬 ~416 个字要 1572 µs（3.8 µs/字），而按设计只需 79 ns/字 —— 慢 48 倍**。而 PIO FIFO 是空的（等数据）、DMA 配置复核全对。

**⇒ 待查（下一轮）**：为什么 PIO 每字要 3.8 µs（设计 79 ns）？候选：① SM 实际时钟远低于 252MHz；② DMA 对 DREQ 的响应被某种节流；③ 通道在"完成 → CHAIN_TO → 控制通道重装填"之间丢了触发（但从 `tcr_timeouts=0` 看，最终是完成了的）。

**⚠️ 方法论教训（本次第 7 次）**：我在 14.8 里凭"287 行/秒"就断言"Core1 算力不够"，**没有先量它内部各段**。⇒ **"慢"和"谁慢"是两件事，必须量到段级再下结论。**

### 14.10 🔴 2026-10-01 深夜·重要：跑着的 DVI 固件会把 SWD 调试口占死

**现象**（连续多次 halt/resume 采样时发生）：

```
Info : SWD DPIDR 0x4c013477          ← DP 层【能读】
Warn : Too long SWD WAIT, issuing DAPABORT
Error: Failed to read memory at 0xe000ed00    ← AHB-AP 过不去
Error: [rp2350.dap.core0] Examination failed
```

⇒ **DP 层正常、但内存/AP 访问全部 WAIT 超时** ⇒ **总线被占死，调试访问进不去。**

**试过的救援（都无效）**：`rp2350-rescue.cfg`（设救援位 → 清零 → 打印 `Now attach a debugger...`）⇒ 之后复查仍 `Examination failed`；普通 `reset halt`、`reset` ⇒ 同样失败。⇒ **只能【物理断电 / 按 RUN】才能恢复。**

**🔴 这条很可能是历史悬案的真相**：项目文档里长期写着"SWD 物理层断开、四种速率全 `cannot read IDR` ⇒ 怀疑接线/GND"。**但这次的证据指向另一个原因：跑着的固件把总线占死。** ⇒ 以后遇到"调试口不通"，**先怀疑目标在跑重负载代码，而不是先怀疑接线**（与 14.1 里"探针被判不能用"是同一类错误归因）。

**⚠️ 对今后作业的影响**：只要 DVI 引擎在跑，SWD 就可能随时失联 ⇒ **要稳定调试，应烧一个"不启动 DVI 引擎"的固件**（或让引擎可被内核停掉），只在需要看画面时才让它跑。

**当前状态（2026-10-01 深夜，用户断电重启后）——失效方式变了，这是关键线索：**

| 阶段 | 症状 | 判读 |
|---|---|---|
| ① 断电**前** | DP 可读（`DPIDR`）+ **AP 全 WAIT** ⇒ `Examination failed` | 总线被跑着的固件占死 |
| ② 断电**后** | **`Error connecting DP: cannot read IDR`**（100/500/1000 kHz 全不行） | **DP 层都读不到 ⇒ 按 `指令本` 规矩 10：先查共地/接线**（断电时线可能松了）|

⚠️ **两个阶段要分清**：①是"目标占死总线"，②是"物理链路"。**别把②当成①的延续** —— 这正是项目历史上把原因归错的那类错误。

**重启后目标板 USB 恢复枚举了**（`PID_0009` + **COM7** + Reset 接口）⇒ 芯片在跑。但**串口只在启动瞬间有输出**（固件主循环不打印），事后接上去读不到东西 ⇒ **不能拿串口替代 SWD 读变量**。

#### ⚠️ 用户澄清（2026-10-01 深夜）：**共地有 5 条（算电脑 USB 内部共地是 6 条）**

用户原话：**"足足5条，算上电脑USB内部共地6条！"**

**🔴 这 5 条地的来历（用户 2026-10-01 深夜亲述，本会话最重要的一条发现）：**

> **"每次你说查共地，我都加一根，加一根。"**

⇒ **这是一条【文档引发的硬件故障】**：规矩 10 的原意是"**地必须共通**"——描述的是一个**状态**；但原文写成 **"`cannot read IDR` 先查共地"** —— 一个**动作**；被反复读成 **"再加一根地线"** ⇒ **加一根、加一根，加到 5 条** ⇒ **地环路**；**⇒ 规则本身制造了它想消除的那个故障。**

### 14.14 ⭐⭐⭐ 2026-10-01 深夜·根因坐实（结构上）：没有自复位环 + 三个 lane 数组内存连续

**完整转储 40 条**（1–20 = `dma_list_error`，21–40 = `dma_list_active`）：

```
l0[6]:  tc = 8, 48, 24, 320, 8, 8         全部 write=TXF0  TREQ=0  CHAIN_TO=2
l1[7]:  tc = 80, 320, 80, 80, 80, 80, 80  全部 write=TXF1  TREQ=1  CHAIN_TO=4
l2[7]:  tc = 80, 320, 80, 80, 80, 80, 80  全部 write=TXF2  TREQ=2  CHAIN_TO=6
```

1. ✅ **确认：列表里【没有任何一条】的 `write_addr` 指向控制通道**（`0x50000080/0x100/0x180`）⇒ **没有"自复位"条目**。
2. ✅ 每条都 `CHAIN_TO` 回**自己 lane 的控制通道** ⇒ 控制通道被重触发后会**接着读下一条**。
3. 🔴 **而三个数组在内存里是【连续】排列的**：

```
l0[0..5]  0x2005ad24 ─┐
l1[0..6]  0x2005ad84 ─┤ 紧邻
l2[0..6]  0x2005adf4 ─┘ 止于 0x2005ae64
```

**⇒ 机制**：lane0 的控制通道（ch2）读完 `l0[5]` 后，下一次读到的是 **`l1[0]`** —— 于是它把 l1 的参数（`write=TXF1`、`TREQ=1`、`CHAIN_TO=4`）**写进了 lane0 的数据通道 ch3**；再往下滚就是 l2 的参数（`TXF2`/`TREQ=2`）。**⇒ 这正是 §14.13 实测到的 `ch3/ch5 = TXF2 / TREQ_SEL=2`，不是读竞争，是【读越界】。**

**⇒ 还能解释"IRQ 只剩 635 次/秒"**：**扫描线结束的 IRQ 靠【同步 lane】的数据通道 CHAIN_TO 触发**；同步 lane 一旦越界，它的 `CHAIN_TO` 就变成**隔壁 lane 的控制通道** ⇒ **同步链断掉** ⇒ "一行结束"不再按点发生 ⇒ IRQ 率崩到 635/s ⇒ 全链变慢。**这与目标描述里那句"链条丢了触发"是同一件事。**

**⚠️ 仍未闭合的算术**：按"每字 3.8 µs"，一行 416 字要 1572 µs；而实测 READ_ADDR 显示控制通道走了 **2~4 遍**列表，两者乘不上。⇒ **越界在结构上确凿，但它是否就是【最初那一下】还需一次实验。**

### 14.17 2026-10-01 深夜·因果链补完 + 修法设计（未实施，后被 14.18 否掉）

#### A. 这是一个【正反馈环】

```
控制通道读越界
  → 每个越界条目都在【重新编程数据通道】（写它的 READ/WRITE/COUNT/CTRL，
    TRANS_COUNT 被反复重置）
  → 数据通道的 320 字传输【永远完不成】
  → dbg_tcr 上不去 → 处理程序那段等待被拖长（实测 502~1854 µs）
  → _dvi_load_dma_op() 更晚才把读指针拨回第 0 段
  → 越界更严重  ⟲
```

**⇒ 它同时解释了三个此前拼不上的数**：① 每字 3.8 µs（应 79 ns，慢 48 倍）—— 传输被反复打断；② `tcr_timeouts=0`（守卫从没打满）—— 传输**最终**还是完成了，只是极慢；③ 活体 READ_ADDR 显示走了 2~4 遍列表 —— **越界是自持的**。

**⇒ 上一任的 `_dvi_fill_unused_slots()` 治好了"永久死机"（`EN=0`），但尾部副本仍然【继续链、继续重新编程数据通道】，所以环还在转。**

#### B. ⚠️ 为什么"让尾条不链"是【错】的修法

尾部那些"空白副本"**是故意的**：**处理程序重建列表期间，链条必须靠它们活着**。若尾条 `CHAIN_TO` 指向自己 ⇒ 链条停下 ⇒ 而 `_dvi_load_dma_op()` 用的 `dma_channel_configure(..., false)` **只装填不触发** ⇒ **没人再启动控制通道 ⇒ 引擎直接挂死。**（这正是目标描述里那句"数据通道一旦停住就无人重新触发它"。）

#### C. ✅ 正确修法：**自复位尾条**（让控制通道把读指针拨回第 0 段）

**原理**：`dma_cb_t` 的 `write_addr` 可以指向**任意地址**。控制通道执行一个条目时，只是把该条目的 4 个字写进 `write_addr`。**所以只要把一个尾条的 `write_addr` 指向【控制通道自己的寄存器】，它就变成"重装自己"的自复位条目。**

**具体做法（放在 `_dvi_load_dma_op()` 里最合适 —— 那里同时有 `dma_cfg` 和列表指针）**：
1. 每个 lane 备一个 4 字的"重装描述块" `s_ctrl_reload[3]`（`dma_cb_t` 大小，静态）；
2. `_dvi_load_dma_op()` 配好控制通道之后，**把它 4 个寄存器的当前值快照进 `s_ctrl_reload[i]`**（即 `{read_addr=该 lane 第 0 段地址, write_addr=&ch[chan_data], transfer_count=4, ctrl=...}`）；—— 用快照而不是重算，**避免手抄 `_dvi_load_dma_op` 里的配置逻辑**；
3. 把**该 lane 数组的最后一个槽位**改写成：`{read_addr = &s_ctrl_reload[i], write_addr = &dma_hw->ch[chan_ctrl], transfer_count = 4, ctrl = <写4字、无DREQ、CHAIN_TO=自己>}`；
4. ⇒ 链条走完真实段 + 空白段后，最后一条**把控制通道读指针拨回第 0 段并重新使能它**，环被切断，且不依赖处理程序的时序。

**保留 `_dvi_fill_unused_slots()` 的空白副本**（它们仍是处理程序重建期间链条的"续命"段），只是最后一条从"空白"换成"自复位"。

**判据**：帧率跳上去 ⇒ 环被切断。**若不变** ⇒ 回到 §14.11 的三件测量。**⚠️ 风险**：这一步动了 DMA 链的收口，做错了会让引擎彻底停（但 SWD 还在，可回退）。

| 改前 | 287 | 1.3 |

### 14.19 🎉🎉 2026-10-01 深夜·突破：守卫 10万→2000 ⇒ 行率涨 4~5 倍【有效但非最终根因】

#### A. 先抓到一个**我自己造的**祸首

读 `g_dvi_tcr_timeouts` 发现：

```
g_dvi_tcr_timeouts = 4467 / heartbeat_lines = 12262   ⇒ 【36% 的行】在触发它
```

⇒ 我第 2 轮加的 `_dvi_restart_dma_chain()` + `return` 路径**在大量执行**，而它做的事是：
**abort 六条通道 → 装 `dma_list_vblank_nosync`（不是 active 列表）→ 启动控制通道 → `return`**，
把**正常的列表选择、队列回收、`_dvi_load_dma_op`** 全部跳过。
⇒ 三分之一的扫描线在放消隐表、缓冲不回收、链被反复推倒重来。
**✅ 已改成 `break`**（只跳出本 lane 的等待、继续走完处理器）。

#### B. 🎯 **真正的根因：那个等 `dbg_tcr == 320` 的循环，77% 的行永远等不到**

`want_tcr = h_active_pixels / DVI_SYMBOLS_PER_WORD = 640/2 = 320`。但 **`dbg_tcr` 数的是【当前这一次触发】的完成数**，而扫描线列表 `l0` 的 tc 序列是：

```
8, 48, 24, 【320】, 8, 8
              ↑ 320 在第 4 条，后面还有两条续命段
```

⇒ **一行跑完时，最后一次触发是那条 `tc=8` ⇒ `dbg_tcr = 8`，永远不是 320。** ⇒ "等 320" **只在恰好撞上第 4 条正在跑的小窗口里才成立**，其余时间守卫必然打满。

**实测**：`tcr_timeouts / 行数 = 1410/2248 = 63%`（守卫 10 万时），每行白烧约 **1.8 ms**。而这正是 §14.9 量到的"IRQ 处理器耗时 502~1854 µs"的来源。

**✅ 修法**：`DVI_TCR_WAIT_GUARD` **100000 → 2000**（与行预算同量级）。等待退化成"给一点点时间让数据排空"，而不是"烧掉 1.8 ms"。

| | 守卫 10 万 | **守卫 2000** |
|---|---|---|
| 行数 | 2246 | **11861** ⇒ **1186 行/秒** |
| 帧数 | 10 | **50** ⇒ **5.0 fps** |
| IRQ 处理器耗时 last | ~1.8 ms | **0 µs** |
| IRQ 处理器耗时 max | 1854 µs | **258 µs** |
| Core1 等缓冲 | 4341 µs | **129 µs**（改善 34 倍）|

**⇒ 判据①（引擎持续出帧）不但达成，而且速率提升了 4~5 倍。**

**⚠️ 仍未达标**：需要 31500 行/秒，现在 1186 ⇒ 还差 **26 倍**。且 `tcr_timeouts/行数` 仍为 **77%**（9144/11861）⇒ **这个等待依然几乎等不到，只是现在只花 ~258 µs 上限**。**下一轮：干脆把这个等待去掉，或把守卫再降一个量级。**

### 14.20 2026-10-01 深夜·瓶颈已搬家：Core1 是受害者不是元凶（原第 17 轮）

给 Core1 循环补上最后两处仪表后（10 秒实测，守卫 2000 的构建）：

#### 🔴 于是回到那个核心矛盾，并指向一个我一直当"铁证"的读数

**矛盾**：`FLEVEL` 显示 FIFO 空（⇒ PIO 在等数据），而 **DMA 配置逐项按 SDK 复核全对**。

**下轮要质疑的具体对象**：`FLEVEL = 0x00080000` 里的 **bit19**。按 RP2040 布局那是

### 14.21 2026-10-01 深夜·打脸与修正：`FLEVEL` 读反过，但结论经 `FSTAT` 复核后仍成立

**RP2350 的 `FLEVEL` 是【4 位一个字段】，不是"低 16 位 TX / 高 16 位 RX"：**

```
TX0 = bits 3:0     RX0 = bits 7:4
TX1 = bits 11:8    RX1 = bits 15:12
（TX2/RX2、TX3/RX3 在 16 位以上）
```

⇒ 此前看到的 `FLEVEL = 0x00080000`，置位的是 **bit19 ⇒ TX2 字段 = 8（满的）**。**我"TX 位为 0 ⇒ FIFO 空 ⇒ PIO 饿死"的解读是错的，方向甚至相反。** **⇒ 这是第 10 次寄存器解码错误，而它一直是我整条"PIO 饿死"推理的基石。**

**✅ 改用 `FSTAT`（非粘滞、字段独立）复核后，结论仍成立：**

```
FSTAT = 0x0f000f07
  TXFULL  (bits 19:16) = 0x0    ⇒ 没有 TX FIFO 满
  TXEMPTY (bits 27:24) = 0xf    ⇒ 【所有 TX FIFO 空】⇒ SM 在等数据 ✅
  RXFULL  (bits 3:0)   = 0x7    ⇒ RX 全满（★ 见下）
FLEVEL = 0x00000000             ⇒ 全空（与 TXEMPTY 一致；上次 0x00080000 是瞬时）
```

⇒ **"PIO 饿死"这次是站得住的（独立证据），但它不再是我原来那条推理链的产物。**

**★ 新疑点（未验证）**：`RXFULL = 0x7` —— RX FIFO 是满的，而这是个**只做 `out`** 的串行器，程序里没有 `in`/`push`。**猜测是 `FJOIN_TX=1` 时 RX 状态位无意义（假象），但没证实。**

**🔴 核心矛盾原封不动**：`TXEMPTY=0xf`（PIO 饿死）**+** DMA 配置逐项按 SDK 复核全对 —— **两者不可能同时成立。**
